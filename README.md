# DB Panel (mydbroot) — веб-панель управления семью СУБД

Универсальная админ-панель к **MySQL, MariaDB, PostgreSQL, SQLite, MongoDB, Redis и Oracle** в одном
интерфейсе: подключения, просмотр данных, CRUD, SQL-редактор, конструктор таблиц, импорт/экспорт,
резервные копии, пользователи БД и права, аудит, история запросов, мониторинг сервера.

Документация описывает **фактический текущий код** репозитория. Всё, чего в коде нет
(Monaco, материализованные представления, WebSocket-пуш, 2FA, S3-бэкапы), в ней не упоминается
как функция — такие места перечислены в разделе [Ограничения](#ограничения-и-известные-границы).

## Стек

### Backend (`backend/`, порт 3001)

| Слой | Пакеты |
|---|---|
| HTTP-сервер | `fastify@^5.3`, `@fastify/cors`, `@fastify/multipart`, `@fastify/rate-limit`, `@fastify/static` |
| Документация API | `@fastify/swagger`, `@fastify/swagger-ui` (`/docs`, `/docs/json`) |
| Хранилище метаданных | `better-sqlite3@^13` — `meta.db` (WAL), таблицы `connections`, `users`, `audit`, `query_history`, `design_snapshots`, `backup_schedules`, `backup_runs`, `table_checkpoints`, `data_undo` |
| Авторизация | `bcryptjs` (10 раундов), `jsonwebtoken` (JWT, TTL 12 ч) |
| Крипто | встроенный `node:crypto`: AES-256-GCM + `scryptSync` |
| Драйверы | `mysql2` (MySQL/MariaDB), `pg` + `pg-cursor` (PostgreSQL), `better-sqlite3` (SQLite), `mongodb` (MongoDB), `ioredis` (Redis), `oracledb` (Oracle, thin-режим) |
| Пулы | `mysql.createPool` (10 соединений) и `pg.Pool` (max 10, `statement_timeout=30000`) |
| Сборка/типы | TypeScript `^5.9.3`, `tsx` (dev-режим), `tsc` (сборка в `dist/`) |

### Frontend (`frontend/`, порт 3000 в dev, nginx:80 в Docker)

| Слой | Пакеты |
|---|---|
| UI | `react@^19`, `react-dom`, `lucide-react` (иконки), `motion` |
| Сборка | `vite@^8`, `@vitejs/plugin-react`, `typescript@^5.9.3`, `esbuild` |
| Стили | `tailwindcss@^4` + `@tailwindcss/vite` |
| SQL-редактор | `react-simple-code-editor` + подсветка `prismjs` (прагма `prism-sql`, тема `prism-tomorrow`) |
| Графики | `recharts` |
| Прочее | `dotenv`, `express`, `mysql2`, `pg`, `mongodb` объявлены в `dependencies`, но в коде UI не используются |

**Редактор SQL — не Monaco.** Это `react-simple-code-editor` (обычный `<textarea>` с подсветкой
Prism). Модели Monaco в зависимостях нет, lazy-подгрузки редактора, minimap и «стейтменты-навигатор»
нет. Кнопки: «Выполнить», «Очистить», «Сохранить» (в историю запросов), «Копировать».

### Корень

`npm workspaces`: `backend` + `frontend`. Все e2e-скрипты и команды разработки живут в корневом
`package.json`.

## Быстрый старт (dev)

```bash
# 1. Зависимости (lock фиксирует одну версию TypeScript — 5.9.3)
npm ci

На машине с 16 ГБ виртуальная машина WSL без ограничений разрасталась до 4+ ГБ,
Windows сжимался, и Docker Desktop зависал: порты 3001/3002 переставали отвечать, и
страница показывала `ERR_CONNECTION_REFUSED`, хотя приложение было живо. Что сделано:

- `~/.wslconfig`: `memory=6GB`, `swap=4GB`, `autoMemoryReclaim=gradual`. Лимит нужен
  и для устойчивости, и для совместимости: при `memory=8GB` Windows оставалось 1.2 ГБ.
  Файл можно удалить — вернётся поведение по умолчанию;
- лимиты памяти контейнеров в `docker-compose.yml`: MySQL и MongoDB по 1 ГБ. Первые
  значения (512 МБ) оказались тесными — MySQL сидел на 90% лимита, MongoDB на 86%,
  что грозило замедлением и OOM-смертями СУБД, а через них и ошибками запросов
  `schema`/`rows`. Фактическое потребление: MySQL ~450 МБ, MongoDB ~300 МБ.

Проверить текущее состояние: `docker stats --no-stream`. Если в списке есть посторонние
контейнеры (Grafana, Prometheus), они тоже едят память WSL.

# 2. Конфиг backend
cp backend/.env.example backend/.env      # Windows PowerShell: Copy-Item backend/.env.example backend/.env
#    ОБЯЗАТЕЛЬНО заменить ENCRYPTION_KEY (64 hex), JWT_SECRET, ADMIN_PASSWORD

# 3. Поднять демо-БД (MySQL, MariaDB, PostgreSQL, MongoDB, Redis)
npm run dbs:up                             # docker compose up -d --wait mysql mariadb postgres mongo redis
# Oracle живёт в отдельном compose-профиле: его образ весит ~2 ГБ и сам инстанс
# просит ~2 ГБ RAM, поэтому в базовый набор он не входит и поднимается явно.
docker compose --profile oracle up -d --wait oracle   # набор проверок: npm run e2e:oracle

# 4. Заполнить demo.users (Ann/Bob) на mysql, mariadb, postgres, mongo
npm run seed:dbs

# 5. Запустить два процесса (в двух терминалах)
npm run dev:backend                        # = npm run dev -w backend → tsx watch src/index.ts, :3001
npm run dev:frontend                       # = npm run dev -w frontend → vite --port=3000 --host=0.0.0.0
```

Открыть **http://localhost:3000**. API доступен на **http://localhost:3001**; фронтенд в dev
проксирует `/api` на `http://localhost:3001` (`VITE_API_PROXY` в `frontend/vite.config.ts`).

Вход: логин/пароль администратора из `backend/.env` (`ADMIN_USER` / `ADMIN_PASSWORD`). Пользователь
создаётся автоматически при **первом** старте, когда таблица `users` пуста.

## Порты: 3000 / 3001 / 3002

| Порт | Кто слушает | Когда | Как открыть |
|---|---|---|---|
| **3000** | Vite dev-сервер (frontend) | `npm run dev:frontend` | http://localhost:3000 |
| **3001** | Fastify backend | `npm run dev:backend`, `NODE_ENV` ≠ production | http://localhost:3001 (`/api/health`, `/docs`) |
| **3001** | **nginx** с собранным SPA | `docker compose up` — `frontend`: `127.0.0.1:3001 → 80` | http://localhost:3001 (это UI) |
| **3002** | **backend** в Docker | `docker compose up` — `backend`: `127.0.0.1:3002 → 3001` | http://localhost:3002/api/health, http://localhost:3002/docs |

То есть в Docker порт 3001 занят веб-интерфейсом (nginx), а API живёт на 3002. Все порты в compose
привязаны к `127.0.0.1` — наружу в Интернет не выставляются.

Дополнительно: если в `backend/dist` рядом есть `frontend/dist/index.html`, backend сам отдаёт SPA
на `/` (`@fastify/static` + `setNotFoundHandler`, `backend/src/app.ts:62-72`). Поэтому в локальной
сборке интерфейс доступен и на http://localhost:3001.

### Порты СУБД в compose (все на `127.0.0.1`)

MySQL `3306`, MariaDB `3307` (нестандартный локальный порт, в подключении указывать явно),
PostgreSQL `5432`, MongoDB `27017`, Redis `6379`.

Креды демо-окружения: MySQL/MariaDB — `root/root` и `demo/demo`; PostgreSQL — `root/root`, БД `demo`;
MongoDB и Redis — без авторизации.

## Запуск в Docker

```bash
# Требует backend/.env — compose читает его через env_file
cp backend/.env.example backend/.env   # и заменить секреты (см. ниже)
npm run stack:up                        # docker compose up --build -d
```

Что поднимается:

- **backend** — образ из `backend/Dockerfile` (многостадийный: `tsc` со всеми devDeps → runtime с
  `npm install --omit=dev` и только `dist`). `ENV NODE_ENV=production`, `PORT=3001`,
  `HOST=0.0.0.0`, `META_PATH=/data/meta.db`, состояние в томе `dbpanel-data:/data`.
  Healthcheck: `GET /api/health`. Ждёт `service_healthy` всех пяти СУБД.
- **frontend** — `frontend/Dockerfile`: `vite build` → `nginx:alpine`, `nginx.conf` проксирует
  `/api/` и `/docs` на `backend:3001`, `/assets/*` отдаётся с `immutable` на год. Healthcheck
  отсутствует; ждёт healthy backend.
- **mysql / mariadb / postgres / mongo / redis** — у каждого свой healthcheck и свой именованный том.

Остановить: `npm run stack:down` (= `docker compose down`). Удалить вместе с данными:
`docker compose down -v`.

### nginx (`frontend/nginx.conf`)

- `client_max_body_size 100m` — иначе дефолт nginx в 1 MB отбил бы 413 на загрузке SQLite-файлов
  (лимит бэкенда — 100 MB) раньше, чем запрос дойдёт до `@fastify/multipart`.
- `proxy_read_timeout` / `proxy_send_timeout` = 300 с под `QUERY_TIMEOUT_MS=30000` и стриминг
  экспорта/бэкапов; `proxy_buffering off`, чтобы поток не копился в nginx целиком.
- `location /docs` проксирует Swagger UI на backend (иначе `/docs` отдавал бы SPA-shell).
- gzip для текстовых типов, `Cache-Control: no-cache` для `index.html`.

### `NODE_ENV=production` — fail-fast

Оба образа и compose выставляют `NODE_ENV=production`. В `backend/src/core/config.ts:54-61` при этом
включается проверка:

- `JWT_SECRET` — непустой и не содержит `dev|change|default|secret`;
- `ENCRYPTION_KEY` — ровно 64 hex-символа и не одни нули;
- `ADMIN_PASSWORD` — длиннее 12 символов и не начинается с `admin|password|testpass|change`.

С плейсхолдерами из `.env.example` контейнер **не поднимется** — это намеренно. В CI `NODE_ENV`
намеренно не задан, иначе e2e-пароли были бы отвергнуты.

## Переменные окружения

Файл `backend/.env` (шаблон — `backend/.env.example`). Загрузка: `config.ts` ищет `.env` рядом с
модулем, в корне воркспейса, `backend/.env`, затем `.env` в cwd; **реальные `process.env` имеют
приоритет** над файлом.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3001` | порт Fastify |
| `HOST` | `127.0.0.1` (в Docker `0.0.0.0`) | адрес прослушивания |
| `ENCRYPTION_KEY` | **обязателен** | 64 hex (32 байта) — мастер-ключ AES-256-GCM для паролей подключений. Генерация: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `JWT_SECRET` | **обязателен** | подпись JWT (12 ч) |
| `ADMIN_USER` | **обязателен** | логин первого администратора |
| `ADMIN_PASSWORD` | **обязателен** | пароль первого администратора |
| `REQUIRE_AUTH` | `1` | `0` — отключить требование Bearer-токена (в UI экран входа пропускается) |
| `QUERY_MAX_ROWS` | `1000` | лимит строк в `POST /query`; к `SELECT` без `LIMIT` добавляется `LIMIT 1000` |
| `QUERY_TIMEOUT_MS` | `30000` | таймаут запроса и `statement_timeout` для PG |
| `RATE_LIMIT_MAX` | `200` | запросов в минуту с одного IP (глобально, все маршруты). Для локального `e2e:all` на быстрой машине 200 может не хватать (свиты шлют сотни запросов в минуту и получают 429): поднимите в `backend/.env` до `1000` — это только локальная настройка стенда, в репозитории дефолт не меняется |
| `CORS_ORIGIN` | `http://localhost:3000,http://127.0.0.1:3000` | список origin через запятую |
| `META_PATH` | `./data/meta.db` (в Docker `/data/meta.db`) | файл метаданных; рядом с ним создаются `backups/`, `checkpoints/`, `sqlite/`, `settings.json` |

Файлы, создаваемые рядом с `META_PATH`: `meta.db` + `meta.db-wal`/`-shm`, `settings.json`,
`backups/<scheduleId>_<ISO>.sql|json`, `checkpoints/<connId>_<db>_<table>_<ISO>_<id8>.sql|json`
(точки восстановления), `sqlite/<name>.db|sqlite|sqlite3` (загруженные файлы).

## Auth и RBAC

Модель: пользователи **панели** (логин в веб-интерфейсе) и пользователи **СУБД** (управляются
внутри целевой базы) — это разные сущности.

### Пользователи панели

- Пароли — `bcrypt` (10 раундов). Токен — JWT (`sub`, `username`, `role`), TTL **12 ч**.
- При каждом запросе `/api/*` токен проверяется и **сверяется с таблицей `users`**
  (`isCurrentUser`): удалённый или переименованный пользователь немедленно теряет доступ
  (401 `Bad token`).
- Токен хранится в браузере в `localStorage` (`mydbroot_token`); при `exp` в прошедшем времени
  Frontend вычищает его на старте. Ответ 401 на любом запросе выбрасывает на экран входа.
- Anti-bruteforce: при неверном логине/пароле сервер ждёт 300 мс и отвечает `Bad credentials`.
- Роли создаются только через `POST /api/auth/users` (admin). Имя: `[A-Za-z0-9_.-]{3,64}`,
  пароль 8–128 символов, роль из `admin|editor|readonly` (по умолчанию `editor`).
- `PATCH /api/auth/users/:id` меняет имя/пароль/роль, `DELETE` не даёт удалить себя.

### Матрица прав

| Операция | admin | editor | readonly | без токена (`REQUIRE_AUTH=0`) |
|---|---|---|---|---|
| Просмотр БД/таблиц/строк, схемы, индексы, связей, триггеров | ✅ | ✅ | ✅ | ✅ |
| SQL только на чтение, поиск по БД, статус сервера | ✅ | ✅ | ✅ | ✅ |
| CRUD строк, DDL, импорт, очистка/удаление таблиц | ✅ | ✅ | ❌ 403 | ✅ |
| Создание подключения и БД | ✅ | ✅ | ❌ 403 | ✅ |
| `PATCH /api/connections/:id` (правка подключения) | ✅ | ❌ 403 | ❌ 403 | ✅ |
| Удаление подключения, удаление БД | ✅ | ❌ 403 | ❌ 403 | ✅ |
| Пользователи и права СУБД (`dbusers`, `grant`, `revoke`) | ✅ | ❌ 403 | ❌ 403 | ✅ |
| `KILL` запроса | ✅ | ❌ 403 | ❌ 403 | ✅ |
| Удаление расписания бэкапов, удаление загруженного SQLite-файла | ✅ | ❌ 403 | ❌ 403 | ✅ |
| Управление бэкапами (создать/включить/запустить/восстановить) | ✅ | ✅ | ❌ 403 | ✅ |
| Пользователи панели (`/api/auth/users`), `PUT /api/settings` | ✅ | ❌ 403 | ❌ 403 | ❌ 401 |
| Чтение `/api/audit` | ✅ | ✅ | ❌ 403 | ✅ |
| История запросов (своя) | ✅ | ✅ | ✅ | ❌ 401 |

Роль `readonly` отсекается двумя механизмами: `assertRoleWritable` (по списку мутирующих SQL-токенов
с учётом строковых литералов и комментариев) и скрытием кнопок изменения в UI. Флаг подключения
`readOnly` — независимый второй уровень: его проверяет `assertWritable` внутри каждого драйвера,
поэтому блокируются и SQL-запросы, и `INSERT/UPDATE/DELETE`, и DDL, и импорт, и `restore` бэкапа.

`/api/health`, `/api/drivers`, `/api/auth/login`, `/docs`, `/docs/json`, `/docs/yaml`.

## Что умеет панель

### Подключения

CRUD подключений, тест соединения (`POST /api/connections/:id/test` → `{ok, latencyMs}`), режим
«Только чтение», шифрование пароля (`AES-256-GCM`, формат `salt:iv:tag:cipher`, все значения hex,
ключ расшифровывается через `scrypt`). Поля принимаются в двух наборах имён: `kind`/`type`,
`user`/`username`, `database`/`databaseName`, `filePath`/`file`. Создание подключения к SQLite
создаёт пустой файл, а с флагом `createDatabase` может заодно создать БД на сервере
(mysql/pg/mongo) — для sqlite это единственный путь.

Путь SQLite валидируется при записи (`normalizeSqlitePath` в `core/context.ts`, вызывается и в
маршрутах, и в `createConnection`):

| Вход | POSIX-бэкенд (Docker/Linux) | Windows-бэкенд |
| --- | --- | --- |
| `data/app.db` | `resolve(dirname(META_PATH), …)` | так же |
| `C:\data\app.db` | **400** `filePath must use forward slashes on this platform` | нормализуется в `C:/data/app.db` |
| пустая строка / `\0` в пути | 400 | 400 |

Причина запрета: на POSIX обратный слэш — часть имени файла, поэтому `C:\data\app.db` раньше
превращался в файл-мусор `/data/C:\data\app.db`, а запросы к нему падали с «no such table».
Проверяется сюитом `e2e-sqlitefiles` (`backslash filePath rejected or normalized`).

### Обзор данных

- Навигация: категория СУБД → список БД → список таблиц (постранично на клиенте, 25/50/100) →
  таблица.
- Схема: **нормализованный контракт `TableSchema`** (`backend/src/core/types.ts`) одинаков для всех
  семи драйверов — `{table, kind: 'table'|'view', comment, extra, columns[], indexes[],
  foreignKeys[], triggers[]}`. Источники: `SHOW COLUMNS`+`SHOW INDEX`+`information_schema`
  (MySQL/MariaDB), `pg_class`/`pg_attribute`/`pg_index`/`pg_constraint`/`pg_trigger` с четырьмя
  параллельными срезами (PostgreSQL), `PRAGMA` + `sqlite_master` (SQLite), первый документ
  (MongoDB), псевдо-таблица `key/type/ttl/len` (Redis), `user_tab_columns`/`user_indexes`/
  `user_constraints`/`user_triggers` (Oracle). Интерфейсы `SchemaColumn`, `SchemaIndex`,
  `SchemaForeignKey`, `SchemaTrigger`; `getSchema` у всех семи возвращает `Promise<TableSchema>`.
  Комментарий таблицы есть у MySQL/MariaDB, PostgreSQL и Oracle, у SQLite он всегда `null`
  (в СУБД нет такой сущности).
- Данные: `GET /rows` с `page`, `pageSize` (драйверы режут до 500, в UI — 25/50/100/200),
  `sort=col:desc` и `filter`. Фильтр и сортировка строк — возможности API; в интерфейсе таблицы
  есть только «Фильтр колонок» на вкладке «Структура» (скрывает колонки, не строки).
  Язык фильтра: `col=value`, `!=`, `<`, `<=`, `>`, `>=`, `~` (LIKE/Regex «содержит»),
  `^` (начало), `$` (конец), несколько условий через `AND`; значения идут bind-параметрами,
  SQL-мусор в значении отбрасывается.
- «Связи» — реальные внешние ключи (`information_schema.REFERENTIAL_CONSTRAINTS`,
  `pg_constraint`, `PRAGMA foreign_key_list`); ER-эндпоинт отдаёт схемы первых **100** таблиц и
  полный список relations с именем констрейнта и правилами `ON DELETE`/`ON UPDATE` (в `Relation`
  для этого добавлены поля `constraint`, `onDelete`, `onUpdate`). У SQLite имён у FK нет — там
  имя синтезируется как `fk_<таблица>_<id>`. У MongoDB и Redis `getRelations` нет, `relations`
  приходит пустым.
- «Триггеры» — просмотр и редактирование: полный CRUD (`POST`/`DELETE .../triggers`), см.
  [Конструктор таблиц](#конструктор-таблиц).
- Глобальный поиск по всем таблицам БД (`GET .../:db/search`), постранично, с лимитом совпадений
  и списком таблиц, где поиск упал.

### Oracle: почему «база» — это схема

Oracle устроен иначе, чем остальные шесть СУБД, и это видно во всём маршруте
`backend/src/drivers/oracle.ts`:

- **`CREATE DATABASE` не существует.** «База» панели здесь — **схема**, а схема Oracle =
  пользователь подключения. Поэтому `listDatabases` возвращает ровно одну запись
  (`SELECT USER FROM dual`), а создание и удаление «базы» — это `CREATE USER` и
  `DROP USER CASCADE` (`routes/connections.ts`). Просмотреть созданную схему можно
  только отдельным подключением под этим пользователем.
- **Подключение — EZ-connect** `host:port[/service]`. Если поле «База данных» пустое,
  идёт подключение к инстансу; если заполнено — как `SERVICE_NAME`. Доменное имя из
  `tnsnames.ora` в панели не поддерживается: драйвер хранит только хост, порт и имя.
- **Сервис и схема — разные вещи, и это видно в маршрутах.** Интерфейс подставляет выбранную
  «базу» в конфиг запроса (`{ ...cc, database: db }`), а для Oracle это схема пользователя, а
  не сервис: connect string строился бы как `oracle:1521/DEMO` и каждый запрос падал бы с
  `NJS-518: Service "DEMO" is not registered`. Поэтому при загрузке подключения
  (`loadDecrypted`) поле `database` один раз запоминается в `serviceName`
  (`ConnectionConfig.serviceName`), и `oracleConnectString` использует именно его
  (`backend/src/core/pool.ts`). Старые подключения работают как раньше: при пустом
  `serviceName` берётся `database`.
- **thin-режим `oracledb`**: Instant Client не нужен, но родной аддон
  `oracledb` требует разрешения на install-скрипт (`allowScripts` в `package.json`).
- **`createPool` асинхронный** (oracledb 6+), поэтому `getOraclePool` кэширует промис,
  а не сам пул, и удаляет его из кэша при неудаче — иначе два параллельных запроса
  создали бы два пула на одно подключение.
- **Лимиты выдачи — `FETCH NEXT n ROWS ONLY`**, а не `LIMIT`: общий `capSelect()`
  для Oracle не годится, поэтому добавлен `capSelectOracle`, который также уважает
  `ROWNUM` в пользовательском запросе.
- **DDL не транзакционный.** Пакет `alterTable` применяется по одному стейтменту и
  останавливается на первой ошибке (`transactional: false`), как в MySQL. Имя
  первичного ключа системное (`SYS_C…`), поэтому оно читается из `user_constraints`.
- **Идентификаторы всегда в двойных кавычках**, поэтому созданные панелью имена
  сохраняют регистр, а не складываются сервером в верхний. Из-за этого свободный SQL
  пользователя тоже требует кавычек: `SELECT * FROM "users"`, иначе ORA-00942.
- **Системные представления `user_*`** вместо `information_schema`: у Oracle его нет.
  Имена служебных выборок приходят в верхнем регистре, поэтому `rows()` приводит
  ключи к нижнему — как в `postgres.ts`, только наоборот.
- **Алиас `COMMENT` нельзя использовать без кавычек**: `COMMENT` — зарезервированное
  слово Oracle, `AS comment` даёт ORA-00923. В драйвере алиасы названы `cmt`/`tcmt`.
- **`EXPLAIN PLAN` требует `PLAN_TABLE` официальной структуры** из
  `$ORACLE_HOME/rdbms/admin/utlxplan.sql`; усечённая таблица даёт ORA-02403.
  Драйвер создаёт её лениво и прячет из списка таблиц.
- **Триггеры — блок PL/SQL**: несколько стейтментов разрешены, `BEGIN … END`
  добавляет сам драйвер, ссылки на записи — `:OLD` / `:NEW`.
- **Нет `ON UPDATE`** для внешних ключей (только `delete_rule`) и **нет
  объекто��ых** прав `CREATE`/`DROP`/`ALTER`/`INDEX` на таблице — это права схемы,
  поэтому в списке привилегий Oracle оставлены `SELECT`, `INSERT`, `UPDATE`, `DELETE`.
- **`getStatus` читает `product_component_version`**, а не `V$VERSION`: последний
  требует прав `SELECT_CATALOG_ROLE`. Текст запроса в списке процессов остаётся пустым
  (`V$SQL` рядовому пользователю недоступен), а `killQuery` адресует сессию по
  `SID` + `serial#` и выдаёт 403 с пояснением, если прав не хватает.
- **Параллелизм отключён**, как и у SQLite: `poolMax: 10`, постраничное чтение и
  стриминг сделаны через `OFFSET`/`FETCH` вместо курсора, поэтому на огромных
  таблицах стриминг медленнее, чем у PostgreSQL.
- **стенд не мешает браузерным наборам**: у Oracle одна «база» — схема подключения,
  и после `e2e-oracle` она пустая. Наборы `e2e-browser`, `e2e-table-tabs` и
  `e2e-monitoring` выбирают первое подключение, чьё имя начинается с `e2e-`, и
  потому исключают `redis` и `oracle` — иначе они открыли бы подключение без
  таблиц и падали бы на пяти шагах, не связанных с их собственными проверками.

### ER-эндпоинт: параллельные схемы и частичные ошибки

`GET /api/connections/:id/:db/er` (`routes/browse.ts`) отвечает
`{tables, schemas, relations, truncated, totalTables, errors}`:

- схемы грузятся **параллельно** через `Promise.allSettled` (лимит `ER_TABLE_LIMIT = 100`) — сто
  последовательных `getSchema` на большой базе занимали десятки секунд;
- одна упавшая таблица (нет прав, битая) **не роняет ответ**: её схема выпадает из графа, а сама
  ошибка попадает в `errors` (и туда же — ошибка `getRelations` с `table: '*'`);
- `truncated` означает, что таблиц в базе больше ста, `totalTables` содержит их реальное число.

### CRUD строк

Инлайн через модалки «Добавить запись» / редактирование / удаление. `UPDATE` и `DELETE` строят
`WHERE` по первичному ключу (или по всем простым значениям строки, если PK не найден). Пустые
значения при редактировании превращаются в `NULL`.

### Порядок категорий и баз в боковой панели

Переставлять можно **и категории СУБД** (MySQL, MariaDB, PostgreSQL, SQLite,
MongoDB, Redis, Oracle — целиком, за шапку), **и базы внутри категории**
(отдельно, за строку). Способ тот же в обоих случаях: **мышью за элемент** и
**стрелками `↑` `↓` с клавиатуры**. При перетаскивании элемент становится
полупрозрачным, а полоска над или под тем, над которым стоит курсор, показывает
место вставки. Сторона выбирается половиной элемента — верхняя даёт «перед»,
нижняя «после»; режим только «перед» в списке высотой 28 пикселей делал бы
перенос на соседнюю строку пустым действием. Одна кнопка **«Сбросить порядок»**
возвращает к порядку по умолчанию сразу оба списка и появляется только когда
есть что сбрасывать.

Клавиатурный путь не запасной, а равноправный: в списке из двух десятков строк
стрелки дают ровный шаг, а перетаскивание по 20-пиксельным строкам легко
промахнуться. Как и у панелей (`PanelGrid.onPanelKey`), перестановка мышью с
клавиатуры недоступна и наоборот.

- **порядок категорий накладывается поверх `SUPPORTED_KINDS`**: тип, добавленный
  позже (Oracle) и ещё не перемещённый, оказывается в конце — как и должен,
  пользователь его не двигал. Тип, выключенный в настройках, в список не
  возвращается: фильтр применяется до сортировки;
- **домена два** (`kindorder:v1:<пользователь>` для категорий и
  `dborder:v1:<пользователь>` для баз), а не один: общий версионированный ключ
  означал бы, что смена формата одного списка ломает чтение другого;
- **механика одна** для обоих списков (`frontend/src/core/orderStore.ts`),
  а `dbOrder.ts` и `kindOrder.ts` — только ключ строки и домен;
- **фокус следует за элементом**: после сдвига он возвращается на переехавший,
  иначе перерисовка роняла бы его на `body` и обход начинался бы заново;
- **на краю списка стрелка не гасится**: если сдвинуть некуда, событие не
  помечается обработанным и панель прокручивается как обычно;
- **вниз — стать после соседа, вверх — перед ним**: вставка «перед» при сдвиге
  вниз оставила бы элемент на месте, потому что он и так перед соседом;
- **база не переезжает между категориями**: бросок в группу другого типа
  игнорируется, у категорий — свой независимый набор состояний перетаскивания;
- **порядок хранится на клиенте** — это вкусовое предпочтение конкретного
  человека, а не свойство панели: настройки `settings.json` общие для всех и меняет
  их только админ, а `PUT /api/settings` перезаписывает объект целиком и чужая
  правка затёрла бы не то поле;
- **сортировки на сервере нет и не сделано**: `SHOW DATABASES` и `listDatabases()`
  у MongoDB отдают базы в произвольном порядке (алфавитный гарантирован только
  у PostgreSQL), поэтому опираться на порядок ответа нельзя — перестановка
  применяется поверх ответа в интерфейсе;
- **неизвестные ключи уходят в конец и не вытесняют выбранное**: база, созданная
  после того, как пользователь всё расставил, не прыгает наверх при каждом
  обновлении списка, а сохраняет порядок сервера;
- **первое перетаскивание работает при пустом хранилище**: базой для перестановки
  служит сохранённый порядок, а если его нет — текущий видимый список, иначе оба
  ключа искались бы в пустом массиве и ничего бы не сдвинулось;
- **свечение**: повреждённое значение в хранилище не замалчивается — панель
  показывает тост и возвращает порядок сервера, потому что молчаливый откат
  выглядел бы как «ничего не сохранилось»;
- **логика без React** (`frontend/src/core/orderStore.ts` + домены `dbOrder.ts` и
  `kindOrder.ts`) проверяется скриптом `npm run check:order-store` (входит в
  `verify`), а обработчики перетаскивания и клавиш — браузерным набором
  `npm run e2e:sidebar-order` (входит в `e2e:full`).

### Панели: сетка как в Grafana

Рабочая область и мониторинг собраны из панелей на сетке: 24 колонки, панель
занимает `{x, y, w, h}` в единицах сетки, а не пиксели, поэтому при изменении ширины
окна панели перестраиваются, а компоновка переживает другой монитор.

- **вкладка «Панели» — основной вид рабочей области**: таблицы, журнал, SQL-редактор,
  поиск и конструктор;
- экран **«Мониторинг»** — те же панели: метрики, нагрузка, запросы, процессы, размеры БД;
- панель перетаскивается за шапку, размер меняется за восемь краёв, шевронка сворачивает;
- кнопка с «ёлочкой» открепляет панель в отдельное окно, окно таскается, растягивается,
  разворачивается и возвращается в сетку;
- компоновка хранится в `localStorage` по имени пользователя и рабочей области
  (`panels:v1:<пользователь>:db` и `panels:v1:<пользователь>:monitoring`), с версией схемы.

Панели следуют за шириной рабочей области: сворачивание левого или правого сайдбара
измеряется `ResizeObserver` и пересчитывает все прямоугольники, поэтому панели
растягиваются на освободившееся место и сжимаются обратно. Узел измерения — тот же слой
сетки, который рисует панели (`PanelGrid.tsx`, `bindGridSurface`): если измерять
другой элемент, ширина слоя и ширина раскладки разойдутся. Проверка:
`npm run check:panel-layout` (геометрия) и `npm run e2e:panels-reflow` (реальный браузер).
  Ключ по имени, а не по роли: два администратора в одном браузере не должны затирать
  компоновку друг друга;
- панель открывается на всю рабочую область двойным кликом по шапке, закрывается повторным
  кликом, клавишей Escape или кнопкой в её шапке. В режиме фокуса остальные панели
  превращаются в полосу вкладок над ней, а фокусная занимает всё поле под полоской.
  Она рисуется **отдельным слоем** последним потомком, с z-index числом выше
  откреплённых окон (`zTop + 1000`). Пока это был обычный элемент списка панелей,
  её положение зависело от порядка и перекрытия координатами, и она оказывалась на
  втором плане; слой не перехватывает клики (иначе полоса вкладок под ним стала бы
  недоступна), а сама панель начинается ниже полосы вкладок, а не поверх неё;
- панель, получившая фокус, управляется с клавиатуры: стрелки двигают её, Shift со стрелками
  меняет размер — мышью трудно попасть ровно в две колонки;
- «Сбросить компоновку» возвращает значения по умолчанию;
- **высота сетки измеряется, а не вычисляется вслепую**: вся цепочка контейнеров панели имеет
  `overflow-hidden`, поэтому сетка выше экрана обрезалась бы и панели выглядели бы
  спрятанными под соседями. Видимые строки считаются от реальной высоты области
  (`visibleRows`), а область панели прокручивается;
- **у каждого откреплённого окна свой z-index, и активация поднимает ровно одно окно**:
  общий счётчик обновлял бы слой у всех окон разом, порядок не менялся бы вовсе, и
  активное окно оставалось бы под остальными (в DOM верхним рисуется последнее, а не
  активное). Логика в `panelLayout.ts` (`raiseWindow`, `windowZOf`, `focusLayerZ`),
  проверена в `check-panel-layout.mts`;
- **слой окон и фокусной панели позиционируется как `fixed` внутри дерева компонентов.**
  Все контейнеры вокруг сетки имеют `overflow: hidden`, поэтому внутри них окно обрезалось
  ровно по краям рабочей области: панель физически не могла выйти поверх боковых панелей и
  выглядела спрятанной под ними. Мешала не глубина, а обрезка, и увеличение z-index не
  помогало. `position: fixed` у потомков `overflow: hidden` НЕ обрезается — он
  позиционируется относительно экрана, поэтому портал не требуется. Слой имеет
  `z-index: 45` (`PANEL_OVERLAY_Z`): выше сайдбаров (30) и шапки (40), но под модальными
  окнами (50) и уведомлениями (100). Координаты окон пересчитываются между рабочей
  областью и экраном, иначе окно съезжало бы на ширину сайдбаров.

#### Модальные окна: ширина и прокрутка

Общего компонента окна в проекте нет — каждое собрано из двух `div`, поэтому правила
держатся в трёх местах и проверяются скриптом:

- подложка `fixed inset-0` имеет `overflow-y-auto`: окно выше экрана (маленькая
  высота, длинная форма) прокручивается, а не обрезается по краям;
- панель имеет `max-w-full` и `my-auto`: она не выходит за правую границу окна
  браузера, а при вертикальной прокрутке прижимается к верху;
- прокручиваемое тело внутри flex-контейнера получает `min-w-0`. Без этого
  flex-элемент не сжимается меньше своего содержимого (`min-width: auto`), и
  содержимое распирает окно вбок.

Ширина окон: конструктор таблицы, «Модели», «Настройки» и «Справка» — `max-w-6xl`,
«Изменение колонки» и «Создание подключения» — `max-w-3xl`.

В конструкторе таблица полей раньше имела `whitespace-nowrap` при восьми колонках,
и её минимальная ширина превышала окно — появлялась горизонтальная прокрутка.
Теперь `table-fixed` с долями колонок, заголовки переносятся, а поля ввода
`w-full min-w-0` вместо фиксированных `w-20`/`w-28`. Прокрутка под таблицей
осталась запасным вариантом для совсем узкого экрана.

#### Тёмная тема и читаемость

В `index.css` объявлено `.dark { color-scheme: dark }`. Без этого нативный `<select>` в тёмной
теме сохранял светлый фон всплывающего списка, а его пункты — тёмный текст: подпись в списке
становилась нечитаемой. Правило живёт внутри `.dark`, который ставит `App.tsx` на `<html>`,
поэтому светлая тема не затрагивается.

Два правила, которых в проекте не хватало и которые ломали читаемость:

- **поля и списки без собственного цвета текста.** Элемент с тёмным фоном и без `text-*`
  берёт цвет от предка; внутри оболочки это светлый `gray-100` и всё выглядит нормально, но
  вне её (всплывающие окна `QuickEdit`, вынесенные порталом в `document.body`) — чёрный от
  `<body>`, то есть нечитаемый на тёмном фоне. Поэтому у всех полей задан явный цвет, а у
  поповеров `QuickEdit` — свой;
- **подписи `gray-500`/`gray-600`.** На тёмном фоне они дают контраст около 3.2:1 при
  пороге WCAG 4.5:1, то есть видны, но читаются плохо. Каждому такому классу добавлен
  вариант для тёмной темы. Глобальное правило `.dark .text-gray-500` пробовалось и удалено:
  находясь вне `@layer`, оно перебивало любые utility-классы Tailwind, включая осмысленные
  `dark:text-*`, и местами ухудшало контраст вместо улучшения.

Проверка `npm run e2e:contrast` считает контраст по формуле WCAG для каждого текста
на рабочей области, вкладке «Панели», в конструкторе, в справке и в настройках, отдельно
проверяет `color-scheme` в обеих темах и то, что во всплывающих окнах вне оболочки нет
чёрного текста. Цвета переводятся в sRGB через canvas: `getComputedStyle` в Chrome
возвращает `oklch(...)`, и разбор такой строки регуляркой давал бы мусор вместо каналов.

Класс `.no-scrollbar` использовался в коде, но не был определён в `index.css`, из-за
чего полоса всё равно появлялась; теперь он есть.

Проверка: `npm run e2e:modal-width`. Статическая часть проверяет правила в исходниках,
браузерная открывает каждое окно и сравнивает ширину панели с окном браузера, ищет
элементы, вылезающие за правый край, и проверяет, что ни в панели, ни в её потомках
нет горизонтальной прокрутки — в том числе при ширине окна 820px. Браузерная часть
пропускается с пометкой SKIP, если стенд не отвечает.
  Портал в `document.body` пробовался и был убран: `StrictMode` вызывает эффекты дважды,
  контейнер портала пересоздавался, и React пытался удалить узел из уже отсоединённого
  контейнера — `NotFoundError` (`the node to be removed is not a child of this node`),
  приложение падало;
- **старая оконная система удалена целиком**: из `MainContent` убраны состояние
  `windows`, обработчики (`handleDetachWindow`, `handleDockWindow`, `bringWindowToFront`,
  `handleCascade`, `handleTile` и прочие), оверлей окон в слое `z=50`, панель задач и файлы
  `WindowsTaskbar.tsx` / тип `WindowId`. Она работала одновременно с `PanelGrid`, и её кнопки
  открепления открывали окна мимо раскладки панелей — из-за этого окна оказывались не на своём
  слое, а пользователь видел в интерфейсе вдвое больше кнопок, чем нужно. Теперь система окон
  одна, и живёт она в `PanelGrid` (`WindowFrame` остаётся — его использует сетка);
- **у каждого окна свой z-index, и активация поднимает ровно одно окно**: общий счётчик
  обновлял бы слой у всех окон разом, и активное окно оставалось бы под остальными
  (в DOM верхним рисуется последнее, а не активное);
- **ключи панелей лежат по пути `main.panels.*`**, потому что блок `panels` вложен в раздел
  `main`. Код вызывал `t('panels.tables')`, `t()` возвращал сам ключ, и в панелях виднелось
  «panels.tables» вместо «Таблицы». Проверяется в `check-locales.mts`;
- **«сумки языков» разворачиваются при слиянии локализаций**: в `locales/index.ts` ключи
  записаны как `{ ru: '…', en: '…', … }`, и обычное глубокое слияние клало объект вместо
  строки — `t()` такой лист не показывает. `deepMerge` разворачивает сумку в текущий язык
  и заходит в объекты всегда, даже если раздела ещё нет в цели;
- **общие надписи вынесены в раздел `ui.*`**: «Отмена», «Сохранить», «Обновить»,
  «Подключения», «Пользователь», «Пароль» и подобные были зашиты прямо в JSX, поэтому
  при выборе английского или любого другого языка они оставались русскими — язык
  переключался, а подписи нет. Теперь это `t('ui.…')` для всех шести языков;
- **английский язык по умолчанию, выбор запоминается**: `LanguageContext` стартует с
  `en`, а выбранный язык пишется в `localStorage` (`mydbroot_lang`) — иначе он слетал
  при каждой перезагрузке и пользователю приходилось бы выбирать его заново. Если
  `localStorage` недоступен, остаётся язык по умолчанию;
- **подписи адресуются полным путём от корня языка**: `t('table.name')`, а не
  `t('ui.table.name')`. Ключ, спрятанный в лишний раздел, не находится — `t()`
  возвращает сам ключ, и пользователь видит «table.name» вместо «Имя». Проверяется в
  `check-locale-keys.mts`, который ищет все литеральные вызовы `t('…')`;
- **зашитый текст не может вернуться незаметно**: `check-hardcoded-text.mts` перечисляет
  пользовательские строки в JSX, которые не проходят через `t()`, и падает, если их стало
  больше лимита (`HARDCODED_BUDGET`, сейчас 0). Путь сюда был в два шага: сначала
  проверке добавили разбор строк в кавычках (было 188 — подписи в массивах,
  объектах и тернарниках оставались невидимыми), после перевода интерфейса осталось
  472, из которых 326 были ложными срабатываниями: служебные значения вроде
  `Europe/Moscow`, `BTREE`, `idx_table_col` и мусор склейки JSX между тегами.
После фильтрации осталось **146 — вся строка была в справочной документации
   `DocsModal`**; интерфейс переведён полностью, и последняя пачка переводов
   (`docs-b`…`docs-k`) обнулила счётчик, так что лимит теперь **0**. Лимит должен
   только снижаться: новая строка без `t()` ломает `npm run verify`;
- **переключение языка проверяется в браузере** (`e2e-lang.mjs`, `npm run e2e:lang`):
  набор убеждается, что по умолчанию английский, после выбора русского подписи стали
  русскими, английских не осталось, а после перезагрузки язык прежний. Ловит и
  забытый `t()`, и поломку самого переключателя.
- **`e2e-browser.mjs` переключает язык на русский в начале**: проверки набора ищут
  русские надписи, а по умолчанию интерфейс английский. Переключение заодно проверяет
  сам переключатель, а `e2e-lang` — что выбор языка переживает перезагрузку;
- **числа и даты форматируются по языку интерфейса** (`frontend/src/intl.ts`): раньше вызовы
  шли с фиксированной локалью `toLocaleString('ru-RU')`, и в английском интерфейсе счётчики и время
  выглядели по-русски — это и давало «пересечение языков». Проверяет `e2e:monitoring`;
- **подписи в настройках, моделях, сайдбарах, шапке и окнах создания переведены
  полностью**: там же остались `SettingsModal`, `ModelsModal`, `TableDesigner`,
  `Sidebar`, `Header`, `WindowFrame`, `EditRowModal` и окна создания;
- **константы уровня модуля хранят ключ перевода, а не текст**: `NAME_RULES` в
  `CreateDatabaseModal` и `AUDIT_TITLES` в `Header` объявлены вне компонента,
  и `t()` там недоступен — раньше такие подписи оставались русскими при любом
  языке. Теперь в константе лежит ключ, а перевод происходит при отрисовке;
- **переводчик доступен вне компонента** (`translate(lang, key)` в `LanguageContext`): функции вроде
  `timeAgo()` объявлены на уровне модуля и хука не видят, поэтому раньше они оставались русскими;
- **русские значения внутри других языков запрещены**: в переводах нет русского текста ни в `en`, ни в
  `de`/`fr`/`es`/`zh` — иначе `t()` показал бы русский посреди английского интерфейса;
- **типы СУБД выключаются тумблерами в настройках** («Общие» → «Типы баз данных»),
  а боковые панели показывают только включённые: группа выключенного типа исчезает
  совсем, вместе с плоским списком подключений и счётчиком. Выключенный тип убирается
  и из окон создания базы и подключения, а активное подключение выключенного типа
  перестаёт быть активным — правой панели нечего показывать;
- **настройка `enabledKinds` трактуется как «все типы», если её нет**: поле появилось
  позже существующих `settings.json`, и пустой список в трактовке «пусто = ничего не
  показывать» молча спрятал бы все подключения у всех, кто обновился. Пустой массив,
  пришедший от интерфейса, означает «выключены все» и сохраняется как есть;
- **список типов живёт в одном месте** (`frontend/src/engineKinds.ts`): боковые панели
  группируют по `postgresql`, а API отдаёт `postgres`. Раньше каждый файл держал свою
  копию списка, и эти два имени расходились — фильтр по настройке молча ничего не
  спрятал бы. Тот же принцип теперь работает и для названий типов: `Sidebar.tsx` берёт их
  из `KIND_LABELS`, потому что своя копия на седьмом типе отдала панели «oracle»
  вместо «Oracle». Правку проверяют `e2e-kinds` (API, включая права: переключать может
  только админ) и `e2e-kinds-browser` (щёлкает тумблер и смотрит группы панели);
- **Oracle в существующих `settings.json` выключен по умолчанию.** Поле `enabledKinds`
  хранит осознанный выбор пользователя, поэтому тип, добавленный позже, автоматически
  не включается: в списке из шести типов Oracle просто отсутствует, и его надо включить
  тумблером в настройках. Это осознанный выбор — молча включать новый движок у всех
  было бы тем же, что и трактовка «пусто = ничего не показывать», только наоборот;
- **оба набора приводят стенд в исходное состояние сами**: `e2e-kinds` возвращает
  `enabledKinds` через API, `e2e-kinds-browser` — тоже через API в `finally`, потому
  что прогон, оборванный на середине, иначе оставил бы панель без типа и следующий
  набор падал бы из-за чужой ошибки.
- **в сетке нет кнопок старой оконной системы**: панели отдают содержимое через
  `renderTableList/renderLogs/renderSqlEditor(..., showWindowControls)`, и при отрисовке внутри
  `PanelGrid` флаг выключен. Раньше в каждой панели висела лишняя оранжевая кнопка, которая
  открывала окно в другом слое (`z=50`, минуя раскладку панелей), то есть работала вторая
  система окон поверх основной — отсюда окна не на своём слое и путаница. Открепить и вернуть
  панель можно из шапки панели. Старая система сохранена для вкладки «Структура»;
- **есть набор проверок в настоящем браузере** (`e2e-browser.mjs`, `npm run
  e2e:browser`, либо всё сразу через `npm run e2e:full`): он ловит то, чего не видит
  проверка через API, — ошибки при
  размонтировании компонентов, необработанные исключения и необработанные ключи
  локализации. Управляет Chrome через DevTools Protocol, без puppeteer и playwright
  (в Node есть встроенный WebSocket), и сам пропускает себя, если Chrome не найден или
  не задан `ADMIN_PASSWORD`.
  Набор проверяет вкладку по умолчанию, быстрое редактирование полей, поднятие
  откреплённого окна над остальными и чистоту размонтирования панелей. ВАЖНО: разбор
  подключения в нём исключает Redis — у него нет прав на изменение схемы, поэтому
  кнопки создания таблицы в интерфейсе не существует;
- **по умолчанию открывается вкладка «Структура»** (список таблиц, журнал,
  SQL-редактор), сетка панелей остаётся отдельной вкладкой;
- **быстрое редактирование полей** (`QuickEdit`): у каждого значения поля рядом стоит
  карандаш, по клику значение правится во всплыващем окне — Enter применяет, Escape
  отменяет, клик снаружи закрывает без изменений. Окно выносится в `document.body`
  (внутри таблиц его обрезали бы прокручиваемые контейнеры), переворачивается вверх при
  нехватке места и прижимается к краю экрана. Подключено в трёх местах: окно создания
  таблицы, визуальный конструктор и таблица структуры. Для уже существующих колонок
  (`QuickOpen`) значение вызывает уже существующий модальный редактор: правка схемы
  требует предпросмотра SQL, выбора диалекта и подтверждения, мини-поле их не заменяет;
- **проверяется, что каждый ключ, который зовёт код, существует в переводах**
  (`check-locale-keys.mts`, входит в `verify`): `t()` при неудаче возвращает сам ключ, и
  пользователь видит «main.tableFields.name» вместо «Имя» — для типов и остальных наборов
  это невидимо. Проверка нашла два настоящих дефекта: ключи `tableFields` лежали по пути
  `tableFields.*`, а код звал `main.tableFields.*`; у `main.designer` не было `title`.
  Неиспользуемые ключи (44) выводятся справочно, без падения;
- **применяется сначала переименование, а alteration — уже по новому имени**: операции
  уходят одной пачкой, и `alterColumn` с правильным именем. Со старым именем он падал бы
  с «колонки нет» — переименование проходило, а изменение типа и значения по умолчанию
  терялось; окно при этом оставалось открытым, а уведомление об ошибке исчезало раньше,
  чем его успевали увидеть. Регресс закрыт в `e2e-browser.mjs`;
- **предпросмотр определения колонки считается так же, как сам запрос**: заглушка `-`
  («длины нет», `TableView.tsx:61`) отбрасывается, иначе предпросмотр показывал
  невалидное `timestamp(-)`, хотя запрос уходил корректный. Слово `NULL` при этом не
  отбрасывается: его вводят осознанно, и запрос уходит с `DEFAULT NULL`;
- сетка рисует только те панели, для которых экран дал содержимое: пустой рамки без
  содержимого пользователь принял бы за поломку. Поэтому в рабочей области это таблицы,
  журнал, SQL-редактор, поиск и конструктор, а в мониторинге — свои панели.

Три свойства, на которых держится надёжность:

- **у панели ровно одно место**: `grid` или `window`, это размеченное объединение типов,
  поэтому «потеряться» панель не может by construction;
- **условия и раскладка считаются одним кодом**: то, что показывает предпросмотр, и то,
  что применяется, не может разойтись;
- **вся математика проверяется без браузера** (`npm run check:panel-layout` в составе
  `verify`), потому что наложение панелей или потеря размера при сворачивании глазами
  не замечаются;
- **раскладка ведёт себя как данные**: версионированная, нормализуется при чтении,
  битое значение не остаётся молча, а сообщает о себе.

Тот же приём у порядка баз: `frontend/src/core/dbOrder.ts` (перестановка мышью и
стрелками плюс хранилище, версия схемы в ключе) +
`frontend/scripts/check-order-store.mts` (70 проверок, входит в `verify`) +
`frontend/src/components/Sidebar.tsx` (разметка строки, обработчики перетаскивания
и клавиш) + `e2e-sidebar-order.mjs` (31 браузерная проверка, входит в `e2e:full`).

Вкладка «Структура» с её собственным журналом окон пока осталась рядом с сеткой: это
единственное дублирование, которое пережило переход. Сетка стала основным видом, но старый
код не удалён — пока сетку не посмотрели вживую, ломать главный экран вслепую смысла нет,
а вкладка стоит одного клика.

### Конструктор таблиц

Создание таблицы (1–200 колонок, allowlist типов по диалекту, `PRIMARY KEY`, `AUTO_INCREMENT`/
`SERIAL`/`AUTOINCREMENT`, `DEFAULT`), удаление таблицы, клонирование `CREATE TABLE ... LIKE ...`
(только MySQL/MariaDB). Тело `CreateTableDef` принимает и `foreignKeys[]`, и `indexes[]`, и
`comment`, а для MySQL/MariaDB — `engine`/`charset`/`collate`: MySQL, PostgreSQL и Oracle создают
индексы отдельными `CREATE INDEX` и вешают комментарии (`COMMENT`/`COMMENT ON`) в той же
транзакции (PG) или пакетом (MySQL/Oracle); SQLite объявляет FK прямо в `CREATE TABLE`.
MongoDB создаёт коллекцию (`createCollection`), Redis таблиц не имеет (400 с объяснением).
Типы проверяются по allowlist в `backend/src/drivers/helpers.ts`
(`TYPE_PATTERNS` + `ENUM(...)`/`SET(...)` для MySQL и `CITEXT` для PG); `DEFAULT` допускает литералы,
`CURRENT_*`, числа, `TRUE/FALSE/NULL`, а также белые списки функций движков (`NOW()`,
`GEN_RANDOM_UUID()`, `SYSDATE`/`SYSTIMESTAMP`, `nextval(...)`). Диалект берётся **из типа
подключения**: отдельного поля `dialect` в теле запроса нет (раньше бэкенд его всё равно игнорировал).

Клонирование выполняется прямым `POST /query`, а список таблиц живёт в `MainContent` и знает
только о том, что перечитывал. Поэтому карточка таблицы после клона (и после DDL в SQL-вкладке)
отправляет `notifyTablesChanged()` — событие `mydbroot:tables-changed`, которое слушает `App` и
превращает в `externalTablesVersion` для `MainContent`. Без этого клон и новая таблица из SQL
появлялись только после перезагрузки страницы. Проверка: `npm run e2e:clone` (входит в
`e2e:full`) — она убеждается, что страница не перезагружалась, список был перечитан и клон
виден на экране.

#### Изменение структуры: один пакет DDL-операций

`PATCH /api/connections/:id/:db/:table` принимает `{ops[]}` (1–50 операций) и применяет их
**пакетом**, а не по одной. Состав `ops` (`AlterOp` в `core/types.ts`):

| Операция | Поля | Диалекты |
|---|---|---|
| `addColumn` / `dropColumn` | `column` / `name` | MySQL/MariaDB, PostgreSQL, SQLite |
| `renameColumn` | `from`, `to` | MySQL/MariaDB, PostgreSQL, SQLite |
| `alterColumn` (тип, `NULL`, `DEFAULT`, `AUTO_INCREMENT`) | `name`, `column` | MySQL/MariaDB, PostgreSQL, SQLite (пересборкой, см. ниже) |
| `renameTable` | `to` | MySQL/MariaDB, PostgreSQL, SQLite (3.25+) |
| `addIndex` / `dropIndex` | `index` (`IndexDef`) / `name` | MySQL/MariaDB, PostgreSQL, SQLite |
| `addForeignKey` / `dropForeignKey` | `fk` (`ForeignKeyDef`) / `name` | MySQL/MariaDB, PostgreSQL, SQLite (пересборкой) |
| `setPrimaryKey` / `dropPrimaryKey` | `columns` | MySQL/MariaDB, PostgreSQL, SQLite (пересборкой) |

MongoDB и Redis DDL-пакетов не поддерживают вовсе → 400. У Oracle нет `ON UPDATE` для внешних
ключей (только `ON DELETE`) — такой пакет отвергается на входе с 400, а не ошибкой сервера.
Остальные неподдерживаемые операции дают внятный 400 с объяснением, а не «Bad alter op».

#### SQLite: пересборка таблицы вместо отказа

SQLite не умеет `ALTER COLUMN` и смену PK/FK без пересоздания таблицы, поэтому `planAlter`/
`alterTable` для `alterColumn`, `set/dropPrimaryKey` и `add/dropForeignKey` строят
recreate-скрипт (`backend/src/drivers/sqlite.ts`, `buildRebuildStatements`):
`CREATE tmp → INSERT SELECT (с маппингом переименований) → DROP → RENAME`, плюс пересоздание
индексов и триггеров на финальном имени. На время пакета гасятся `PRAGMA foreign_keys`, в конце
проверяется `PRAGMA foreign_key_check` (битый FK — 400 с откатом всего пакета). `preview`
показывает ровно этот скрипт, потому что строитель у предпросмотра и применения общий.
Проверка: `e2e-design.mjs` (блок `rebuild`).

Ответ: `{ok, statements[], applied, transactional, undoAvailable}` — видно, каким SQL пакет
реально применён. Валидация: все имена проходят через `ident()`, `ON DELETE`/`ON UPDATE` — только
по allowlist `CASCADE`, `RESTRICT`, `SET NULL`, `SET DEFAULT`, `NO ACTION`, тип индекса — по
allowlist `BTREE/HASH/FULLTEXT/SPATIAL/GIN/GIST/BRIN` (PG-специфичные и `WHERE` у частичных
индексов отвергаются на MySQL/SQLite).

#### Предпросмотр и откат

- `POST .../:table/preview` — **сухой прогон**: возвращает `statements`, `transactional`, `ops`,
  `before` (плоский список значимых строк схемы «сейчас») и `applyHint`. Ничего не выполняет.
  Стейтменты строит **тот же** `planAlter` в драйвере, что и `alterTable`, поэтому предпросмотр
  не может разойтись с реальностью. Схему «после» без применения получить нельзя, поэтому факт
  показывается отдельным вызовом после apply.
- `POST .../:table/undo` — откат последнего пакета по снапшоту из таблицы `design_snapshots`
  в `meta.db` (по подключению/БД/таблице хранится только последний снапшот; в нём — список
  операций, плоские строки схемы «до» и полный DDL «до»). Автоматически восстанавливаются
  удалённые индексы, внешние ключи и триггеры. **Изменения колонок и переименования откатить
   нельзя** — сервер не помнит прежние данные, поэтому приходит 409 с `ddlBefore` для ручной
   сверки. Нет снапшота —
   404 («откатывать нечего», в интерфейсе это объяснение, а не ошибка), а 409 с `skipped` — если
   восстановить нечего (например, SQLite без пересоздания: там FK восстанавливается тем же
   rebuild-механизмом через `alterTable`).
- Снапшот снимается best-effort: если схему прочитать не удалось, alter всё равно уходит, но
  ответ содержит `undoAvailable: false`.

#### Транзакционность пакета

| СУБД | Поведение при ошибке в пакете |
|---|---|
| PostgreSQL, SQLite | пакет в одной транзакции (`BEGIN`/`COMMIT` и `better-sqlite3`-транзакция), ошибка откатывает всё целиком |
| MySQL, MariaDB | DDL коммитится неявно, настоящей транзакции нет: операции идут по одной выделенной сессии и останавливаются на первой ошибке → **409** с `partial: true, applied: N` |

#### Триггеры

`POST .../:table/triggers` (`{name, timing, event, statement}`) и
`DELETE .../:table/triggers/:name`. Коды ошибок драйвера переводятся в 409/404
(«Already exists» / «Not found»), а не в 500. Особенности по диалектам:

- **PostgreSQL** — в `statement` передаётся **имя уже созданной функции**; триггер создаётся с
  `EXECUTE FUNCTION` (в `pg_get_triggerdef` так и показывается). Функция ищется в схеме таблицы:
  нет такой — 400 с подсказкой создать её через `CREATE FUNCTION` в SQL-редакторе, а не `42883`
  от сервера. Имя таблицы может быть квалифицированным (`schema.table`); схемы кроме `public`
  читаются и пишутся везде (`getSchema`, `getPage`, DDL, гранты), в списке таблиц не-`public`
  видны как `schema.table`.
- **MySQL / MariaDB** — один SQL-стейтмент с `FOR EACH ROW`; `INSTEAD OF` отвергается (400).
- **SQLite** — тело оборачивается в `BEGIN ... END` (если пользователь уже написал — не трогаем),
  поэтому допускается несколько стейтментов; выполняется через `exec`, а не `query`.
- **MongoDB, Redis** — 400: драйверы не умеют `createTrigger`.

#### Представления

`POST /api/connections/:id/:db/views` (`{name, sql}`) и `DELETE .../views/:name`.
`sql` обязан быть одним читающим `SELECT`/`WITH` (`checkViewSql` в `drivers/helpers.ts`:
запись, мультистейтменты и пустое тело — 400). Поддерживают MySQL/MariaDB (на пуле с выбранной
БД, иначе `ER_NO_DB_ERROR`), PostgreSQL (со схемой: `"schema"."view"`), SQLite и Oracle
(дубль — 409 через `ORA-00955`, отсутствие — 404 через `ORA-00942`); MongoDB/Redis → 400.
Представления входят в `listTables` всех четырёх SQL-драйверов (MySQL — через `SHOW TABLES`,
PG — `pg_tables` + `pg_views`, SQLite — `sqlite_master`, Oracle — `user_tables` + `user_views`),
поэтому видны в навигации, читаются (`rows`, `getPage`) и переживают ER-граф; `kind` в схеме —
`view` (Oracle определяется через `user_views`). Дубли и отсутствие маппятся в 409/404
(`translateDriverError`, включая кривой код MariaDB и `Unknown VIEW`), а не в 500.
Проверка: `npm run e2e:views` (входит в `e2e:all`).

#### Схемы PostgreSQL

`POST /api/connections/:id/:db/schemas` (`{name}`) и `DELETE .../schemas/:name`
(`?cascade=1` — вместе с содержимым, иначе непустая отвергается 409 `2BP01`;
`public` удалять нельзя — 400; дубль — 409 `42P06`, отсутствие — 404 `3F000`).
Остальные СУБД → 400 (`Schemas are not supported`). Таблицы в схеме создаются обычным
`POST .../tables` с квалифицированным именем (`schema.table` — разбирает `pgSplit`),
в списке видны как `schema.table`. В UI — кнопка «Новая схема» в шапке списка таблиц
(только PostgreSQL, только на изменяемом подключении). Проверка: `npm run e2e:schema`.

#### Интерфейс конструктора

Вкладки «Индексы», «Связи» и «Триггеры» редактируемые (создание и удаление через design API).
Сохранение колонки уходит через design API пакетом `renameColumn` + `alterColumn` (+
`setPrimaryKey`/`dropPrimaryKey` при смене PK), а не собранным вручную `ALTER TABLE`. Любая
операция сначала показывает панель применённого DDL с подсказкой о транзакционности, рядом —
кнопка «Откатить DDL». У заголовка — бейдж `VIEW` для представлений и комментарий таблицы;
диалектные «хвосты» (`extra`) показываются чипами. Мёртвый скрытый блок «Дополнительно» удалён.
Подписи вкладок берутся из i18n (`table.tabs.*`): ключ `privileges` («Привилегии») добавлен в
`ru`, `en`, `de`, `fr`, `es`. **В `zh` его нет**, а `t()` при промахе возвращает сам ключ, поэтому
на китайском вкладка называется `table.tabs.privileges`. Контролы внешних ключей открыты для
всех SQL-диалектов, включая SQLite (там добавление/удаление FK идёт пересборкой таблицы, а дроп
понимает и синтезированные сервером имена `fk_<таблица>_<id>`). Вкладка «Привилегии» выбирает
пользователя вместе с хостом (`user@host` для MySQL/MariaDB — гранты там именно на такую пару).

### SQL-редактор

Два редактора (в нижней панели и на вкладке «SQL») с подсветкой Prism. Запрос выполняется **в
контексте выбранной БД**. Несколько стейтментов выполняются по очереди, возвращается результат
последнего. Перед выполнением SQL проходит через T-SQL-транслятор: `IDENTITY(1,1)` →
`AUTO_INCREMENT`/`SERIAL`, `GETDATE()` → `NOW()`/`CURRENT_TIMESTAMP`, `[name]` → кавычки диалекта,
`NVARCHAR(n)` → `VARCHAR(n)`, инлайн-`FOREIGN KEY` выносится в табличное ограничение для MySQL.
`SELECT` без `LIMIT` автоматически получает `LIMIT 1000`. Скрипты, сохранённые кнопкой
«Сохранить», попадают в историю; каждый `POST /query` автоматически логируется в неё.

Ошибка самого запроса — это **400 с текстом СУБД**, а не 500: опечатка или отсутствующая таблица
описаны сервером базы («Table 'demo.nope' doesn't exist», «You have an error in your SQL
syntax»), и панель показывает их как есть (`backend/src/core/dberror.ts`). Раньше такой ответ
доходил как `500 Internal server error` без текста, и по нему было нельзя понять, что
исправлять. Таймаут запроса — `504`. Настоящие 5xx остаются 5xx и по-прежнему не раскрывают
внутренности.

Частый случай с готовыми дампами (WordPress, Joomla, 1С) — `DEFAULT '0000-00-00 00:00:00'`:
MySQL 8.4 и MariaDB 10.2+ по умолчанию включают `NO_ZERO_DATE` и `STRICT_TRANS_TABLES`, поэтому
такая дата недопустима, и сервер отвечает `Invalid default value for 'post_date'`. Панель
дописывает к этому тексту подсказку (в `hintFor` в `core/dberror.ts`): поставьте реальную дату
вроде `1970-01-01 00:00:00`, разрешите `NULL` или ослабьте `sql_mode`.

#### Как интерфейс переводит ошибки сервера

Текст ошибки остаётся английским: его читают в журналах и в ответах API. Для перевода рядом с
ним идёт **машинный код** (`code`) — стабильный идентификатор, который не меняется вместе с
формулировками сервера:

| Код | Когда | Ключ перевода |
| --- | --- | --- |
| `explain_readonly` | «Объяснить» на запросе, меняющем данные | `errors.explainReadonly` |
| `table_not_found` | нет таблицы или колонки | `errors.tableNotFound` |
| `zero_date` | `DEFAULT '0000-00-00 00:00:00'` | `errors.zeroDate` |
| `bad_identifier` | недопустимое имя объекта | `errors.badIdentifier` |
| `read_only_connection` | подключение только для чтения | `errors.readOnlyConnection` |
| `unsupported_operation` | операции нет у этой СУБД | `errors.unsupportedOperation` |
| `undo_structural` | отказ откатить DDL, менявший колонки (409) | `errors.undoStructural` |
| `undo_nothing` | откатывать нечего: снимка DDL нет | `errors.undoNothing` |

Отказ отката DDL (`POST …/:table/undo`) возвращает `partial: true` и `ddlBefore` — DDL до
изменения. Интерфейс показывает перевод по коду, а под ним сам `ddlBefore`: это SQL,
переводить его нельзя, и он и есть инструкция что делать вручную.

Отказ по «только чтение» раньше писался вручную в 24 местах десяти файлов — теперь его даёт
`assertNotReadOnly` (`core/types.ts`), и код доезжает до интерфейса отовсюду.

Код проставляют `core/errcodes.ts` (`withCode`, `codeForDriverError`) и отдаёт общий обработчик
ошибок (`app.ts`). `ApiError` в `api.ts` переводит сообщение по коду **при создании ошибки**,
поэтому все `error.message` в компонентах дают перевод без правок в каждом из них, а исходный
английский текст остаётся в `error.serverMessage` для журнала. Кода нет — показывается текст
сервера как есть. Проверка: `npm run e2e:error-codes`.

Разбиение скрипта на стейтменты (`splitStatements` в `drivers/helpers.ts`) понимает не только
кавычки и комментарии, но и **тела `BEGIN ... END`** и **dollar-quoted блоки `$$...$$`**
(`CASE...END` внутри тела учитывается отдельно, `BEGIN TRANSACTION/WORK` телом не считается).
Благодаря этому `CREATE TRIGGER` и `CREATE FUNCTION` с многострочным телом из вкладки SQL больше
не рвутся на части.

### Мониторинг

Экран «Мониторинг» опрашивает `GET /api/system/status` (CPU, RAM, uptime, platform, loadavg — это
**хост, где работает backend**) и `GET /api/connections/:id/status` (версия, uptime, соединения,
запросы, медленные запросы, список процессов, размеры БД) каждые 10 секунд; QPS считается как
разница счётчика запросов между опросами. Живой пуш отсутствует — только polling. `KILL` доступен
только администратору на изменяемом подключении.

### Пользователи и права СУБД

Список пользователей, создание, удаление, список грантов, выдача/отзыв привилегии. Реализации:

| СУБД | Пользователи | Гранты |
|---|---|---|
| MySQL / MariaDB | `mysql.user` (`user@host`, хост выбирается, дефолт `%`) | `SHOW GRANTS`, `GRANT/REVOKE` на `*.*`, `db.*`, `db.table` для `user@host` |
| PostgreSQL | `pg_roles` (`rolcanlogin`) | `GRANT/REVOKE` на `schema.table` или `ALL TABLES IN SCHEMA public` |
| MongoDB | `usersInfo` в БД подключения (или `admin`) | роли из allowlist встроенных (`read`/`readWrite`/`dbAdmin`/...) или кастомные по шаблону — мусор даёт 400 на входе, а несуществующая роль 400 с текстом сервера (было 500) |
| Oracle | `all_users` (видимые текущему пользователю) | `GRANT/REVOKE` на таблицу; новый пользователь сразу получает `CREATE SESSION/TABLE/SEQUENCE/VIEW/TRIGGER` |
| Redis | `ACL LIST` | `ACL SETUSER` (`+@all`, `+select` и т. п.) |
| SQLite | — | возвращается пустой список, изменение → 400 |

Имя пользователя БД — по одному набору на движок (`validateDbUserName(name, kind)`:
PG до 63 с буквы, Oracle до 30 с `#`, Mongo с `-`); пароль 8–128 символов без управляющих
символов (кавычки/`;`/бэкслэш разрешены — в DDL уходят через `escSqlString()`);
привилегия из allowlist `SELECT|INSERT|UPDATE|DELETE|CREATE|DROP|ALTER|INDEX|ALL`.
API принимает `host` (`POST /dbusers`, `?host=` в DELETE/grants, поле `host` в grant/revoke);
в UI поле хоста показывается только для MySQL/MariaDB.

### Аудит и история

- **Аудит** (`audit`): `connId`, `action`, `target`, `ok`, `ms`, `at`, `actor`. Пишется на
  `conn.create/update/delete/test`, `db.create/drop`, `query`, `import`, `export`, `row.insert/update/delete`,
  `design.create/alter/drop`, `design.undo`, `design.trigger.create/drop`, `dbuser.create/drop`,
  `dbuser.grant/revoke`, `backup`, `restore`, `kill`.
  Читается с фильтром `connId` и `limit` (1–500). В UI это вкладка «События» и колокольчик
  уведомлений в шапке. В окне уведомления (`Header.tsx`) — кнопки **←**/**→** и счётчик
  `позиция / всего`: листают список, не закрывая окно, плюс стрелки клавиатуры `←`/`→`;
  на первом и последнем элементе соответствующая кнопка отключена. Проверка:
  `npm run e2e:notif` (входит в `e2e:full`).
- **История запросов** (`query_history`): автологин каждого `POST /query` (успех/ошибка, `execMs`),
  **DDL из конструктора** (пакет alter — каждым выполненным стейтментом, создание/удаление
  триггера — одним; `design.create`/`design.drop` в историю не пишутся), ручное сохранение,
  `PATCH` (снять/поставить «сохранён», переименовать — только владелец),
  `DELETE` (только владелец). Retention: 200 несохранённых записей на пользователя; сохранённые не
  вычищаются. `GET /api/history` всегда фильтрует по текущему `userId`; поддерживает
  `connId`, `savedOnly`, `q` (по SQL и имени), `limit` (1–200).
- **Очистка журналов** (в UI — кнопка «Очистить» в панели «Журналы» на каждой вкладке):
  - `DELETE /api/audit?all=1` (или `?connId=`) — журнал операций, **только admin**. Запись о самой
    очистке пишется **после** удаления (`audit.clear`), поэтому след остаётся виден.
  - `DELETE /api/history?scope=mine|saved|all` (+ `connId`) — журнал запросов. `mine` доступен любой
    роли (только свои записи), `saved` и `all` — только admin. Само действие логируется как
    `history.clear` в журнале операций.
  - Вкладка «SQL» (список запросов текущей сессии) чистится только на клиенте — эти записи нигде не
    сохраняются.
  - Подтверждение обязательно: удаление необратимо, отмены нет.
- **Снапшоты DDL** (`design_snapshots` в `meta.db`): `connId`, `dbName`, `tableName`, `opsJson`,
  `statementsJson`, `linesBefore`, `ddlBefore`, `actor`, `at`; индекс по
  `(connId, dbName, tableName, at DESC)`. Хранится только последний пакет на таблицу — этого
  хватает для одного отката (`POST .../undo`), но не для полной истории изменений.

### Точки восстановления (checkpoints) данных

Отличаются от бэкапа по расписанию: снимаются по требованию и автоматически перед разрушительным
DDL, поэтому не зависят от таймера. Это «страховочная копия одной таблицы», а не бэкап инстанса.

- Где лежат: каталог `checkpoints/` рядом с `meta.db`, записи — в таблице `table_checkpoints`
  (`connId`, `dbName`, `tableName`, `reason`, `file`, `format`, `bytes`, `rows`, `ddl`, `actor`, `at`).
- Формат дампа: `sql` для MySQL/MariaDB/PostgreSQL/SQLite (файл `.sql` — `CREATE TABLE` + `INSERT`),
  `json` для MongoDB (файл `.json` — плоский массив документов коллекции).
- Ограничения: 50 МБ на дамп (дальше `413` и подсказка «сделайте бэкап по расписанию»),
  **20 последних точек на таблицу** — старые файлы и записи удаляются автоматически.
- Автоматическая точка создаётся перед `dropColumn` и `DROP TABLE`; в ответе DDL приходит
  `checkpointId`. Ручная — `POST /api/checkpoints` с `reason: 'manual'`.
- Откат: `POST /api/checkpoints/:id/restore`. Если таблица/коллекция уже существует, нужен явный
  `dropExisting: true`, иначе `409` — данные после точки иначе не вернуть. При откате SQL-таблица
  пересоздаётся (`recreated: true`), MongoDB-коллекция очищается и заполняется заново, причём
  `_id` документов **сохраняются** (иначе ссылки на документы из других коллекций разорвались бы).
- Ограничения доступа: `readonly` не имеет доступа ни к списку, ни к созданию; удалять точки может
  только администратор; откат доступен любой пишущей роли.
- Осиротевшие файлы подчищаются `sweepCheckpointFiles` (файл без записи в `table_checkpoints`).

### Аудит со значениями правок

Колонка `valuesJson` в таблице `audit` (миграция выполняется при старте). Для
`row.insert` / `row.update` / `row.delete` пишется, что именно изменилось: `{before, after}`
плюс `patch` для правки. Ограничения: значение обрезается до 200 символов, глубина вложенности —
2 уровня, вся запись — до 8 КБ; при превышении сохраняется `{truncated: true, preview}`.
`GET /api/audit` распаковывает поле в `values` и не отдаёт сырой `valuesJson`; `readonly` по
прежнему не видит аудит. В интерфейсе это строки «было:» / «стало:» в журнале «События».

### Правила имени базы данных

Правила живут в одном месте — `backend/src/core/dbname.ts`, дублируются в форме
(`CreateDatabaseModal.tsx`), чтобы пользователь видел подсказку до отправки, и
покрыты набором `e2e-dbname`.

| СУБД | длина | набор символов |
| --- | --- | --- |
| MySQL / MariaDB | 64 | `[A-Za-z0-9_$]` |
| PostgreSQL | 63 | буква или `_` в начале, дальше `[A-Za-z0-9_$]` |
| MongoDB | 63 | `[A-Za-z0-9_-]`, не начинается с `system.` |
| SQLite | 64 | `[A-Za-z0-9_-]` (имя становится именем файла) |
| Redis | 64 | набор ключей: `[A-Za-z0-9_.:-]` |

У Redis нет схем, а есть 16 пронумерованных логических баз (`databases 16` в
`redis.conf`) и команда `SELECT`. Панель показывает в списке только базу `0` и те
номера, где реально есть ключи: все 16 строк выглядели бы одинаковыми и пустыми, как
будто панель создала 16 подключений. Список берётся из `INFO keyspace` (одна команда
на все базы), а если она недоступна — откатывается к прежнему `0…15`. Нужную бату можно
выбрать и вручную: `SELECT 7` в SQL-редакторе.

Почему не одна проверка на все СУБД: единое «`[A-Za-z0-9_]`, до 64» отвергало
валидные имена (дефис в MongoDB) и пропускало 64-символьные, которые MongoDB и
PostgreSQL не принимают, — пользователь получал 502 «Internal server error» вместо
400 с объяснением. Отдельно обрабатываются: обрезка пробелов по краям, «база уже
существует» и коллизия только по регистру в MongoDB (`shop` против `Shop`).

**Чтение** из базы проверяется мягче, чем создание. `ident()` в `drivers/helpers.ts`
намеренно строг — имена таблиц и колонок панель создаёт сама, и лишний символ там
это ошибка пользователя. А для имени БД есть отдельный `dbIdent()`: буквы, цифры,
`_`, дефис и `$`, до 64 символов. База с дефисом в имени могла появиться на сервере
помимо панели, и драйвер всё равно оборачивает имя в обратные кавычки. Со строгим
`ident()` чтение из неё падало с `Bad database: my-db` (400).

### Массовые операции по фильтру и предпросмотр (dry-run)

`POST /api/connections/:id/:db/:table/rows/bulk` с `{where, patch?|delete?, dryRun?,
confirm?, allowAll?}` — массовое обновление или удаление строк по фильтру из строки фильтра
панели (`col=value AND col2>10`; `OR` не поддерживается, как и при чтении).

Как устроено: сначала выборка строк по фильтру (как при чтении), затем операция по
первичному ключу каждой строки через обычные `updateRow`/`deleteRow`. Это медленнее одного
`UPDATE`, зато одинаково работает на всех СУБД и даёт образы «до» для отката.

Правила безопасности:

- по умолчанию — **предпросмотр**: возвращает `matched`, `sample` до 5 строк и человекочитаемый
  `preview`; ничего не меняется;
- применение требует **оба** флага: `dryRun: false` **и** `confirm: true`. Один флаг —
  недостаточно, а `confirm` без `dryRun` даёт 400 с объяснением (иначе «тихий» предпросмотр
  выглядел бы как отказ);
- пустой фильтр запрещён (иначе удар пришёлся бы по всей таблице), если не передано
  `allowAll: true`;
- больше 1000 подходящих строк — отказ с указанием количества. Проверка идёт постранично
  (`pageSize` у драйверов клампается до 500, поэтому один запрос на 1001 строку вернул бы
  500 и лимит не сработал бы никогда);
- **точка восстановления — условие операции**: если снимок снять не удалось (например, дамп
  тяжелее 50 МБ), операция отклоняется с 409 и *ничего не меняется*. Продолжить без точки
  восстановления можно только явным `allowWithoutCheckpoint: true` — панель спрашивает об этом
  отдельно и предупреждает, что откатывать будет нечем. В `ALTER TABLE` (design.ts) снимок
  остаётся лишь страховкой: там операция одна, а здесь меняются сотни строк;
- при успешном снимке его id возвращается в `checkpointId`; операция также попадает в аудит
  (`row.bulk_update`/`row.bulk_delete`) и в историю запросов;
- строки, у которых в выборке не оказалось значения ключа, в СУБД не отправляются (иначе
  фильтр был бы `{id: undefined}`) и попадают в `failed`;
- у MongoDB ключ строки — `_id` (у коллекций нет PRIMARY KEY);
- ошибки по отдельным строкам не роняют операцию: они возвращаются в `failed`.

Предпросмотр разрушительных операций: `DELETE .../tables/:table?dryRun=1` (сколько строк исчезнет,
какая операция выполнится) и `DELETE .../databases/:db?dryRun=1` (сколько таблиц в базе и список до
20 имён). Ничего не удаляют, системные базы по-прежнему защищены.

В интерфейсе — кнопка **«Массовые действия»** в заголовке вкладки «Данные»: фильтр, колонка и
значение для обновления или удаление, затем обязательный предпросмотр с числом строк,
SQL-превью (с значениями, а не только с именами колонок) и подтверждением. Значение
приводится к типу колонки, а не остаётся строкой — иначе `INTEGER` получал бы текст.

Предпросмотр удаления таблицы и базы работает и в интерфейсе: перед `DROP` панель
показывает число строк (или таблиц) и сам SQL-оператор, и только потом спрашивает
подтверждение. Раньше эти endpoints существовали, но вызывались только из тестов.

### Как выполняется массовая операция

Два пути, и в ответе видно, какой сработал (`mode`):

- **`set`** (основной) — одно выражение на всё множество: `UPDATE t SET … WHERE …`
  или `DELETE FROM t WHERE …`, в MongoDB — `updateMany`/`deleteMany`. Один поход в СУБД
  независимо от числа строк. Замер на PostgreSQL, 1000 строк: **333 мс** против
  **4307 мс** у построчного пути (~13×), из них большая часть времени — снятие точки
  восстановления, а не сама правка.
- **`rows`** (запасной) — поштучные `updateRow`/`deleteRow` по первичному ключу. Нужен,
  если драйвер не умеет set-based (например, Redis) или если сет-операция упала:
  маршрут молча возвращается на этот путь, а не прерывает операцию на середине.

Ключевое свойство: **условие отбора одно и то же** для подсчёта, предпросмотра и
самой правки. И то и другое собирается одной функцией `buildWhere()` в
`drivers/helpers.ts` (для MongoDB — `parsePageFilter()`), поэтому предпросмотр не может
показать 500 строк, а операция — затронуть другие. Набор `e2e-bulk` проверяет и это
(`affected equals previewed`), и то, что запасной путь даёт тот же результат.

Форсировать построчный путь можно переменной окружения `PANEL_BULK_MODE=rows` —
это диагностика, когда set-based на конкретной СУБД ведёт себя неожиданно.

### Известные ограничения массовых операций

- Транзакции нет. Сбой на середине построчного пути оставит часть строк изменёнными;
  откат — через точку восстановления, которая снимается до начала операции.
- `OR` в фильтре не поддерживается (как и при чтении); LIKE-операторы те же, что в панели
  фильтра: `~` (содержит), `^` (начинается), `$` (заканчивается).
- Лимит 1000 строк на операцию — сознательный: снимок состояния это полный дамп
  таблицы, и для больших объёмов он упирается в лимит 50 МБ.
- Прогресс-репортинг не сделан. На set-based пути операция занимает доли секунды и
  ждать нечего, на запасном — заметно дольше, и панель молчит до ответа.

### План выполнения запроса (EXPLAIN)

`POST /api/connections/:id/explain` с `{sql, db, analyze?}` — план без выполнения запроса
(для PostgreSQL `EXPLAIN (FORMAT TEXT)`, для MySQL/MariaDB `EXPLAIN`, для SQLite
`EXPLAIN QUERY PLAN`). Поддерживают не все СУБД: для MongoDB и Redis отвечаем 400 с
объяснением, планировщика там нет.

- **Только чтение.** Запрос проверяется по первому ключевому слову и по наличию
  операций записи: `INSERT`/`UPDATE`/`DELETE`/`DROP`/`CREATE`/`TRUNCATE`/`GRANT` и т. п. →
  400. Это важно, потому что `analyze: true` в PostgreSQL **выполняет** запрос, и без
  проверки кнопка «Объяснить» могла бы стать источником неожиданных записей;
- для PostgreSQL `analyze: true` добавляет фактические тайминги и буферы
  (`EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)`);
- в MySQL база выбирается подключением, а не префиксом в тексте: `EXPLAIN db.SELECT …`
  не разбирается, поэтому такой вариант не используется;
- план попадает в аудит как `query.explain`; роль `readonly` смотреть план может (это чтение).

В интерфейсе это кнопка **«Объяснить»** рядом с «Выполнить» в обоих редакторах SQL;
показывается та же таблица результата, только строками плана.

### Откат изменений данных (data undo)

Третий механизм отката, самый лёгкий: перед правкой строк снимаются образы **только затронутых
строк** (без дампа таблицы), поэтому не срабатывает лимит 50 МБ и он не «съедает» точку
восстановления. Отличается от «Откатить DDL» (структура) и от checkpoint (дамп таблицы).

- Где хранится: таблица `data_undo` в `meta.db` — `connId`, `dbName`, `tableName`, `op`
  (`insert`/`update`/`delete`), `pkJson`, `beforeJson`, `afterJson`, `rows`, `summary`, `undone`,
  `blocked`, `actor`, `at`. **30 последних записей на таблицу**, старые удаляются.
- Заполняется автоматически маршрутами строк: `POST`/`PATCH`/`DELETE .../rows`. Образы читаются
  **до** изменения (для правки и удаления) — иначе откатывать было бы нечего.
- Откат: `POST /api/data-undo/:id/undo`, повтор: `POST /api/data-undo/:id/redo` (только после
  отката, иначе `409`; повторный откат — тоже `409`). В интерфейсе это кнопка
  **«Откатить данные»** в карточке таблицы: список операций с действиями «Отменить»/«Повторить».
- Обратные операции строятся по первичному ключу: откат вставки удаляет добавленную строку, откат
  правки возвращает прежние значения, откат удаления вставляет строки обратно **с теми же
  ключами**. В MongoDB ключ — `_id`, и он сохраняется.
- Намеренные ограничения (лучше отказ, чем тихая порча данных):
  - без первичного ключа откат невозможен — запись помечается неоткатываемой (`blocked`);
  - больше 500 строк за раз или образ больше 1 МБ — тоже `blocked` с подсказкой про checkpoint;
  - **PostgreSQL с `GENERATED ... AS IDENTITY`**: откат удаления запрещён (`409`) — вернуть строку с
    прежним ключом нельзя, а генерировать заново значит разорвать ссылки. У обычного `serial`
    такой проблемы нет: явный ключ вставить можно, поэтому откат работает;
  - `POST /query` (ad-hoc SQL) образы не снимает — там нужен checkpoint.
- Доступ: `readonly` заблокирован (403), `editor` может смотреть и откатывать, удалять записи
  журнала может только администратор. Ошибка подготовки образа **не отменяет** саму правку данных.

### Защита от перезаписи чужих правок (optimistic locking)

Правка строки в панели — это `UPDATE ... WHERE`, поэтому правку одного человека
могла молча затереть другая вкладка. Теперь клиент передаёт `expected` — значения
строки, на основе которых он правил, и сервер проверяет их в том же `WHERE`:

- `PATCH`/`DELETE .../rows` принимают необязательное поле `expected`;
- если значения не совпали, сервер отвечает **409** и возвращает актуальную строку
  (`current`) и список проверенных колонок (`checked`) — панель показывает
  «изменили, пока вы правили» и обновляет данные, ничего не затирая;
- `expected` проверяет только те колонки, которые меняете: если чужое изменение
  было в другой колонке, ваша правка безопасна;
- без `expected` поведение прежнее (обычный unconditional UPDATE);
- колонки со значением `NULL` в проверку не входят: в SQL `WHERE col = NULL` не
  находит строку никогда. В MongoDB `{col: null}` совпадает и с отсутствующим
  полем, поэтому там `null` проверяется.

### Сравнение модели с базой (drift)

`POST /api/models/:id/diff` с `{connId, db, includeExtra?}` — отчёт без изменений:
чего не хватает, что лишнее и что разошлось (колонки, индексы, внешние ключи,
триггеры). В модальном окне моделей это кнопка **«Сравнить с базой»».

Что намеренно не сравнивается, иначе были бы постоянные ложные расхождения:
значения по умолчанию (у SERIAL это `nextval(...)`, у PG — `NULL`), `extra`,
тела триггеров (СУБД переформатируют) и точная запись типов: `INT`/`integer`/`int4`
и `VARCHAR(100)`/`character varying(100)` считаются одним типом. Автоиндекс
первичного ключа (`PRIMARY`, `t_pkey`) тоже игнорируется — он есть в любой таблице
с PK. `includeExtra: false` убирает «лишние» объекты, когда база намеренно богаче
модели.

### Модели проекта

Сохранённая схема целиком, в отличие от точки восстановления (дамп одной таблицы) и от отката DDL
(один пакет). Модель можно применить к другой базе — это перенос конструкции между СУБД.

- Где хранится: `project_models` и `model_versions` в `meta.db`. В модели — имя (уникальное),
  `dbKind`/`dbName` источника, комментарий, `tablesJson` (таблицы, колонки, индексы, внешние ключи,
  триггеры), `version`, автор, даты.
- Версионирование: каждое сохранение (`PUT`) кладёт **предыдущее** содержимое в `model_versions`
  (последние **20**), `version` растёт. Опциональный `expectedVersion` защищает от потери правок:
  при расхождении — `409`. Откат на версию создаёт **новую** версию, история не теряется.
- Ограничения: 200 таблиц и 200 колонок в модели, имя до 128 символов и только буквы/цифры/
  подчёркивание, JSON до 4 МБ; индексы и внешние ключи проверяются на существование колонок.
- Сценарии API: `POST /api/models/import` забирает схему существующей базы в модель (это основной
  путь «сохранить»), `POST /api/models` создаёт модель из готового JSON, `PUT` — новая версия.
- Применение `POST /api/models/:id/apply` (`{connId, db, dropExisting?}`): создаёт отсутствующие
  таблицы, затем индексы, внешние ключи и триггеры. Существующие таблицы по умолчанию **не**
  трогаются (попадают в `skipped`); с `dropExisting: true` они пересоздаются — и перед каждой
  снимается точка восстановления. Таблицы удаляются в обратном порядке зависимостей, иначе
  PostgreSQL/MySQL не даст удалить родителя, на который ссылается FK. Ошибка по одной таблице не
  роняет всё применение — она попадает в `errors`, а ответ содержит выполненные `statements`.
- Права: читать может любой авторизованный (включая `readonly`), сохранять — `editor`/`admin`,
  удалять — только `admin`. Действия пишутся в аудит (`model.import`, `model.save`,
  `model.apply`, `model.create`, `model.delete`, `model.update`).
- **Перевод типов между СУБД** (`backend/src/core/typemap.ts`): модель, снятая с одной СУБД,
  применяется к другой, поэтому типы и выражения `DEFAULT` переводятся в диалект цели, а не
  передаются как есть. Правила: `VARCHAR2`↔`VARCHAR`, `TEXT`↔`TEXT`/`CLOB`, `BLOB`/`BYTEA`,
  `BOOLEAN`/`BOOL`, `DOUBLE`↔`DOUBLE PRECISION`, `SERIAL`→`INT`, `UUID`→`VARCHAR(36)`,
  `INTERVAL DAY TO SECOND`→`INTERVAL` (PG) или `VARCHAR(30)` (MySQL), метки времени →`DATETIME`.
  Длина и точность переносятся по максимуму цели: `VARCHAR(5000)` → `VARCHAR2(4000)`,
  `NVARCHAR2(4000)` → `NVARCHAR2(2000)`, `CHAR(4000)` → `CHAR(2000)`. Oracle `NUMBER(p[,s])`
  разбирается по параметру, потому что `NUMBER` без точности — это 38 знаков, а не «целое»:
  `NUMBER(19)` → `BIGINT` (PG/MySQL) или `INTEGER` (SQLite), `NUMBER(19,2)` → `NUMERIC`/`DECIMAL`,
  `NUMBER` → `NUMERIC(38,0)`. Имена типов, у которых нет соответствия, оставляются как есть —
  если целевая СУБД их не понимает, `apply` вернёт ошибку, а не создаст таблицу «на всякий случай».
- Внешние ключи и триггеры не применяются к таблице, которую этот прогон не создавал: её ещё нет,
  и сервер вернул бы `ORA-00942`/`42P01`. Для таких объектов `apply` сообщает `skipped`.
- **SQLite получает внешние ключи прямо в `CREATE TABLE`** (`CreateTableDef.foreignKeys`,
  `inlineForeignKeySql`): у него нет `ALTER TABLE ADD CONSTRAINT`, поэтому ключ к новой таблице
  иначе добавить нельзя и модель теряла все связи. Имена ограничений SQLite не хранит
  (`PRAGMA foreign_key_list` их не отдаёт), поэтому драйвер собирает `fk_<таблица>_<n>` — проверять
  надо смысл ключа, а не имя.
- **Ширина отображения целых отбрасывается вне MySQL/MariaDB.** `INT(11)`, `BIGINT(20)`,
  `TINYINT(3)` — это артефакт MySQL (сервер её игнорирует), а не точность числа: PostgreSQL и
  SQLite такой тип не понимают, а Oracle прочитал бы скобки как точность. Поэтому
  `mapColumnType` переводит их по смыслу: `INT(11)` → `INTEGER`/`NUMBER`, `BIGINT(20)` →
  `BIGINT`/`NUMBER(19)` (у Oracle самого `BIGINT` нет — `ORA-00902`), `TINYINT(3)` → `NUMBER(3)`.
  Для MySQL ширина сохраняется, и allowlist (`TYPE_PATTERNS`) её принимает.
- **`DEFAULT` ставится перед `NOT NULL`** во всех диалектах: Oracle разбирает определение колонки
  строго по порядку и на `col NUMBER NOT NULL DEFAULT 0` отвечает `ORA-03076`.
- Проверка правил отдельно от сервера: `npm run check:type-map` (93 проверки перевода, allowlist
  цели и `DEFAULT`), входит в `verify`. Живой перенос на пять СУБД — `npm run e2e:model-xengine`
  (входит в `e2e:all`): он проверяет не только «таблица создалась», но и что в неё влезают
  `12.34` в `DECIMAL(10,2)` и `2^53-1` в `BIGINT`, и что внешний ключ создан.
- В интерфейсе: правая панель → **«Модели проекта»** — список, поиск, импорт схемы текущей базы,
  история версий с возвратом, применение к выбранной базе двумя кнопками (дописать / пересоздать).



`GET/PUT /api/settings` — общие для инстанса (файл `settings.json` рядом с `meta.db`): название
проекта, часовой пояс, тема, «проверять обновления», включение/длительность тостов, уведомления.
Менять может только администратор. Тема дополнительно хранится в `localStorage`.

## HTTP API

Базовый префикс — `/api`. При `REQUIRE_AUTH=1` каждый запрос, кроме публичного списка, требует
заголовок `Authorization: Bearer <JWT>`. Тело запросов — JSON (кроме загрузки файлов — multipart).
Swagger UI: `GET /docs` (публичен), схема: `GET /docs/json` и `/docs/yaml`.

Порядок регистрации в `app.ts` здесь принципиален: swagger подключается первым
плагином, а маршруты — отдельным `app.register()` ниже. `register()` откладывает запуск
плагина до `ready()`, поэтому при регистрации маршрутов напрямую (`app.get(...)`) все они
попадали в Fastify раньше, чем fastify-swagger ставил свой хук `onRoute`, — и спецификация
содержала ноль маршрутов при 110 зарегистрированных. `hideUntagged: false` это не лечило:
дело было не в фильтре, а в пустом списке. Проверка: `npm run check:openapi` (работает без
стенда, поднимает приложение в процессе и требует непустую спецификацию).

Ошибки всегда в формате `{ "error": "..." }`. Коды `4xx` — это наши собственные проверки
(сообщение безопасно для клиента), `5xx` — санитизируются до `Internal server error`, детали
пишутся в лог.

## Резервные копии, импорт и экспорт

### Расписания бэкапов

`backup_schedules`: подключение, БД (пусто = `main`/БД подключения), формат `sql|json`,
интервал `intervalMin` (5…43200, по умолчанию 1440 = сутки), `keepLast` (1…50, по умолчанию 7),
`enabled`, `lastRunAt`, `nextRunAt`. MongoDB допускает только `json`. Планировщик в памяти
backend тикает **каждые 30 секунд** и выполняет просроченные включённые расписания
(в `audit` такие запуски помечаются `actor='scheduler'`).

Формат файла: `<каталог META_PATH>/backups/<scheduleId>_<ISO-дата>.sql|json`; дамп `sql` начинается
с `CREATE TABLE IF NOT EXISTS` и содержит `INSERT INTO` по всем таблицам, `json` — объект
`{"таблица": [строки...]}`. Дамп пишется потоком, память константна. После успешного запуска
выполняется retention: всё старше `keepLast` удаляется с диска и из `backup_runs`.

### Восстановление

`POST /api/backups/runs/:id/restore`: сначала из файла вычисляются имена таблиц (для `sql` — по
`INSERT INTO`, для `json` — по ключам объекта), затем каждая очищается (`DELETE FROM` /
`deleteMany`) и заполняется заново — это идемпотентно и не плодит дубли первичных ключей.
Ограничения: `readOnly`-подключение → 403, драйвер без `clearTable`/`importRows`/`execScript` →
400 (SQL-скрипт в MongoDB/Redis не заливается: у документов и ключей нет SQL), дамп больше
100 MB → 413.

### Импорт

`POST /api/connections/:id/import` с `{format, db, table, data}`; `data` — строка, лимит 10 MB
(для маршрута отдельно поднят `bodyLimit` до 15 MB).

| Формат | Что происходит | Ограничения |
|---|---|---|
| `sql` | выполняется как скрипт | MySQL/MariaDB, PostgreSQL, SQLite, Oracle; MongoDB/Redis → 400; лимит скрипта 5 MB, таймаут 120 с |
| `csv` | первая строка — заголовки, далее `parseCsv` (кавычки, переносы строк в кавычках, BOM) | требуется `table` (для Redis — префикс ключей); ≤50 000 строк, пачками по 500 |
| `json` | массив объектов | требуется `table` (для Redis — префикс ключей); ≤50 000 строк; при импорте в MongoDB `_id` выбрасывается (кроме `keepIds` у checkpoint), а расширенный JSON (`$oid`, `$date`, `$number*`, `$binary`) превращается в нативные `ObjectId`/`Date`/числа; строка Redis с полем `key` пишет именно этот ключ (`SET` для скаляра, `HSET` для хеша), без `key` — `HSET table:i` |

В UI импорт доступен на вкладке «Импорт» и в правой панели; для CSV/JSON нужно выбрать таблицу
назначения, для `sql` — необязательно.

### Экспорт

`GET /api/connections/:id/:db/:table/export?format=csv|json|sql` — потоковый ответ с
`Content-Disposition: attachment`. `sql` начинается с `CREATE TABLE IF NOT EXISTS` (структура
восстанавливается из нормализованного `TableSchema`), дальше `INSERT INTO`; диалектные кавычки
(`\` для MySQL/MariaDB, `"` для PG/SQLite). MongoDB + `format=sql` → 400. В UI: вкладка «Экспорт»
(одна таблица или вся база, формат на выбор), кнопка «Экспорт» в карточке таблицы, массовый экспорт
выбранных таблиц в CSV и кнопка «Экспорт» в правой панели (все таблицы БД в CSV).

#### Экспорт всей базы

`GET /api/connections/:id/:db/export?format=csv|json|sql` — та же потоковая выгрузка, но одним
файлом по всем таблицам базы. Необязательный параметр `tables=a,b` ограничивает выгрузку
подмножеством; неизвестная таблица → 404, неверный `format` → 400.

Порядок таблиц в SQL-дампе выстраивается по внешним ключам (`core/tableorder.ts`): сначала
таблицы, на которые ссылаются другие, затем зависимые. Без этого дамп не восстанавливался —
таблица с FK попадала раньше той, на которую ссылается. При цикле по FK порядок остаётся
исходным, сервер не падает.

Формат при всей базе:

- `sql` — последовательность `CREATE TABLE` + `INSERT INTO` в восстанавливаемом порядке;
- `json` — объект `{"имя таблицы": [строки], ...}`;
- `csv` — составной файл: первые строки поясняют формат, каждая таблица идёт после
  строки-разделителя `# table: <имя>` со своим заголовком колонок, чтобы файл можно было
  разделить обратно.

В UI это список «Что выгружать» на вкладке «Экспорт»: по умолчанию выбрана вся база,
но можно указать конкретную таблицу. Имя файла — `имя базы.формат`.
Проверка: `npm run e2e:export-db`.

Что теперь восстанавливает `CREATE TABLE` в SQL-дампе (`core/dump.ts`):

- автоинкремент: `AUTO_INCREMENT` (MySQL/MariaDB), `SERIAL` (PostgreSQL),
  `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite);
- уникальные индексы отдельными `CREATE UNIQUE INDEX`, обычные — `CREATE INDEX` (уникальность
  больше не теряется молча после restore);
- внешние ключи с `ON DELETE`/`ON UPDATE`: у SQLite — **внутри** `CREATE TABLE` (у него нет
  `ALTER TABLE ... ADD CONSTRAINT`), у MySQL/PostgreSQL — отдельными `ALTER TABLE ADD CONSTRAINT`;
- служебные автоиндексы SQLite (`sqlite_*`) пропускаются — их сервер создаёт сам из ограничений;
- **неизвестный тип больше не подменяется на `TEXT`**: тип берётся от сервера как есть, иначе
  дамп внешне выглядел бы корректно, а схема после restore отличалась бы.

Тот же генератор (`renderTableDdl`) используется для поля `ddlBefore` в снапшоте DDL и в ответе
409 при невозможности отката — по нему структуру можно восстановить вручную.

Ключевые решения:

- Метаданные панели (подключения, пользователи, аудит, история, снапшоты DDL, расписания бэкапов,
  настройки) лежат в локальной `meta.db`; целевые данные панель не хранит.
- Структура объекта приходит из драйвера в одном нормализованном виде (`TableSchema`), а
  `planAlter` в каждом драйвере — единственный построитель DDL и для предпросмотра, и для
  применения: разойтись они не могут по построению.
- Реестр драйверов (`plugins/registry.ts`) — точка расширения: добавить СУБД = написать драйвер
  и вызвать `register()` в `app.ts`. `GET /api/drivers` показывает, что зарегистрировано.
- Пулы MySQL/PG ключуются `id@host:port:user:database` — разные БД одного подключения не делят
  пул; при удалённой default-БД драйверы автоматически переподключаются к служебной БД
  (или без выбора БД для MySQL).
- Отдельный пул **без** default-БД используется для операций уровня сервера (`SHOW DATABASES`,
  `SHOW TABLES FROM db`, `CREATE/DROP DATABASE`, гранты), чтобы они работали независимо от того,
  жива ли default-БД подключения.
- Все имена таблиц/колонок проходят через `ident()` (буквы любых алфавитов, цифры, `_`, а также
  `#`, `$`, `-` — их используют CMS: `#__mywidget` у Joomla, `my-table`), значения —
  через bind-параметры; фильтры строк разбираются с белым списком операторов. Кавычки, обратные
  кавычки, пробелы, точки и `;` по-прежнему запрещены: имя подставляется в запрос уже обёрнутым
  в кавычки диалекта, и без escape-а именно эти символы выпустили бы значение за пределы
  идентификатора. Правило закреплено статически: `npm run check:identifiers` (58 проверок, входит
  в `verify`) — оно фиксирует и «слишком строгое» поведение (панель создаёт объект через SQL и
  больше не может его открыть), и «слишком мягкое» (выход значения за кавычки).
- `capSelect` не даёт выкачать таблицу целиком: `SELECT`/`WITH` без верхнеуровневого `LIMIT`
  получают `LIMIT QUERY_MAX_ROWS`. Импорт/экспорт от этого лимита не зависят (поток + пачки).

## Тесты (e2e) и CI

Прогон начинается с `e2e-preflight`: он ждёт, пока frontend и backend начнут отвечать, и
либо поглощает перезапуск контейнеров, либо печатает понятную ошибку вместо
`TypeError: fetch failed` с ECONNREFUSED. **Не пересобирайте контейнеры во время
прогона** — соединения наборов при этом рвутся, и падение будет выглядеть как поломка
приложения. Адреса стенда переопределяются через `E2E_BASE` / `E2E_API`.

28 HTTP-сюитов, гоняются **против поднятого backend** (не мокают драйверы):

`e2e-users` (идемпотентные фикстуры `ro_user`/`e2e_editor` + проверка входа), `e2e-dbs`,
`e2e-export` (5000 строк, round-trip), `e2e-er`, `e2e-status`, `e2e-backup` (schedule/run/restore/
retention), `e2e-design` (create/alter/drop, форма `TableSchema`, защита от инъекций),
`e2e-model` (контракт `TableSchema` и полнота SQL-дампа на mysql/mariadb/pg/sqlite/mongo:
`autoInc`, составные и уникальные индексы, FK с правилами, триггеры, `kind: 'view'`, отсутствие
`DEFAULT 'NULL'`, round-trip дампа через SQLite), `e2e-triggers` (CRUD триггеров на
mysql/mariadb/pg/sqlite: `FOR EACH ROW`, `EXECUTE FUNCTION`, обёртка `BEGIN..END` без двойного
`BEGIN`, 409 на дубль, 404 на удаление отсутствующего, 400 на MongoDB/Redis, 403 на
read-only-подключении), `e2e-preview` (стейтменты предпросмотра совпадают с apply, `before`,
флаг `transactional`, предпросмотр ничего не применяет), `e2e-undo` (откат индексов/FK/триггеров,
409 с `ddlBefore` для пакетов с колонками), `e2e-checkpoints` (ручные и авто-точки, откат данных на
mysql/pg/sqlite/mongo, сохранение `_id` документов при откате, 20 точек на таблицу, права),
`e2e-dbusers`, `e2e-grants`, `e2e-audit`, `e2e-audit-values` (аудит правок строк хранит before/after, длинные
значения обрезаются, сырой `valuesJson` не отдаётся), `e2e-rows`, `e2e-dbname` (правила имени БД: свои пределы 63/64 у каждой СУБД, ни одного 502 от драйвера), `e2e-bulk` (массовые операции: предпросмотр ничего не меняет, пустой фильтр и односторонний confirm отклоняются, авто-точка), `e2e-row-lock` (конфликт правки строки: 409 + актуальная строка, чужое изменение не затирается), `e2e-poolkill`, `e2e-sqlitefiles`,
`e2e-history`, `e2e-logs-clear` (очистка журналов: права ролей, `mine`/`saved`/`all`, по подключению,
изоляция истории по пользователям), `e2e-models` (модели проекта: импорт схемы, версии и откат версии,
конфликт версий, применение модели к другой СУБД с индексами/FK, пересоздание с чекпоинтом,
права), `e2e-docs`, `e2e-redis`. Общие приспособления — `e2e-fixtures.mjs` (наборы сами
восстанавливают удалённые подключения и базу `demo`).

```bash
npm run dbs:up          # mysql:3306, mariadb:3307, postgres:5432, mongo:27017, redis:6379
npm run seed:dbs        # сид demo.users (Ann/Bob) на mysql/mariadb/pg/mongo

# backend: REQUIRE_AUTH=1, ADMIN_PASSWORD=<...>, META_PATH=./data/meta.db, порт 3001
npm run e2e:all         # фикстуры + 28 сюитов, порядок важен (общие фикстуры и состояние)
```

Требования: поднятые пять СУБД на указанных портах и backend с `REQUIRE_AUTH=1`.
`E2E_BASE` (по умолчанию `http://localhost:3001`) и `ADMIN_USER`/`ADMIN_PASSWORD` можно переопределить
через окружение. Отдельный сюит: `npm run e2e:<имя>`.

Хосты СУБД для e2e:

| Переменная | По умолчанию | Кто использует |
| --- | --- | --- |
| `E2E_DB_HOST` | — | переопределяет все четыре хоста сразу |
| `E2E_MYSQL_HOST` | compose-имя `mysql` | хост, который видит **backend** |
| `E2E_MARIADB_HOST` | `mariadb` | то же |
| `E2E_PG_HOST` | `postgres` | то же |
| `E2E_MONGO_HOST` | `mongo` | то же |
| `E2E_REDIS_HOST` | `redis` | то же |
| `E2E_LOCAL_MONGO_HOST` | `127.0.0.1` | прямой `mongodb://` из самого скрипта (чистка) |
| `E2E_SQLITE_DIR` | перебор `/data/sqlite`, `backend/data/sqlite` | каталог загруженных SQLite-файлов **внутри backend** |

Значения по умолчанию рассчитаны на стек, где backend тоже в Docker: тогда `127.0.0.1` внутри
контейнера указывает на сам контейнер. Если backend запущен нативно на хосте, задайте
`E2E_DB_HOST=127.0.0.1` (и `E2E_REDIS_HOST=127.0.0.1`).

Сюиты **самовосстанавливают** свои `e2e-*` подключения: при расхождении хоста/порта/БД с
compose-окружением существующее подключение обновляется через `PATCH /api/connections/:id`, поэтому
старые `127.0.0.1` из прошлых прогонов не ломают набор. `seed:dbs` идемпотентен: создаёт базу
`demo`, если её нет, и берёт MariaDB с published-порта `3307`.

`e2e-sqlitefiles` работает с файлами в ФС backend-а: путь строится строковой склейкой
(`/data/sqlite/<file>.db`), а не `path.join` — на Windows `path.join` превратил бы `/data/sqlite` в
`\data\sqlite`, и backend создал бы файл-мусор. Проверяется оба режима удаления подключения:
metadata-only (файл остаётся) и `?dropDatabase=1` (файл удаляется).

Проверки без БД: `npm run typecheck`, `npm run verify` (`typecheck` + `vite build` +
`docker compose config --quiet`), а также разбор скриптов на стейтменты — 12 кейсов
(`BEGIN...END`, `$$...$$`, `CASE...END`, `BEGIN TRANSACTION`, комментарии, `''` в литералах):

```bash
cd backend; npx tsx scripts/check-split-statements.mts   # 12/12 PASS, печатает SPLIT OK
```

### CI (`.github/workflows/ci.yml`)

`npm ci` → `npm run typecheck` → `build backend` → `build frontend` → `docker compose config` →
`node backend/dist/index.js` в фоне с опросом `/api/health` → `npm run seed:dbs` → `npm run e2e:all`.

Service-контейнеры: **mysql, mariadb (на 3307), postgres, mongo, redis**, у всех healthcheck'и.
Backend запускается обычным процессом (не `tsx watch`), `NODE_ENV` намеренно не задан, чтобы
production-guard не отверг e2e-значения.

### Функции, которых нет (сознательно не документируются как возможности)

- **2FA** — серверного эндпоинта нет; вкладка «Безопасность и 2FA» прямо сообщает об этом.
- **Создание/изменение/удаление представлений и схем** — только просмотр: `CREATE VIEW`,
  `ALTER SCHEMA`, отдельные схемы PostgreSQL по-прежнему делаются вручную через SQL-редактор.
  (Индексы, внешние ключи, первичный ключ и триггеры, наоборот, редактируются — см.
  [Конструктор таблиц](#конструктор-таблиц).)
- **Materialized Views, S3/облачные бэкапы, сжатие/шифрование дампов, отправка бэкапов на почту** —
  не реализовано. Бэкапы пишутся локально в `<каталог META_PATH>/backups`.
- **WebSocket / живой пуш** — зависимость `@fastify/websocket` установлена, но нигде не
  подключена; обновление данных только по запросу (мониторинг опрашивает раз в 10 с).
- **Автообновление данных в открытой таблице** — нет; есть кнопки обновления и повторная загрузка
  после DDL/CRUD.
- **Отмена запроса из UI** — только `KILL` по pid у администратора (MySQL/MariaDB, PostgreSQL).
- **Импорт/экспорт в формате XLSX, сжатые архивы** — нет.
- **Схемы PostgreSQL**: чтение, DDL, триггеры, гранты и DML работают с `schema.table`;
  создание/удаление — через `POST/DELETE .../schemas` (кнопка «Новая схема» в списке таблиц).
  `grant` без таблицы по-прежнему бьёт по `ALL TABLES IN SCHEMA public`.
- **Redis**: только команды `GET`, `SET`, `DEL`, `HGETALL`, `KEYS` в SQL-редакторе; список ключей
  обрезается на 500; «создать таблицу» возвращает 400 (вместо неё — кнопка «Новый ключ» в быстрых
  действиях: имя + значение через `insertRow`); импорт CSV/JSON и стриминг для экспорта поддержаны,
  SQL-скрипты, DDL-пакеты, триггеры и `KILL` — нет; список «баз» — это номера 0…15; «схема» ключа —
  псевдо-таблица `key/type/ttl/len` без индексов, внешних ключей и триггеров.
- **MongoDB**: «запрос» — это JSON вида `{"db":"demo","collection":"users","filter":{...},"limit":50}`
  (для очистки — `"clear": true`); SQL-скрипты невозможны; внешних ключей и триггеров нет;
  `KILL` не поддерживается; DDL-пакеты, предпросмотр, откат и CRUD триггеров → 400.
- **SQLite**: пользователей/грантов/`KILL` нет; при отсутствующем файле тест подключения
  возвращает ошибку, а не «ok». DDL полностью поддерживается через автоматическую пересборку
  таблицы (`buildRebuildStatements`): `ALTER COLUMN`, добавление/удаление FK, смена PK —
  в одной транзакции с `foreign_key_check`;
  - `renameTable` требует SQLite **3.25+** (проверяется на версии файла, иначе 400);
  - индексы создаются и удаляются; контролы внешних ключей открыты, как у остальных;
  - тело триггера допускает несколько стейтментов и оборачивается в `BEGIN ... END`;
  - при откате DDL внешние ключи восстанавливаются тем же rebuild-механизмом;
  - комментарий таблицы всегда `null`.
- **MySQL / MariaDB**: DDL коммитится неявно, поэтому пакет операций не транзакционный — при
  ошибке возможен частичный результат (409 с `partial`, `applied`); триггеры не знают `INSTEAD OF`;
  `DROP INDEX` требует имени таблицы (`DROP INDEX t idx`), а `DROP TRIGGER` — только имени.
  `RENAME COLUMN` требует MySQL 8.0+ / MariaDB 10.5.2+ (версия читается из `SELECT VERSION()`,
  иначе 400 — как проверка SQLite 3.25 для `RENAME TABLE`).
- **Транзакционность DDL** — только у PostgreSQL и SQLite; откат через `/undo` покрывает
  индексы, внешние ключи и триггеры, но **не** изменения колонок и переименования (сервер не
  хранит прежние данные) — для них отдаётся 409 с DDL «до».
- **Пул соединений**: только для MySQL/MariaDB и PostgreSQL; MongoDB/SQLite/Redis открывают
  соединение на операцию.

### Прочие особенности

- Если `ENCRYPTION_KEY` изменится, существующие подключения перестанут работать
  (`Bad cipher payload`); перешифровка — `npm run rotate:key -w backend` (скрипт делает копию
  `meta.db` → `meta.db.before-encryption-rotation`).
- `settings.json` и `meta.db` лежат рядом; при монтировании тома в Docker не забудьте сохранить
  `ENCRYPTION_KEY` вместе с ними.
- `AUDIT.md` — исторический документ аудита; его разделы 1–3 описывают состояние кода
  **до** исправлений, актуальные утверждения — в разделе 0 того же файла и в этом README.
- `frontend/package.json` содержит неиспользуемые UI-зависимости (`express`, `dotenv`, `mysql2`,
  `pg`, `mongodb`, `@google/genai`, `motion`).
- Из кода удалён мёртвый хвост предыдущих итераций: `toTable` в драйвере Redis и поле `dialect`
  в `CreateTableDef` (бэкенд его игнорировал, диалект берётся из `kind` подключения).

## Troubleshooting

**`docker compose up` не стартует / «env file not found»**
Compose читает `env_file: ./backend/.env` — файл обязателен. Скопируйте `.env.example` и замените
секреты.

**Контейнер backend падает сразу с `Missing env ...` или «must be replaced in production»**
В Docker выставлен `NODE_ENV=production`, и `core/config.ts` требует настоящие `ENCRYPTION_KEY`
(64 hex), `JWT_SECRET` (без слов `dev|change|default|secret`) и `ADMIN_PASSWORD` (≥12 символов,
не `admin…/password…/testpass…/change…`). Сгенерируйте ключ:
`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.

**Не могу войти, 401 `Bad credentials`**
Администратор создаётся только при пустой таблице `users`. Если пароль в `.env` менялся после
первого запуска, он не действует — сбросьте `backend/data/meta.db` (потеряете подключения,
аудит, историю) либо заведите нового админа: временно поставьте `REQUIRE_AUTH=0`, создайте
пользователя через UI (Настройки → Пользователи) и верните `REQUIRE_AUTH=1`.

**401 `Bad token` / постоянный возврат на экран входа**
Токен протух (12 ч) или пользователь удалён/переименован/сменил роль — `isCurrentUser` сверяет
токен с `users` при каждом запросе. Выйдите и войдите заново. Слишком много попыток входа даёт
`429` (rate limit 200/мин).

**`502` / «Ошибка загрузки баз данных» после выбора подключения**
Драйвер не смог достучаться до СУБД. Проверьте кнопку «Проверить базу» в правой панели, порт
(для MariaDB в compose это **3307**, не 3306), креды и `docker compose ps` (healthcheck'и).
Для SQLite проверьте существование файла — при удалённом файле тест вернёт ошибку.

**`413 Request body is too large`**
Общий лимит JSON-тел — 1 MiB; поднят только для импорта (15 MiB, из них данные ≤10 MB). Загрузка
`.sqlite` идёт multipart'ом (до 100 MB) и лимитом не ограничена. Через nginx при `client_max_body_size`
проблем нет — проверено, что 413 приходит от backend.

**`CORS` в консоли браузера**
`CORS_ORIGIN` должен содержать origin страницы (в dev — `http://localhost:3000`,
`http://127.0.0.1:3000`). В Docker UI живёт на `:3001`, но запросы идут на тот же origin через
nginx-прокси, поэтому CORS не применяется.

**Порт занят**
В dev занят `3000` (Vite) и `3001` (backend); в Docker — `3001` (nginx) и `3002` (backend).
Проберитесь по списку портов СУБД: `3306/3307/5432/27017/6379`. Свободный порт фронта меняется
в `frontend/package.json` (`vite --port=...`), порт backend — через `PORT` в `.env`.

**Панель открывается, но пустая / «Нет подключений»**
`GET /api/connections` отдаёт пустой массив, если в `meta.db` нет записей. В Docker это ожидаемо
для свежего тома: создайте подключение через UI или залейте фикстуры `npm run seed:dbs` (это
внешние БД, а не метаданные панели).

**После смены `ENCRYPTION_KEY` подключения перестали открываться**
Используйте `npm run rotate:key -w backend -- --dry-run` (покажет, что расшифровывается),
затем с `--new-key <64hex>`. Скрипт копирует `meta.db` в `meta.db.before-encryption-rotation`.

**Импорт/экспорт «зависает» на большой таблице**
Это нормально: поток идёт батчами по 1000 строк. Увеличьте `QUERY_TIMEOUT_MS`, если упираетесь
в таймаут; при работе через nginx таймауты уже 300 с.

**Redis: «Redis db must be a number 0..N»**
Поле «Номер БД» должно быть целым числом (`0`…`15` по умолчанию). Строка `db` вместо номера → 400.

**MongoDB: «Mongo query must be JSON like …»**
В редакторе для MongoDB ожидается JSON, а не `db.users.find()`:
`{"db":"demo","collection":"users","filter":{"age":{"$gt":18}},"limit":50}`.

**Windows: `npm run clean -w frontend` не работает**
Скрипт использует `rm -rf` (нужен Git Bash). Удаляйте `frontend/dist` вручную или через PowerShell.

**Проверить, что всё собирается**
`npm run typecheck`, `npm run verify`, `npm run build`. `npm run verify` дополнительно проверяет
`docker-compose.yml` на валидность.
