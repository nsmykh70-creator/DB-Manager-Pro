# DB Panel — пошаговое руководство пользователя

Документ описывает работу в веб-панели **DB Panel** от входа до диагностики. Он рассчитан на
администратора БД, который уже получил URL панели и учётные данные (или может поднять панель сам —
см. [Приложение A](#приложение-a-поднять-панель-самостоятельно)).

Все действия описаны так, как они выглядят в интерфейсе. Названия кнопок и вкладок приведены
в русской версии интерфейса; при переключении языка (кнопка «глобус» в шапке) названия меняются,
логика — нет.

## 1. Что такое DB Panel

Единая панель для семи СУБД:

| СУБД | Что показывает панель | Особенности |
|---|---|---|
| **MySQL** | базы, таблицы, строки, схема, индексы, внешние ключи, процессы, размеры | `SHOW PROCESSLIST`, `KILL` |
| **MariaDB** | то же, что MySQL | отдельная категория, по умолчанию порт 3306 |
| **PostgreSQL** | то же + `pg_stat_activity` | только схема `public` |
| **SQLite** | один файл: таблицы, строки, схема | без сервера, без пользователей и прав |
| **MongoDB** | базы, коллекции, документы | вместо SQL — JSON-запросы |
| **Redis** | номера БД (0…15) и ключи | вместо таблиц — ключи, только 5 команд |
| **Oracle** | схема, таблицы, строки, схема, индексы, внешние ключи, триггеры, план запроса | «база» = схема = пользователь подключения, порт 1521 |

Панель ничего не копирует и не кэширует: всё, что вы видите, запрашивается у живой СУБД.
Всё, что вы делаете, попадает в целевую базу с правами того пользователя, который указан в
подключении.

## 2. Вход в панель

1. Откройте адрес панели в браузере (в Docker-развёртывании это обычно `http://localhost:3001`,
   при локальной разработке — `http://localhost:3000`).
2. Появится экран **«Войдите в панель управления»** с полями «Пользователь» и «Пароль».
3. Введите логин и пароль, нажмите **«Войти»**.

Что важно знать:

- Сессия живёт **12 часов**, после чего панель вернёт вас на экран входа.
- При неверном пароле показывается «Bad credentials». Несколько неудачных попыток подряд могут
  упереться в ограничение частоты запросов — подождите минуту.
- Если учётных данных нет, обратитесь к администратору панели (пользователю с ролью `admin`).
  Логин и пароль первого администратора задаются при развёртывании.
- Если панель запущена без обязательной авторизации, экран входа не показывается — вы сразу
  окажетесь в интерфейсе. В этом случае роль никого не ограничивает, а кнопка «Выйти» в меню
  пользователя отсутствует.
- Роль, под которой вы вошли, видна в правом верхнем углу: «иконка пользователя → логин, роль».
  Она определяет, какие действия вам доступны (см. раздел [14](#14-пользователи-панели-и-роли)).
- **Выйти** — меню пользователя справа в шапке → «Выйти».

## 3. Обзор интерфейса

Экран состоит из четырёх частей:

```
┌────────────┬──────────────────────────────────────────────┬──────────────┐
│ Левая      │  Шапка: проект · подключение · БД · тема ·   │ Правая       │
│ панель     │  язык · уведомления · настройки · профиль    │ панель       │
│            ├──────────────────────────────────────────────┤ «Информация  │
│ Подключения│  Рабочая область: вкладки Структура / SQL /  │ о сервере»   │
│ Категории  │  Поиск / Экспорт / Импорт / Операции         │ Быстрые      │
│ СУБД → БД  │                                              │ действия     │
└────────────┴──────────────────────────────────────────────┴──────────────┘
```

**Левая панель**

- Блок **«Подключения»** — все настроенные подключения. У каждого две кнопки: шестерёнка
  (изменить настройки) и корзина (удалить подключение из панели; сама база при этом остаётся).
  Для каждой базы — своя кнопка корзины **удаления базы** (системные базы `mysql`, `postgres`,
  `local` и т. п. удалить нельзя: кнопки для них не показываются).
- Блок **«Базы данных»** — категории СУБД (MySQL, MariaDB, PostgreSQL, SQLite, MongoDB, Redis, Oracle).
  Категория раскрывается и показывает базы **всех** подключений этого типа сразу.
- **Категории СУБД можно переставлять мышью и стрелками**: тяните категорию за её шапку
  или поставьте на неё курсор и нажимайте `↑` и `↓`. При перетаскивании видно полоску
  места вставки — над категорией или под ней, в зависимости от того, в какой её половине
  находится курсор. При перестановке стрелками фокус остаётся на переехавшей категории.
- **Базы внутри категории переставляются так же**: тяните строку за любую часть, кроме
  кнопок действий, или нажимайте `↑` и `↓`. Переносить базу в категорию другого типа
  нельзя — такой перенос игнорируется.
- Порядок категорий и баз сохраняется в браузере отдельно для вашего пользователя,
  переживает обновление списка и перезагрузку страницы. Кнопка **«Сбросить порядок»**
  (она появляется, только когда порядок изменён) возвращает сразу оба списка к порядку
  по умолчанию.
- Кнопки: **«Подключение»** (создать), **«Создать»** (создать базу), значок обновления (перечитать
  список баз), **«Мониторинг»**, **«Документация»**, **«Управление доступом»** (пользователи панели),
  **«Настройки»**.
- Стрелка в шапке левой панели сворачивает её в узкую полосу — рабочая область становится шире.

**Шапка**

- Слева: название проекта, активное подключение (зелёная точка = выбрано), его хост/порт и тип,
  текущая база данных.
- Справа: язык (глобус), светлая/тёмная тема, уведомления (колокольчик), настройки (шестерёнка),
  сворачивание правой панели, меню пользователя.

**Рабочая область** — вкладки **Структура**, **Панели**, **Конструктор**, **SQL**, **Поиск**,
**Экспорт**, **Импорт**, **Операции**. На вкладке «Структура» дополнительно есть список
таблиц, журнал операций и компактный SQL-редактор. Вкладка «Панели» собирает таблицы,
журнал, SQL-редактор, поиск и конструктор на сетке, где их можно переставлять и растягивать
(см. раздел 16-ter). Экран «Мониторинг» устроен так же.

**Правая панель** — «Информация о сервере»: версия, количество баз, соединения, время работы,
медленные запросы, список баз с размерами, список процессов (с кнопкой `KILL` у администратора),
блок «Пользователи БД», быстрые действия: «Новая БД», «Новая таблица», «Импорт», «Экспорт»,
«Проверить базу», «Резервное копирование».

**Оконный режим** (кнопка «Оконный режим» и оранжевые «ёлочки»): список таблиц, журнал и
SQL-редактор открепляются в отдельные перетаскиваемые окна с панелью задач внизу (каскад, плитка,
свернуть все, развернуть все, закрепить обратно в сетку).

## 4. Подключение к базе данных

### 4.1. Создать подключение

1. Левая панель → **«Подключение»**.
2. Заполните форму:

| Поле | Значение |
|---|---|
| Тип подключения | MySQL / MariaDB / PostgreSQL / MongoDB / Redis / SQLite / Oracle |
| Название | Своё имя подключения, обязательно. Например `production-postgres` |
| Хост | `localhost` или адрес сервера БД |
| Порт | подставляется автоматически: 3306 / 3306 / 5432 / 27017 / 6379 / 1521. Для MariaDB в docker-окружении проекта это **3307** |
| База данных (для Redis — «Номер БД», для Oracle — имя сервиса) | необязательно; для Redis — целое число, например `0`. Номер можно оставить пустым — будет `0`. Для Oracle пустое поле даёт EZ-подключение к инстансу, а заполненное используется как `SERVICE_NAME` |
| Пользователь | необязательно |
| Пароль | необязательно |
| Только чтение | галочка — панель запретит любые изменения в этой базе |

Для **SQLite** вместо хоста/порта/пользователя одно поле — **«Путь к файлу»**, например
`data/local.sqlite` или `sqlite/app.sqlite`. Относительный путь считается от каталога, где лежит
`meta.db` (в Docker — `/data`). Если указать `createDatabase`, пустой файл будет создан.

> **Только прямые слэши.** Путь с обратными слэшами (`C:\data\app.db`) на Linux/Docker-сервере
> отклоняется с ошибкой `filePath must use forward slashes on this platform`: там обратный слэш —
> часть имени файла, и без проверки панель создавала файл-мусор вроде
> `/data/C:\data\app.db`, после чего любой запрос к нему падал с «no such table».
> На Windows-сервере такой путь автоматически приводится к `C:/data/app.db`.

3. **«Создать»**. Подключение появится в блоке «Подключения» и станет активным; панель сразу
   попробует загрузить список баз.

> **Важно про хост, если панель запущена в Docker.** Backend обращается к СУБД изнутри своего
> контейнера, поэтому `localhost` в поле «Хост» укажет на сам backend, а не на сервис БД, и
> панель вернёт `502 Bad Gateway` на `/status`, `/dbusers` и списки таблиц. В docker-окружении
> проекта указывайте имя сервиса: `mysql`, `mariadb`, `postgres`, `mongo`, `redis`,
> `oracle`. Если СУБД запущена на хосте машины, а панель — в контейнере, нужен
> `host.docker.internal`. Локальный запуск backend на машине, наоборот, требует
> `127.0.0.1` и опубликованных портов (3306 / 3307 / 5432 / 27017 / 6379 / 1521).
> Быстрая проверка — «Проверить подключение».

### 4.2. Проверить подключение

Правая панель → **«Проверить базу»**. Всплывающее уведомление покажет
`OK (N мс)` или текст ошибки. Проверка не зависит от существования «базы по умолчанию» —
тестируется сам сервер. Именно сюда стоит идти первым, если в консоли браузера появились
`502 Bad Gateway`: почти всегда это неверный хост (см. врезку выше) или не запущенная СУБД.

### 4.3. Изменить подключение

Шестерёнка у подключения в левой панели. Можно поменять название, хост, порт, базу, пользователя,
пароль, путь к файлу SQLite и флаг «Только чтение». **Правку может выполнить только администратор.**
Чтобы сменить пароль, введите новый — пустое поле означает «оставить прежний».

### 4.4. Удалить подключение

Корзина у подключения → подтверждение. Удаляется **только запись в панели**, сама база и её данные
остаются. Операция доступна только администратору; для подключения в режиме «только чтение»
сервер вернёт отказ.

Если подключение удалили в другой вкладке (или его пересоздали с новым идентификатором), текущая
вкладка это заметит: выбор сбросится, список подключений обновится, а в уведомлениях появится
«Подключение удалено в другой вкладке». Перезагружать страницу вручную не нужно.

Чтобы удалить саму базу данных, используйте корзину у конкретной базы в левой панели (раздел 5.3)
или удалите подключение с параметром «физического удаления» — это делает только администратор
через API, в интерфейсе отдельной кнопки для этого нет.

## 5. Создание базы данных

### 5.1. Создать

Левая панель → **«Создать»** (или правая панель → «Новая БД»).

1. **Категория СУБД** — совпадает с типом подключения.
2. **Подключение** — из списка подключений этой категории.
3. **Имя базы данных**. Правила **разные для разных СУБД**, и подсказка под полем
   меняется при переключении категории:

   | СУБД | длина | что можно |
   |---|---|---|
   | MySQL / MariaDB | до 64 | латиница, цифры, `_` и `$` |
   | PostgreSQL | до 63 | начинается с буквы или `_`, дальше латиница, цифры, `_`, `$` |
   | MongoDB | до 63 | латиница, цифры, дефис и `_`; не может начинаться с `system.` |
   | SQLite | до 64 | латиница, цифры, дефис и `_` — имя станет именем файла |
   | Redis | до 64 | набор ключей: допускаются точка, дефис и двоеточие |

   Проверка выполняется **в форме**, до отправки: под полем появляется подсказка с
   правилом, а кнопка «Создать» остаётся неактивной, пока имя некорректно.

   Почему ограничения такие: имя попадает в DDL, в путь файла SQLite и в идентификаторы
   MongoDB, где точка и `$` имеют особый смысл. Поэтому панель отклоняет такое имя сразу
   и объясняет, что именно не так, вместо ошибки от сервера базы данных.

   Пробелы по краям панель обрезает сама: `  shop  ` превратится в `shop`.
4. **«Создать»**.

Что происходит под капотом и чего ждать:

| Тип | Результат |
|---|---|
| MySQL / MariaDB | `CREATE DATABASE ... CHARACTER SET utf8mb4` |
| PostgreSQL | `CREATE DATABASE` через служебную базу `postgres` |
| MongoDB | база материализуется служебной коллекцией (MongoDB создаёт базы лениво) |
| SQLite | создаётся файл `<имя>.sqlite` рядом с файлом существующего SQLite-подключения и заводится **отдельное подключение** |
| Redis | отказ: «В Redis нет баз данных — используйте номер БД 0..15» |

Права на создание БД определяются пользователем подключения (нужны `CREATE`/`CREATEDB`).
Ошибка прав придёт с текстом драйвера, например «Не удалось создать БД в MySQL: Access denied».

Две частые ситуации с понятным ответом вместо ошибки:

- **Чтение из «чужой» базы работает.** Если база с дефисом в имени (`my-db`, `read-me-1`)
  была создана на сервере мимо панели, панель её покажет и даст открыть: при чтении имя
  проверяется мягче, чем при создании. Ошибка `Bad database` означала бы обратное — такую
  базу просто нельзя было бы открыть.
- **«База уже существует»** — панель скажет об этом до обращения к СУБД.
- **MongoDB: имя отличается от существующего только регистром** (`shop` и `Shop`) —
  MongoDB такие базы считает одинаковыми, поэтому панель отвечает
  «нельзя создать `Shop`: база `shop` отличается только регистром», а не ошибкой сервера.


### 5.2. Выбрать базу

Клик по названию базы в левой панели. Имя базы также показано в шапке. Все последующие действия
(таблицы, запросы, экспорт, бэкап) применяются к выбранной базе.

### 5.3. Удалить базу

Корзина у названия базы в левой панели → подтверждение «Это действие необратимо».
Доступно **только администратору**. Системные базы защищены и удалить их нельзя:
MySQL/MariaDB — `information_schema`, `mysql`, `performance_schema`, `sys`;
PostgreSQL — `postgres`, `template0`, `template1`; MongoDB — `admin`, `config`, `local`.
Для SQLite удаление файла заодно удаляет и подключение (кроме подключений с суффиксом
`(Faraja)`).

У **Redis** корзины нет: там «база» — это номер 0…15, отдельной сущности для удаления не
существует. Стираются только ключи конкретной базы (команда `FLUSHDB`), панель такую команду не
выполняет — иначе это выглядело бы как «удалить базу», а стирало бы данные целиком.

## 6. Работа с таблицами

Карточка открытой таблицы состоит из семи вкладок: **Структура**, **Индексы**, **Связи**,
**Привилегии**, **Триггеры**, **Данные**, **SQL**. Первые три — это конструктор структуры
(колонки, индексы, внешние ключи), четвёртая — права, пятая — триггеры, последние две — работа с
данными и произвольный SQL. В шапке карточки есть общие для всех вкладок кнопки: «Добавить»
(строка), «SQL», **«Откатить DDL»**, **«Откатить данные»**, «Клонировать» (только
MySQL/MariaDB) и «Экспорт».

Порядок работы с DDL простой: правьте структуру на нужной вкладке → панель показывает SQL перед
применением ([6.7](#67-предпросмотр-и-применение-ddl)) → если что-то пошло не так, жмите
**«Откатить DDL»** ([6.8](#68-откатить-ddl)).

### 6.1. Список таблиц

Вкладка **«Структура»**, карточка «Таблицы базы данных»:

- поле «Поиск таблиц…» фильтрует список по подстроке имени;
- постраничная навигация, размер страницы 25 / 50 / 100 (выборка на клиенте, сервер отдаёт полный
  список имён);
- галочки слева — массовые операции над выбранными таблицами: «Экспорт» (все в CSV),
  «Очистить», «Удалить» (последние две — только для изменяемого подключения и не для `readonly`);
- кнопки в строке таблицы: «глаз» — открыть данные, «таблица» — открыть структуру,
  «лупа» — подставить `SELECT * ... LIMIT 50` в SQL-редактор, «+» — подставить `INSERT`
  (только для SQL-баз), «ластик» — очистить (`DELETE FROM ...`, без `WHERE`),
  «корзина» — удалить таблицу, «ёлочка вверх» — открыть таблицу в отдельном окне.

Массовые «Очистить» и «Удалить» спрашивают подтверждение с перечислением таблиц и показывают
отчёт об успехах и ошибках по каждой таблице.

### 6.2. Создать таблицу

На вкладке **«Структура»** нажмите кнопку **«Создать таблицу»** в заголовке над списком таблиц
(или правая панель → «Новая таблица»). Откроется окно **«Конструктор создания таблицы»**.

1. **Целевая СУБД** — в открытой базе диалект зафиксирован и показан названием, переключать его
   нельзя: конструктор всегда пишет SQL под тип активного подключения.
2. **Имя таблицы** — буквы (латиница и кириллица), цифры, подчёркивание. Кавычки, точки и
   двоеточия запрещены: панель сама обернёт имя в кавычки диалекта.
3. **Поля таблицы** — по одному полю в строке. Строка добавляется кнопкой
   **«Добавить ещё одно поле»** и удаляется корзиной в этой же строке. Заголовок
   «Поля таблицы (N)» показывает текущее число полей, подпись под таблицей — состав первичного ключа.
4. Заполните столбцы строки:

   | Столбец | Что задаёт | Особенности |
   |---|---|---|
   | **PK** (ключ слева) | первичный ключ | клик по ключу назначает и снимает PK; строка с PK подсвечивается |
   | **Имя поля** | имя колонки | обязательное; имена должны различаться в пределах таблицы |
   | **Тип (СУБД)** | тип из списка диалекта | список подставляется по активной СУБД |
   | **Длина** | размер для `VARCHAR`/`CHAR`, точность для `DECIMAL`/`NUMERIC` | для типов без параметра поле игнорируется |
   | **Null** | разрешено ли `NULL` | снятая галочка = `NOT NULL`; у поля с PK галочка заблокирована |
   | **По умолчанию** | `DEFAULT` | подсказки под полем — типичные значения для диалекта |
   | **Автоинкремент** | автонарастающий счётчик | доступен только для поля с PK |

5. **«Создать таблицу»** — панель собирает `CREATE TABLE` и отправляет его в выбранную базу.
   Внизу окна перед применением показывается предпросмотр определения колонки в диалекте целевой
   СУБД, поэтому результат можно проверить глазами до отправки.

Ограничения конструктора:

- от 1 до 200 колонок;
- типы только из allowlist диалекта, а не произвольные строки. Для MySQL/MariaDB это `INT`,
  `INTEGER`, `BIGINT`, `TINYINT`, `SMALLINT`, `MEDIUMINT`, `VARCHAR`, `CHAR`, `TEXT`, `MEDIUMTEXT`,
  `LONGTEXT`, `DATETIME`, `TIMESTAMP`, `DATE`, `TIME`, `YEAR`, `DECIMAL`, `FLOAT`, `DOUBLE`,
  `BOOLEAN`, `BOOL`, `JSON`, `BLOB`, `MEDIUMBLOB`, `LONGBLOB`. Для PostgreSQL — `integer`, `int`,
  `bigint`, `smallint`, `serial`, `bigserial`, `smallserial`, `numeric`, `real`,
  `double precision`, `varchar`, `char`, `text`, `boolean`, `timestamp`, `timestamptz`, `date`,
  `time`, `jsonb`, `json`, `bytea`. Для SQLite — `INTEGER`, `TEXT`, `REAL`, `BLOB`, `NUMERIC`,
  `VARCHAR`, `BOOLEAN`, `DATETIME`, `DATE`. Типы вроде `ENUM`, `SET`, `GEOMETRY` или `UUID`
  (в списке PostgreSQL его нет) придётся добавить через SQL-редактор;
- автоинкремент требует целочисленного типа: `AUTO_INCREMENT` (MySQL/MariaDB),
  `SERIAL`/`BIGSERIAL` (PostgreSQL), `INTEGER PRIMARY KEY AUTOINCREMENT` (SQLite);
- значение по умолчанию — литерал в кавычках, число, `NULL`/`TRUE`/`FALSE` либо
  `CURRENT_TIMESTAMP` / `CURRENT_DATE` / `CURRENT_TIME`. Выражения и подзапросы в `DEFAULT`
  панель не принимает;
- составной первичный ключ конструктор не собирает: если отметить PK у двух полей, панель
  сформирует два `PRIMARY KEY` подряд и сервер отклонит такой `CREATE TABLE`. Составной PK
  задаётся только через SQL-редактор (`PRIMARY KEY (a, b)`), в конструкторе отмечайте одну колонку;
- для MongoDB создаётся коллекция (типы колонок на сервер не влияют — коллекции schemaless);
- для Redis кнопка недоступна: у Redis нет таблиц.

#### «Только чтение» и «Дополнительно» в редакторе поля

В редакторе поля (см. [6.3](#63-изменить-таблицу)) под предпросмотром есть блок
**«Дополнительно (с сервера, только чтение)»**. Это не ошибка и не запрет на изменение колонки:

- значение берётся у сервера — это колонка `Extra` в таблице структуры: `AUTO_INCREMENT`,
  `ON UPDATE CURRENT_TIMESTAMP`, `GENERATED ...`, `INVISIBLE`, `COLLATE ...` и прочие диалектные
  хвосты, которые СУБД сама добавляет к определению колонки;
- пометить «только чтение» означает, что **править его в панели нельзя**: произвольные диалектные
  выражения API конструктора не принимает, поэтому такой атрибут можно изменить только через
  SQL-редактор;
- к «только чтение» у подключения (галочка в настройках подключения) это отношения не имеет — см.
  [4.1](#41-создать-подключение) и [14.3](#143-что-может-каждая-роль).

#### Чего в конструкторе нет

Под полями окна есть прямой дисклеймер: **параметры `engine`, `collation` и дополнительные
атрибуты таблицы не поддерживаются API конструктора**. Это осознанное ограничение, а не ошибка:

- `ENGINE=InnoDB`, `CHARSET`, `COLLATE` уровня таблицы конструктор не формирует — таблица
  создаётся с настройками по умолчанию, которые действуют на сервере (для MySQL обычно InnoDB
  и `utf8mb4_..._ci`);
- `COLLATE` на уровне колонки конструктор тоже не задаёт;
- если конкретные `ENGINE` или `COLLATE` критичны, создайте таблицу через SQL-редактор
  (вкладка «SQL») — там можно написать любой `CREATE TABLE` вручную.

### 6.3. Изменить таблицу

Откройте таблицу (клик по имени) → вкладка **«Структура»**:

- **«Добавить колонку»** — новая колонка;
- **карандаш** у колонки — правка: переименование (`renameColumn`), тип, `NULL`, `DEFAULT`,
  признак `PK`;
- **корзина** у колонки — удаление;
- фильтр «Фильтр колонок» — скрывает несовпадающие колонки.

Что именно можно изменить у существующей колонки:

| Что меняем | Как это выглядит для администратора |
|---|---|
| **Имя** | новое имя в поле «Имя поля»; панель отправляет `RENAME COLUMN` |
| **Тип** (с длиной) | выбирается из списка диалекта; `VARCHAR`/`CHAR` требуют заполненной длины |
| **Nullable** | список «NULL (Разрешить пустоту)»: «Да (NULL)» или «Нет (NOT NULL)» |
| **Default** | поле «По умолчанию» + кнопки-подсказки с типичными значениями диалекта |
| **PK** | кнопка «Primary Key (PK)»: включение даёт `ADD PRIMARY KEY`, снятие — `DROP PRIMARY KEY` |
| **Дополнительно** | только чтение: значение приходит с сервера, см. [6.2](#62-создать-таблицу) |

Панель сравнивает старую и новую колонку и формирует пакет операций: если изменились только
`NULL` или `DEFAULT`, тип трогать не нужно; если добавился или снялся PK, к пакету
добавляется операция `ADD PRIMARY KEY` / `DROP PRIMARY KEY`. Перед отправкой пакет
предпросматривается — см. [6.7](#67-предпросмотр-и-применение-ddl).

Где это работает, а где нет:

| СУБД | Правка колонки |
|---|---|
| MySQL / MariaDB | полностью: `MODIFY COLUMN` одним стейтментом, `DROP PRIMARY KEY` / `ADD PRIMARY KEY`, `AUTO_INCREMENT` |
| PostgreSQL | тип, `NULL`, `DEFAULT`, `PK` — через `ALTER TABLE ... ALTER COLUMN` (тип идёт с `USING`) |
| SQLite | всё поддерживается через автоматическую пересборку таблицы (см. ниже) |
| MongoDB | недоступно: коллекции schemaless |
| Redis | недоступно |

SQLite сам не умеет менять тип колонки, `NULL`/`DEFAULT`, первичный ключ и внешние ключи
без пересоздания таблицы, поэтому панель делает это за вас автоматически: строит новую таблицу
с нужной структурой, переносит данные (`INSERT INTO ... SELECT`, переименования колонок
учитываются), удаляет старую, переименовывает новую и возвращает на место индексы и триггеры.
Предпросмотр показывает ровно этот скрипт (первые строки — `DROP TABLE IF EXISTS
"_dbpanel_rebuild_..."`), выполняется всё в одной транзакции с проверкой `foreign_key_check`.
Ручное пересоздание через SQL-редактор больше не требуется.

В PostgreSQL изменение колонки разбивается на несколько стейтментов (`ALTER COLUMN ... TYPE ...
USING ...`, `SET/DROP NOT NULL`, `SET/DROP DEFAULT`) и выполняется в одной транзакции — если хотя бы
один не прошёл, не применится ни один. Имя ограничения первичного ключа для `DROP PRIMARY KEY`
панель спрашивает у каталога (`pg_constraint`), а не угадывает по шаблону `<таблица>_pkey`: если
ограничение переименовали вручную, откат всё равно сработает правильно.

В таблицах структуры `Extra` для MySQL/MariaDB — это колонка, куда попадают `AUTO_INCREMENT`,
`ON UPDATE CURRENT_TIMESTAMP`, `STORED/VIRTUAL GENERATED` и т. п. (список — в конструкторе).

### 6.4. Вкладка «Индексы»

Вкладка показывает все индексы таблицы: имя (у индекса первичного ключа — пометка `PK`), тип,
признак уникальности и колонки. Форма создания находится над таблицей и состоит из:

| Поле | Что задаёт | Правила |
|---|---|---|
| **Имя** | имя индекса | обязательное, например `idx_orders_user_id`; допускаются буквы, цифры, подчёркивание |
| **Колонки** | список колонок индекса | множественный выбор, от 1 до 16; порядок выбора = порядок в индексе (составной индекс) |
| **Уникальный** | `UNIQUE` | запрет дублей в этих колонках; включите, если значения должны быть уникальны |
| **Тип** | метод доступа | необязательное поле, например `BTREE`, `HASH`, `FULLTEXT`, `SPATIAL`, а для PostgreSQL ещё `GIN`, `GIST`, `BRIN`. Пустое поле = тип по умолчанию сервера |
| **«Создать индекс»** | отправка | предпросмотр DDL показывается до применения |

Список колонок в форме — это множественный выбор: кликом или `Ctrl` добавьте нужные колонки, они
появятся под полем в порядке выбора. Чтобы заменить уже выбранные колонки на другие, сначала
нажмите **«Сбросить колонки»** (ссылка под списком), иначе новые добавятся к прежним.

Диалектные правила для типа индекса:

- `GIN`, `GIST`, `BRIN` — только PostgreSQL, для остальных СУБД панель вернёт 400 с текстом
  «Index type ... is PostgreSQL-only»;
- `FULLTEXT` и `SPATIAL` — только MySQL/MariaDB, и они не совмещаются с `UNIQUE`;
- у SQLite индекса нет типа вообще: поле «Тип» должно быть пустым, иначе панель ответит
  «SQLite indexes have no type»;
- частичный индекс (`CREATE INDEX ... WHERE ...`) поддерживается только PostgreSQL и в панели
  не задаётся — пишите его в SQL-редакторе.

**Удаление индекса** — корзина в строке индекса → подтверждение → `DROP INDEX`
(`DROP INDEX ... ON ...` для MySQL/MariaDB, где индекс принадлежит таблице).

**Почему PRIMARY удалить нельзя.** У индекса, созданного для первичного ключа, в панели нет кнопки
удаления, и при попытке панель отвечает подсказкой: «Индекс PRIMARY KEY удаляется вместе с
первичным ключом». Причина в самой СУБД: индекс первичного ключа — это не отдельный объект, а
обязательная часть определения `PRIMARY KEY`. Удалить его можно только вместе с ключом, а для
первичного ключа нужен отдельный шаг ([6.3](#63-изменить-таблицу)) плюс соблюдение ограничений
диалекта (в SQLite и этого недостаточно — нужна пересозданная таблица). Поэтому панель не
предлагает действие, которое сервер всё равно отклонит.

### 6.5. Вкладка «Связи»

Вкладка **«Связи»** показывает два вида ссылок: собственные внешние ключи таблицы (у них есть имя
ограничения, колонки, таблица-ссылка и правила `ON DELETE` / `ON UPDATE`) и **входящие ссылки** —
внешние ключи других таблиц, которые ссылаются на эту (в строке они помечены словом «входящий» и
редактировать их нельзя, они принадлежат другой таблице).

Форма создания внешнего ключа:

| Поле | Что задаёт | Правила |
|---|---|---|
| **Имя** | имя ограничения | для MySQL/MariaDB и PostgreSQL обязательно (например `fk_orders_user_id`); панель подставляет его в `ADD CONSTRAINT` |
| **Колонки** | колонки этой таблицы | множественный выбор, от 1; порядок выбора = порядок в ключе |
| **Ссылается на** | имя таблицы-ссылки | обязательно, вводится вручную (например `users`) |
| **Колонки ref** | колонки в таблице-ссылке | вводятся через запятую, например `id`; число значений должно совпадать с числом колонок |
| **ON DELETE** | правило при удалении строки-родителя | `CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`, `SET DEFAULT` или «—» (не задавать) |
| **ON UPDATE** | правило при изменении строки-родителя | те же значения |
| **«Создать внешний ключ»** | отправка | перед применением показывается SQL |

Значения правил ссылочной целостности:

| Правило | Что произойдёт |
|---|---|
| `CASCADE` | связанные строки удаляются (или обновляются) вместе с родительской |
| `SET NULL` | в связанных строках проставляется `NULL` — колонка должна быть nullable |
| `RESTRICT` | действие запрещается, пока есть зависимые строки |
| `NO ACTION` | проверка откладывается до конца транзакции (обычно то же, что `RESTRICT`) |
| `SET DEFAULT` | подставляется значение по умолчанию |

Значение правила в панель попадает не свободным текстом, а из белого списка. Если вписать что-то
другое, backend ответит 400 с текстом `Bad FK action: ...` и подсказкой со списком допустимых
значений — это защита от опечаток вроде `ON DELETE CASCAD`.

**Удаление внешнего ключа** — корзина в строке связи → подтверждение:
`ALTER TABLE ... DROP FOREIGN KEY` (MySQL/MariaDB) или `ALTER TABLE ... DROP CONSTRAINT`
(PostgreSQL).

> **Важно: SQLite не поддерживает добавление FK к существующей таблице.**
> У SQLite нет `ALTER TABLE ... ADD CONSTRAINT`, поэтому ни форма создания связи, ни кнопки
> удаления в панели не показываются, а вместо них выводится объяснение: внешний ключ задаётся
> только в `CREATE TABLE` (вкладка «SQL»). Удаление FK в SQLite тоже требует пересоздать таблицу.
> Практический порядок для SQLite: посмотрите `PRAGMA foreign_key_list(таблица)` в SQL-редакторе,
> затем пересоздайте таблицу с нужным набором ограничений.

### 6.6. Вкладка «Триггеры»

Вкладка показывает имя триггера, момент срабатывания («Когда»), событие и тело. Создать и удалить
триггер можно прямо из панели; у MongoDB и Redis триггеров нет вообще, там вкладка показывает
сообщение, что драйвер их не поддерживает.

Форма создания:

| Поле | Что задаёт | Правила |
|---|---|---|
| **Имя** | имя триггера | обязательное, например `trg_orders_audit` |
| **Когда** | момент срабатывания | `BEFORE`, `AFTER`, а для PostgreSQL и SQLite ещё `INSTEAD OF`; у MySQL/MariaDB — только `BEFORE` и `AFTER` |
| **Событие** | операция | `INSERT`, `UPDATE` или `DELETE` |
| **Тело** | см. ниже | для PostgreSQL — **имя уже созданной функции**, для MySQL/MariaDB и SQLite — SQL |
| **«Создать триггер»** | отправка | результат пишется в журнал запросов |

Тело триггера — единственное место, где в DDL попадает свободный SQL, поэтому требования к нему
различаются по диалектам:

**PostgreSQL** — в поле нужно указать **имя функции, созданной заранее**. Панель собирает
`CREATE TRIGGER ... EXECUTE FUNCTION public.<имя>()`; сам SQL триггера в этом поле писать нельзя.
Сначала создайте функцию через SQL-редактор, затем укажите её имя:

```sql
CREATE FUNCTION trg_orders_touch() RETURNS trigger AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

Затем в панели: имя `trg_orders_touch`, `BEFORE`, `UPDATE`, тело — `trg_orders_touch`.
Если функции нет, сервер ответит ошибкой, а панель покажет её текст.

**MySQL / MariaDB** — тело это **один** SQL-стейтмент, который выполняется для каждой строки
(`FOR EACH ROW`), например `SET @x = NEW.name` или `INSERT INTO log (msg) VALUES (NEW.name)`.
Несколько стейтментов через `;` здесь запрещены: панель вернёт
`Trigger body must be a single statement ...`.

**SQLite** — тело может содержать **несколько** стейтментов, разделённых `;`. `BEGIN` и `END`
писать не нужно: панель сама обернёт тело в `BEGIN ... END` (если вы написали `BEGIN` сами,
обёртка не добавится). Длина тела — до 10 КБ.

```
UPDATE orders SET updated_at = CURRENT_TIMESTAMP WHERE id = NEW.id;
INSERT INTO orders_log (order_id, action) VALUES (NEW.id, 'update');
```

**Удаление триггера** — корзина в строке триггера → подтверждение:
`DROP TRIGGER` (для PostgreSQL `DROP TRIGGER ... ON таблица` требует имени таблицы, панель
подставляет текущую).

### 6.7. Предпросмотр и применение DDL

Любое изменение структуры (индекс, внешний ключ, колонка, PK) панель сначала **предпросматривает**,
и только потом применяет:

1. Панель просит backend построить SQL для пакета операций — ровно те же стейтменты, которые затем
   будут выполнены. Предпросмотр ничего не меняет в базе.
2. Показывается панель **«DDL применён — SQL, который выполнила панель»** с самими стейтментами и
   строкой-подсказкой о транзакционности. Кнопка «Скрыть» убирает блок.
3. После успешного применения структура и данные перечитываются, а пакет попадает в журнал
   запросов и аудит.
4. Если предпросмотр не удался, операция **не применяется** — панель показывает ошибку, чтобы вы
   не отправили заведомо нерабочий DDL.

Транзакционность зависит от СУБД, и об этом честно предупреждает подсказка в панели:

| СУБД | Поведение DDL-пакета | Что видит администратор |
|---|---|---|
| PostgreSQL | пакет выполняется в одной транзакции (`BEGIN` … `COMMIT`); ошибка откатывает всё целиком | зелёная подсказка «выполняется в одной транзакции: при ошибке откатывается целиком» |
| SQLite | пакет выполняется в транзакции, ошибка откатывает всё целиком | то же зелёное сообщение |
| MySQL / MariaDB | DDL коммитится неявно, отката нет: уже выполненные операции остаются | жёлтое предупреждение «DDL этой СУБД коммитится неявно и не откатывается. Проверьте скрипт перед применением» |

Если в MySQL/MariaDB пакет из нескольких операций оборвался на середине, backend отвечает
**409** с текстом вида `Applied partially (2 of 5 ops). MySQL/MariaDB commit DDL implicitly and
cannot roll back: fix it manually or re-apply.` Что делать:

1. открыть вкладку **«Структура»** и **«Индексы»**/**«Связи»** таблицы и сравнить с ожиданием —
   какие объекты реально созданы, а какие нет;
2. посмотреть применённые стейтменты в панели DDL и в **журнале запросов** (см. раздел 16) — там
   записан точный SQL каждой операции;
3. довести таблицу до нужного состояния точечными операциями из панели или вручную через
   SQL-редактор, каждую отдельным пакетом;
4. если изменения нужны «как было» — воспользуйтесь кнопкой **«Откатить DDL»** (см. 6.8): индексы,
   внешние ключи и триггеры она вернёт автоматически.

Обратите внимание на формулировку про откат: откат — это не отмена транзакции, а **восстановление
объектов, попавших в снапшот**. Поэтому сообщение «применено частично» не означает «ничего не
сделано»: сначала сверьте фактическое состояние таблицы.

### 6.8. «Откатить DDL»

Кнопка **«Откатить DDL»** в шапке карточки таблицы отменяет **последний** пакет изменения
структуры этой таблицы. Перед откатом панель спрашивает подтверждение, прямо называя, что именно
вернётся: удалённые индексы, внешние ключи и триггеры.

Как это работает:

- перед каждым DDL-пакетом панель читает схему таблицы и сохраняет снапшот: плоский список
  значимых строк схемы (колонки, индексы, внешние ключи, **вместе с телами триггеров**) и полный
  `CREATE TABLE` этой таблицы;
- снапшот лежит в служебной базе панели (`meta.db`) в таблице `design_snapshots`. Хранится
  **только последний пакет на каждую таблицу**: предыдущие снапшоты удаляются, поэтому откат всегда
  относится к самой последней операции, а не к произвольному моменту времени;
- при откате панель сравнивает текущую схему со снапшотом и восстанавливает то, чего больше нет.

Что откат **умеет** восстанавливать:

- удалённые **индексы** (включая уникальность);
- удалённые **внешние ключи** с их `ON DELETE` / `ON UPDATE`;
- удалённые **триггеры** — с полным телом, поэтому они пересоздаются рабочими.

Что откат **не умеет**:

- изменения **колонок**: добавление, удаление, переименование, смену типа, `NULL`, `DEFAULT`;
- **переименование таблицы**;
- изменение состава **первичного ключа**.

Причина простая: сервер не хранит прежние значения колонок, а данные таблицы откат не
восстанавливает. Поэтому в этом случае панель **не сообщает об успехе**: она показывает блок с
текстом «Откат невозможен: последний пакет менял колонки» и **DDL до изменения** — полный
`CREATE TABLE` из снапшота. Его можно скопировать и выполнить в SQL-редакторе, восстановив структуру
вручную, а данные перенести экспортом.

Дополнительные ограничения:

- в SQLite внешние ключи при откате **не** восстанавливаются: `ALTER TABLE ADD CONSTRAINT`
  не поддерживается, панель сообщит, что нужна пересозданная таблица;
- если в текущей схеме есть всё, что было в снапшоте, откат ответит «Nothing to restore»;
- если таблица удалена целиком, откат недоступен: «Table ... is gone: nothing to undo»;
- если снапшота нет (например, схему не удалось прочитать перед изменением), откат ответит 404
  «No DDL snapshot to undo for this table»;
- откат недоступен для подключения в режиме «только чтение» и для роли `readonly` — backend
  отвечает 403;
- откат меняет только структуру. Данные, которые успели измениться между двумя пакетами, он не
  трогает, поэтому после отката сверьте таблицу.

Откат — не отмена: он восстанавливает объекты из снапшота, а не откатывает транзакцию. Поэтому
после отката всегда сверяйте фактическое состояние таблицы с ожидаемым.

### 6.9. Удалить таблицу

Корзина в строке таблицы на вкладке «Структура» или корзина в шапке карточки открытой таблицы →
подтверждение. Необратимо. Только для изменяемого подключения и не для роли `readonly`.
Для SQLite выполняется `DROP TABLE`, для MongoDB — `drop()` коллекции, для Redis — `DEL` ключа.

### 6.10. Клонирование таблицы

В открытой таблице кнопка **«Клонировать»** (только MySQL/MariaDB) предлагает имя копии
(по умолчанию `<таблица>_copy`) и выполняет `CREATE TABLE ... LIKE ...`.
Данные в копию **не** переносятся — копируется только структура.

Клон появляется в списке таблиц сразу, перезагружать страницу не нужно. То же самое работает
для `CREATE TABLE`, `DROP TABLE` и `ALTER TABLE`, выполненных в SQL-вкладке: список
перечитывается сам.

## 7. Просмотр данных и CRUD строк

### 7.1. Вкладка «Данные»

Клик по имени таблицы → вкладка **«Данные»** (или кнопка «глаз» в списке таблиц).

- Вверху: счётчик строк на странице (и приблизительный итог, если драйвер его отдаёт) и пометка
  «усечено», если страница неполная.
- Кнопки **«Добавить запись»** и **«Обновить»**.
- Размер страницы: 25 / 50 / 100 / 200 (сервер отдаёт максимум 500 за раз), стрелки «‹ ›».
- Значения `NULL` показываются словом `NULL`, объекты (JSON, документы) — в виде JSON.

### 7.2. Фильтр и сортировка

В самой таблице вкладки **«Структура»** есть поле **«Фильтр колонок»** — оно скрывает колонки,
имя которых не содержит введённую подстроку. Это фильтр колонок, а не строк.

Фильтрация и сортировка **строк** поддерживаются API и доступны, когда вы запрашиваете данные
напрямую:

```
GET /api/connections/<connId>/<db>/<table>/rows?page=1&pageSize=200&sort=id:desc&filter=age%3E30
```

Язык фильтра:

| Форма | Смысл |
|---|---|
| `col=5` | равно (число сравнивается как число) |
| `col!=5`, `col<>5` | не равно |
| `col>5`, `col>=5`, `col<5`, `col<=5` | сравнения |
| `col~ann` | содержит подстроку (MySQL/PG/SQLite — `LIKE`, MongoDB — регистронезависимый regex) |
| `col^Ann` | начинается с |
| `col$nn` | заканчивается на |
| `col=1 AND age>30` | несколько условий, до 20 |

Значение можно взять в кавычках: `name='Ann Smith'`. Спецсимволы внутри значения запрещены
(кавычки, скобки, точки с запятой), SQL-мусор отбрасывается — вместо тихого «ничего не найдено»
панель вернёт понятную ошибку. Максимум: 500 символов в фильтре, 200 символов в значении.
Чтобы отфильтровать данные без API, используйте поиск по базе (раздел 9) или SQL с `WHERE`.

### 7.3. Добавить запись

**«Добавить запись»** → форма по колонкам. Автоинкрементные и первичные ключи заполнять не нужно.
Пустые поля не отправляются. Требование — заполнить хотя бы одно поле. После сохранения список
перечитывается.

### 7.4. Изменить запись

Карандаш в строке → форма. Панель сама вычисляет, что изменилось, и отправляет только
изменённые поля; пустая строка сохраняется как `NULL`. Условие `WHERE` строится по первичному
ключу (а если PK определить не удалось — по всем простым значениям строки). Если изменений нет,
вы увидите уведомление «Изменений нет».

### 7.5. Удалить запись

Корзина в строке → подтверждение «Удалить запись?». Если сервер сообщил, что удалено 0 строк,
вы увидите «Запись не найдена» — вероятно, строку уже удалили из другого окна.

### 7.6. Конфликт правок: «изменили, пока вы правили»

Если строку изменили в другой вкладке, панель **не затрёт** чужое изменение.
При сохранении она передаёт серверу значения, которые видела при открытии, и
сервер проверяет их вместе с ключом. Если значения уже не совпадают, правка
отклоняется: вы увидите сообщение «изменили, пока вы правили — изменение не
применено», а данные обновятся.

- проверяются только те колонки, которые вы меняете: правка другой колонки чужому
  изменению не мешает;
- обычный просмотр и вставка новых строк работают как обычно;
- в сообщении сервер отдаёт актуальное состояние строки — его видно в ответе API
  (409, поля `current` и `checked`);
- колонки со значением `NULL` не участвуют в проверке: в SQL условие `= NULL` не
  находит строку никогда (в MongoDB — участвуют);
- если конфликт не возникает, всё работает как раньше.

### 7.7. Отмена правки («Откатить данные»)

Любая правка строк здесь (добавление, изменение, в том числе правка ячейки прямо в таблице,
удаление) попадает в список **«Откатить данные»** в шапке карточки. Там видно время, тип
операции, число строк и автора, а также кнопки **«Отменить»** и **«Повторить»** (повтор доступен
только после отмены).

- Хранятся последние 30 операций на таблицу; панель показывает, почему откат недоступен
  (например, «без первичного ключа откат невозможен»).
- Отмена восстанавливает прежние значения, а удалённые строки — вместе с их ключами.
- Подробности и ограничения — в разделе [12.7](#127-откат-изменения-данных-откатить-данные).

### 7.8. Кнопки, которых не будет

Если подключение в режиме «только чтение» или ваша роль панели — `readonly`, панель не покажет
кнопки «Добавить», редактирование и удаление, а вверху появится жёлтая полоса
«только чтение». Это поведение, а не ошибка: сервер всё равно отклонил бы такую операцию.

То же касается конструктора структуры: формы создания индекса, внешнего ключа и триггера, кнопки
«Откатить DDL», добавления и правки колонок при такой комбинации скрыты целиком, а не заблокированы
после нажатия. Если какая-то из этих форм отсутствует, сначала проверьте роль и галочку
«Только чтение» — прочитать можно всё, изменить структуру нельзя.

## 7-bis. Массовые операции по фильтру

Кнопка **«Массовые действия»** в заголовке вкладки «Данные» (роль «редактор» или «админ»).

Работает в два шага, и это не формальность: операция сначала показывает, **сколько строк
она затронет**, и только потом применяется.

1. Введите фильтр строк в том же синтаксисе, что и в панели фильтра:
   `status='active' AND amount>100`. Условия соединяются через `AND`; `OR` не
   поддерживается — так же, как при чтении.
2. Выберите действие:
   - **обновление**: колонка и новое значение — одно значение записывается во все
     подходящие строки;
   - **удаление**: удаляет все найденные строки.
3. Нажмите «Предпросмотр обновления» или «Предпросмотр удаления». Панель покажет число
   строк и первые строки примера. **На этом шаге база не меняется.**
4. Проверьте число строк — это главная проверка. Если оно неожиданно большое, скорее всего,
   фильтр слишком широкий или пустой по смыслу.
5. Нажмите «Обновить N строк» / «Удалить N строк» и подтвердите. Перед применением панель
   снимает **точку восстановления** таблицы; её id остаётся в ответе, откат — в разделе
   «Точки восстановления» (или кнопкой «Откатить данные» для отдельных строк).

Ограничения и особенности:

- пустой фильтр запрещён — сначала сузьте выборку;
- не больше 1000 подходящих строк за одну операцию: разделите выборку на части. Панель
  считает страницами по 500 строк, поэтому «больше 1000» определяется верно, а не по
  первой странице;
- **если точку восстановления снять не удалось** (например, дамп таблицы тяжелее
  50 МБ), операция не выполняется вообще: панель объяснит причину и спросит, продолжать
  ли без точки восстановления. Согласившись, вы теряете возможность отката — поэтому
  по умолчанию ответ «нет»;
- операция выполняется одним запросом (`UPDATE … WHERE …` / `DELETE … WHERE …`, в MongoDB —
  `updateMany` / `deleteMany`), поэтому 1000 строк обрабатываются за доли секунды. Число
  затронутых строк всегда равно числу из предпросмотра: условие отбора одно и то же;
- транзакции нет: если операция прервётся на середине, откат — через точку восстановления,
  снятую до начала работы;
- в журнале операция видна как `row.bulk_update` или `row.bulk_delete`; в ответе также
  приходит `mode` — `set` (один запрос) или `rows` (поштучный запасной путь, он включается
  только если set-based недоступен или не сработал).
- в MongoDB строки опознаются по `_id` (у коллекций нет первичного ключа);
- если часть строк изменить не удалось, панель сообщит об этом — оставшиеся строки
  обработайте отдельно;
- операция попадает в журнал (`row.bulk_update` / `row.bulk_delete`) с указанием числа строк.

Предпросмотр удаления таблицы и базы устроен так же: при удалении таблицы или базы панель
сначала показывает, сколько строк исчезнет (или сколько таблиц в базе и как они называются)
и какой SQL-оператор будет выполнен, и ничего не удаляет до подтверждения.

## 8. SQL-запросы

В панели два редактора SQL: компактный в нижней части вкладки «Структура» (рядом с журналом)
и большой на вкладке **«SQL»**. Это обычный текстовый редактор с подсветкой синтаксиса
(шрифт моноширинный, тема тёмная). Автодополнения и подсказок по схеме нет.

Кнопки редактора: **«Выполнить»**, **«Очистить»**, **«Сохранить»** (в историю запросов),
**«Копировать»**.

Под редактором появляется результат: число строк, время выполнения в мс, при обрезке —
пометка «усечено», и таблица результата.

### 8.1-bis. Объяснить запрос (план выполнения)

Рядом с **«Выполнить»** в обоих редакторах SQL есть кнопка **«Объяснить»** — она показывает,
как СУБД собирается выполнять запрос: какие индексы используются, какие таблицы сканируются
целиком, примерная стоимость и — в PostgreSQL при анализе — фактические тайминги.

**Объяснить можно только чтение.** Если запрос пишет данные (`INSERT`, `UPDATE`, `DELETE`,
`DROP`, `CREATE` и т. п.), панель откажется: в PostgreSQL анализ с таймингами запрос
выполняет по-настоящему, и без этой проверки кнопка могла бы изменить данные.

Поддерживается там, где есть планировщик:

| СУБД | Что покажет |
|---|---|
| MySQL / MariaDB | план с ключами, типом доступа, числом строк и `Extra` |
| PostgreSQL | текстовый план; с анализом — фактическое время и буферы |
| SQLite | `EXPLAIN QUERY PLAN`: сканирование, использование индекса, временные таблицы |
| MongoDB, Redis | не поддерживается — планировщика нет, панель сообщит об этом |

План запроса попадает в журнал событий как `query.explain`.

### 8.1. Как писать запросы

- Запрос выполняется **в выбранной базе**. Сначала выберите базу в левой панели, потом пишите
  запрос — `CREATE TABLE` попадёт именно туда.
- Можно писать несколько стейтментов через `;` — они выполняются по очереди, в таблице
  результата показывается результат последнего.
- `SELECT` без `LIMIT` автоматически ограничивается 1000 строками. Нужно больше — добавьте
  `LIMIT` сами; лимит настраивается переменной `QUERY_MAX_ROWS` на стороне сервера панели.
- Таймаут запроса — 30 с по умолчанию (`QUERY_TIMEOUT_MS`). Долгий запрос вернёт ошибку таймаута.
- Кнопка «Выполнить» недоступна для пустого редактора.

### 8.2. Диалектные правила

| СУБД | Что писать в редакторе |
|---|---|
| MySQL / MariaDB | обычный SQL, идентификаторы в обратных кавычках `` `имя` `` |
| PostgreSQL | обычный SQL, идентификаторы в двойных кавычках `"имя"`, только схема `public` |
| SQLite | обычный SQL, двойные кавычки |
| **MongoDB** | **JSON**, например `{"db":"demo","collection":"users","filter":{"age":{"$gt":18}},"limit":50}`; очистка коллекции — `{"collection":"users","clear":true}` |
| **Redis** | **JSON** с одной из команд: `{"cmd":"GET","key":"foo"}`, `{"cmd":"SET","key":"foo","value":"bar"}`, `{"cmd":"DEL","key":"foo"}`, `{"cmd":"HGETALL","key":"foo"}`, `{"cmd":"KEYS","pattern":"user:*"}` |

Шаблоны можно вставлять кнопками в списке таблиц (лупа — `SELECT`, плюс — `INSERT`).

### 8.3. Совместимость с T-SQL

Панель сама переводит распространённые скрипты, написанные для SQL Server:

| Что написано | Как станет (MySQL) | Как станет (PostgreSQL) | Как станет (SQLite) |
|---|---|---|---|
| `col INT PRIMARY KEY IDENTITY(1,1)` | `AUTO_INCREMENT` | `SERIAL` / `BIGSERIAL` / `SMALLSERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` |
| `GETDATE()` | `CURRENT_TIMESTAMP` | `NOW()` | `CURRENT_TIMESTAMP` |
| `[имя]` | `` `имя` `` | `"имя"` | `"имя"` |
| `NVARCHAR(50)` | `VARCHAR(50)` | `VARCHAR(50)` | `VARCHAR(50)` |
| инлайн `col INT FOREIGN KEY REFERENCES t(id)` | выносится в `FOREIGN KEY (...) REFERENCES ...` | без изменений | без изменений |

Замены делаются только вне строковых литералов и комментариев и только в MySQL/MariaDB/PostgreSQL/
SQLite. Для MongoDB и Redis перевода нет.

Стандартный `GENERATED ALWAYS AS IDENTITY` / `GENERATED BY DEFAULT AS IDENTITY` (PostgreSQL 10+)
транслятор не трогает — это не T-SQL-конструкция, и её подмена ломала бы запрос.

### 8.4. Типичные примеры

```sql
-- MySQL / MariaDB / PostgreSQL / SQLite
SELECT * FROM users WHERE age >= 30 ORDER BY name LIMIT 100;
UPDATE users SET age = age + 1 WHERE id = 5;
DELETE FROM users WHERE id = 5;
CREATE INDEX idx_users_age ON users(age);   -- индексы создаются только вручную
```

```json
// MongoDB: документы старше 18 лет
{"db":"demo","collection":"users","filter":{"age":{"$gt":18}},"limit":50}
```

```json
// Redis: все ключи пользователей и содержимое одного хеша
{"cmd":"KEYS","pattern":"user:*"}
{"cmd":"HGETALL","key":"user:1"}
```

## 9. Поиск по базе данных

Вкладка **«Поиск»**.

1. Введите текст (1–200 символов) и нажмите **«Искать»** (или `Enter`).
2. Панель перебирает таблицы выбранной базы и показывает найденные строки с указанием таблицы
   и колонок.

Особенности:

- поиск подстроки без учёта регистра по всем значениям строки (вложенные JSON-документы тоже);
- по умолчанию — до 1000 совпадений, пагинация по 50; ограничения настраиваются на сервере;
- если какая-то таблица не читается (нет прав, битая), она попадёт в счётчик «Ошибки таблиц» —
  это не поломка поиска, а недостаточные права;
- при достижении лимита появится пометка «достигнут лимит 1000»;
- актуально для больших баз: поиск читает страницы по 500 строк, поэтому он может занять время.

## 10. Импорт данных

Два места: вкладка **«Импорт»** и кнопка **«Импорт»** в правой панели. Панель читает файл
**целиком на стороне браузера** и отправляет его одним запросом — ограничения на размер
приведены ниже.

### 10.1. Подготовка файла

Формат определяется по расширению: `.sql` → SQL-скрипт, `.csv` → CSV, `.json` → JSON.

| Формат | Требования |
|---|---|
| `.sql` | любой скрипт с `;`-разделителями. Поддерживается MySQL/MariaDB, PostgreSQL, SQLite. Для MongoDB и Redis — нет. Лимит 5 МБ, таймаут выполнения 120 с |
| `.csv` | первая строка — заголовки колонок. Кавычки, запятые внутри кавычек и переносы строк в кавычках обрабатываются корректно, BOM отбрасывается. Нужно выбрать **таблицу назначения** |
| `.json` | массив объектов: `[{"id":1,"name":"Ann"},{"id":2,"name":"Bob"}]`. Нужно выбрать **таблицу назначения** |

### 10.2. Импорт

1. Выберите базу (import идёт в неё).
2. На вкладке «Импорт» в выпадающем списке укажите таблицу назначения (для SQL — можно
   «Не выбрана (только для SQL)»).
3. Кликните по области «Выберите файл .sql, .csv или .json».
4. Дождитесь сообщения об окончании: «Импорт завершён: N операций (X мс)».

При импорте CSV/JSON в MongoDB поле `_id` из файла отбрасывается — идентификаторы генерирует сервер.

### 10.3. Ограничения и частые отказы

| Причина | Сообщение / что делать |
|---|---|
| Файл больше 10 МБ | «Bad data (10MB max)». Разбейте файл на части |
| Больше 50 000 строк в CSV/JSON | «Too many rows (50k)». Импортируйте частями |
| Не выбрана таблица для CSV/JSON | «Для CSV/JSON выберите таблицу назначения» |
| Подключение только для чтения | «Connection is read-only» |
| Роль `readonly` | «Role readonly cannot write» |
| Нет прав на `INSERT` | Ошибка драйвера (например, `Access denied` / `permission denied`) |
| SQL-скрипт в MongoDB | «Import SQL not supported for mongodb» — используйте JSON |
| Импорт идёт не в ту базу | Смените базу в левой панели и повторите — контекст берётся из выбранной БД |

Импорт **не** откатывает уже вставленные строки, если упадёт на середине: при bulk-импорте
сначала фиксируется уже вставленное. После неудачи проверьте фактическое содержимое таблицы,
и при необходимости очистите её (кнопка «ластик») и повторите.

## 11. Экспорт данных

Три способа:

| Способ | Где | Что делает |
|---|---|---|
| Одна таблица или вся база, формат на выбор | вкладка «Экспорт», список «Что выгружать» | «Экспорт» → один файл `<таблица>.<формат>` или `<база>.<формат>` |
| Вся база одним файлом | там же, пункт «Вся база …» в списке | все таблицы базы в одном файле, порядок таблиц пригоден для восстановления |
| Кнопка «Экспорт» в открытой таблице | карточка таблицы | то же, формат `sql` (структура + данные) |
| Массовый экспорт | галочки в списке таблиц → «Экспорт», или «Экспорт» в правой панели | все выбранные таблицы / все таблицы базы, всегда в CSV, файлы `<база>_<таблица>.csv` |

Форматы:

- **SQL** — `CREATE TABLE IF NOT EXISTS ...` со структурой и последующие `INSERT INTO`.
  Такой файл можно сразу загрузить обратно через импорт SQL; диалектные кавычки сохраняются.
- **CSV** — первая строка — заголовки, значения всегда в кавычках.
- **JSON** — массив объектов; для последующего импорта это готовый формат.

При экспорте **всей базы** формат один и тот же, но содержимое составное:

- **SQL** — структура и данные всех таблиц в порядке, пригодном для восстановления: сначала
  таблицы, на которые ссылаются другие, затем зависимые. Такой дамп можно загрузить в пустую
  базу без ошибок порядка.
- **JSON** — объект, где ключ — имя таблицы, значение — массив её строк:
  `{"users": [...], "orders": [...]}`.
- **CSV** — один общий файл: в начале пояснение формата, затем каждая таблица со своим
  заголовком колонок, перед ней строка-разделитель `# table: <имя таблицы>`. По этим
  разделителям файл можно разделить обратно на отдельные CSV.

Ограничения и особенности:

- для MongoDB формат **SQL недоступен** (панель не знает SQL-диалект документов) — только CSV/JSON;
- для Redis доступен просмотр ключей; «экспорт» отдаёт то, что драйвер умеет отдать по ключу;
- экспорт идёт потоком, поэтому память не растёт: выгрузка большой таблицы не уронит ни панель,
  ни браузер. Скачивание может занять время;
- массовый экспорт с галочками скачивает несколько файлов — проверьте, не блокирует ли браузер
  «множественную загрузку» (обычно достаточно разрешить её в настройках загрузок). Экспорт всей
  базы из вкладки «Экспорт» файлов не множит: это один файл;
- если у базы нет таблиц, экспорт всей базы вернёт ошибку «нет таблиц для экспорта», а не пустой файл.

## 12. Резервное копирование и восстановление

Раздел «Резервные копии» находится в модальном окне **Настройки → Резервные копии**
(быстрый доступ: правая панель → «Резервное копирование»).

### 12.1. Создать расписание

1. Выберите **формат**: `SQL` или `JSON`. Для MongoDB доступен только `JSON`.
2. Укажите **интервал в минутах** (допустимо 5…43200; по умолчанию 1440 — сутки).
3. Укажите **сколько копий хранить** (1…50; по умолчанию 7).
4. **«Создать расписание»**.

БД для копирования берётся из выбранной в панели базы. Если оставить базу пустой, возьмётся
база подключения по умолчанию (для SQLite — `main`).

### 12.2. Создать копию сейчас

**«Создать копию сейчас»** — запускает внеплановый запуск существующего расписания с теми же
параметрами; если подходящего расписания нет, панель создаст его. В списке появится запуск
с размером файла и числом таблиц.

Файлы копий: `<каталог данных панели>/backups/<id-расписания>_<дата-время>.sql|json`.
В Docker каталог данных — том `dbpanel-data` (внутри контейнера `/data/backups`).

### 12.3. Управление расписаниями

Для каждого расписания доступны «Выключить»/«Включить» и «Удалить».
Удаление расписания (администратор) удаляет и его файлы запусков. Ручное изменение интервала и
числа копий настраивается через API; в интерфейсе доступны включение/выключение и удаление.

Планировщик работает внутри backend и проверяет расписания **каждые 30 секунд**, поэтому
копия может появиться с небольшим опозданием относительно интервала.

### 12.4. Восстановление

Восстановление выполняется через API (кнопки в интерфейсе нет):

```
POST /api/backups/runs/:id/restore
```

Как это работает: панель определяет список таблиц в копии, **полностью очищает** каждую из них
и загружает содержимое заново. Это безопасно относительно первичных ключей, но означает, что
данные, появившиеся после копии, будут потеряны.

Ограничения:

- подключение в режиме «только чтение» — отказ (403);
- максимальный размер дампа — 100 МБ;
- MongoDB и SQLite восстанавливаются из JSON-копий; SQL-дампы для них не создаются;
- роль `readonly` восстановление недоступно;
- перед восстановлением в рабочей среде сделайте независимую копию — операция необратима.

### 12.5. Если копии нужны регулярно

Панель делает копии только по расписанию и не умеет отправлять их наружу. Для надёжности
копии забирайте с диска (том `dbpanel-data`) и храните отдельно, а для критичных баз
используйте штатные средства СУБД (`mysqldump`, `pg_dump`, `mongodump`, `redis-cli --rdb`).

### 12.6. Точки восстановления (отличаются от бэкапа по расписанию)

Точка — это дамп **одной таблицы** (или коллекции MongoDB), снятый по требованию либо
автоматически перед разрушительным DDL. От бэкапа отличается тем, что не зависит от таймера
и снимается в момент, когда данные вот-вот изменятся.

Где хранится: `<каталог данных панели>/checkpoints/` (в Docker — том `dbpanel-data`).

Как пользоваться:

```
GET    /api/checkpoints?connId=<id>&db=<db>&table=<table>   # список точек
POST   /api/checkpoints  { "connId": "...", "db": "...", "table": "...", "reason": "manual" }
POST   /api/checkpoints/:id/restore  { "dropExisting": true }
DELETE /api/checkpoints/:id                                  # admin
```

Что нужно знать:

- **Автоматическая точка** создаётся перед удалением столбца и перед `DROP TABLE`; её `id`
  возвращается в ответе на DDL. Откат по ней возвращает таблицу с данными и удалённым столбцом.
- Если таблица или коллекция сейчас существует, откат **не выполнится** без `dropExisting: true`
  (ответ `409`) — это защита от случайной потери свежих данных.
- При откате SQL-таблица пересоздаётся заново, а коллекция MongoDB очищается и заполняется
  заново; `_id` документов при этом сохраняются, поэтому ссылки на документы из других
  коллекций остаются рабочими.
- Хранятся **20 последних точек на таблицу**, старые удаляются автоматически. Дамп больше
  50 МБ не сохраняется — панель предложит сделать бэкап по расписанию.
- Роль `readonly` не видит точки и не может их создавать; удалять точки может только администратор.

### 12.7. Откат изменения данных («Откачить данные»)

Самый быстрый способ вернуть одну правку: **в карточке таблицы** нажмите **«Откатить данные»** —
откроется список последних операций над строками этой таблицы (вставка, изменение, удаление) с
кнопками **«Отменить»** и **«Повторить»**.

Как это работает: перед каждой правкой панель запоминает содержимое только тех строк, которые
изменяются (не всю таблицу), поэтому откат мгновенный и работает даже на больших таблицах. Хранятся
последние **30** операций на таблицу.

Три независимых механизма отката — не путайте их:

| Механизм | Что отменяет | Где |
| --- | --- | --- |
| Откатить DDL | изменение структуры (индексы, связи, триггеры) | карточка таблицы |
| Откатить данные | вставку/изменение/удаление строк | карточка таблицы → «Откатить данные» |
| Точка восстановления | всё содержимое таблицы | только через API (см. 12.6) |

Ограничения (намеренные — лучше отказ, чем испорченные ключи):

- без первичного ключа откат невозможен, и операция помечается серым;
- если за раз затронуто больше 500 строк, откат недоступен — берите точку восстановления;
- **PostgreSQL с `GENERATED ... AS IDENTITY`**: отменять удаление нельзя (ключ пришлось бы выдать
  заново и сломать ссылки), поэтому пункт будет недоступен; с обычным `serial` откат работает, и
  отменяются также вставка и изменение;
- изменения, сделанные через **SQL-редактор**, в этот список не попадают — для них нужна точка
  восстановления;
- отмена и повтор необратимы и требуют подтверждения.

Через API то же самое:

```
GET    /api/data-undo?connId=<id>&db=<db>&table=<table>
POST   /api/data-undo/:id/undo     # отменить операцию
POST   /api/data-undo/:id/redo     # повторить после отмены
DELETE /api/data-undo/:id          # удалить запись (администратор)
```

## 13. Пользователи базы данных и права

Речь о пользователях **целевой СУБД**, а не панели. Управляет ими администратор панели.

### 13.1. Где это в интерфейсе

- Правая панель → блок **«Пользователи БД»**: список пользователей, кнопка обновления, форма
  «логин + пароль» и кнопка добавления, корзина у пользователя.
- Внутри таблицы → вкладка **«Привилегии»**: выбор пользователя, выбор привилегии, область
  (`база.таблица`), кнопки «Обновить», «Выдать», «Отозвать», список текущих привилегий.

### 13.2. Создание пользователя

Правая панель → «Пользователи БД» → введите логин (3–32 символа: латиница, цифры, `_`) и пароль
(8–128 символов, без `'`, `"`, `\`, `;`) → «+».

Что делает панель:

| СУБД | Команда |
|---|---|
| MySQL / MariaDB | `CREATE USER 'u'@'%' IDENTIFIED BY '…'` |
| PostgreSQL | `CREATE ROLE "u" WITH LOGIN PASSWORD '…'` |
| MongoDB | `createUser` с ролью `readWrite` в целевой БД |
| Redis | `ACL SETUSER u reset on >пароль ~* +@all` (полные права) |
| SQLite | отказ: «SQLite has no DB users» |

### 13.3. Гранты

Вкладка «Привилегии» таблицы: выберите пользователя, привилегию из списка, при необходимости
таблицу, нажмите «Выдать». Отзыв — кнопка «Отозвать».

Допустимые привилегии: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `ALTER`,
`INDEX`, `ALL PRIVILEGES`. Для PostgreSQL набор скромнее: `SELECT`, `INSERT`, `UPDATE`, `DELETE`,
`ALL PRIVILEGES`, и грант всегда выдаётся на таблицу либо на все таблицы схемы `public`.
Для MongoDB привилегией фактически является **роль** (например, `readWrite`, `read`).

Панель не различает «выдать на базу» и «выдать на таблицу» отдельно от того места, где вы
нажали кнопку: для MySQL/MariaDB цель вычисляется из выбранных базы и таблицы (`*.*`, `db.*`,
`db.table`).

### 13.4. Просмотр привилегий

Кнопка «Обновить» в блоке привилегий показывает фактические права пользователя
(`SHOW GRANTS` / `information_schema.role_table_grants` / роли MongoDB / правила ACL Redis).
Это лучший способ проверить, что грант применился.

Ошибки, которые вы увидите:

- «Admin only» — операция доступна только администратору панели;
- «Connection is read-only» — подключение помечено «только чтение»;
- «DB users not supported for sqlite» — у SQLite нет пользователей;
- «Недостаточно прав» от СУБД — у пользователя подключения нет `CREATE USER` / `GRANT OPTION`.

## 14. Пользователи панели и роли

Левая панель → **«Управление доступом»** (или Настройки → вкладка «Пользователи»).

### 14.1. Создать пользователя панели

Поля «Логин», «Пароль», роль (`Editor` / `Readonly` / `Admin`) → **«Создать»**.
Имя: 3–64 символа, латиница, цифры, `_`, `.`, `-`. Пароль: минимум 8 символов. Имя должно быть
уникальным.

### 14.2. Изменить и удалить

- **«Изменить»** — новая форма с логином, новым паролем (оставьте пустым, чтобы не менять) и ролью.
- **«Удалить»** — с подтверждением. Нельзя удалить самого себя. После удаления или смены роли
  его активная сессия немедленно перестаёт работать: панель вернёт на экран входа.

### 14.3. Что может каждая роль

| Действие | Admin | Editor | Readonly |
|---|---|---|---|
| Смотреть базы, таблицы, строки, схемы, индексы, связи, триггеры | ✅ | ✅ | ✅ |
| SQL на чтение, поиск, статус сервера | ✅ | ✅ | ✅ |
| Изменять данные и структуру (CRUD, DDL, импорт, очистка, удаление) | ✅ | ✅ | ❌ |
| Создавать и удалять индексы, внешние ключи, триггеры | ✅ | ✅ | ❌ |
| Предпросматривать DDL и откатывать последний пакет изменений | ✅ | ✅ | ❌ |
| Создавать подключения и базы | ✅ | ✅ | ❌ |
| Изменять и удалять подключения, удалять базы | ✅ | ❌ | ❌ |
| Пользователи и права **СУБД** | ✅ | ❌ | ❌ |
| Убивать чужие запросы (`KILL`) | ✅ | ❌ | ❌ |
| Резервные копии: создать, включить, запустить, восстановить | ✅ | ✅ | ❌ |
| Удалить расписание копий, удалить загруженный файл SQLite | ✅ | ❌ | ❌ |
| Пользователи панели и общие настройки панели | ✅ | ❌ | ❌ |
| Журнал событий (аудит) | ✅ | ✅ | ❌ |

Отдельно от роли работает галочка **«Только чтение»** у подключения: она запрещает изменения
в этой конкретной базе независимо от роли (в том числе у администратора), и панель просто не
покажет соответствующие кнопки.

### 14.4. Рекомендации

- Дайте операторам роль `Editor` на отдельном подключении с «только чтение» для тех баз, где
  им не нужно изменение данных.
- Роль `Admin` выдавайте только тем, кто управляет пользователями, подключениями и правами СУБД.
- `Readonly` удобен для аналитики: поиск, выгрузки, просмотр схемы работают, а кнопки
  изменения скрыты.

## 15. Мониторинг и диагностика

### 15.1. Экран «Мониторинг»

Левая панель → **«Мониторинг»**. Панель каждые 10 секунд опрашивает сервер и показывает:

- **Загрузка CPU и ОЗУ** — ресурсы **хоста, на котором работает панель**, а не вашей СУБД;
- **Запросы (QPS)** и их общее количество, медленные запросы — по данным целевого сервера;
- **Соединения** и число процессов;
- два графика: загрузка ЦП и динамика QPS (последние ~20 замеров).

Если сервер не отвечает, вверху появится красная плашка «Ошибка API» с текстом причины —
это самый быстрый способ увидеть, что происходит с подключением.

### 15.2. Правая панель «Информация о сервере»

Для выбранного подключения показывается: версия сервера, сколько баз на сервере, число соединений,
время работы, медленные запросы, список баз с размерами в байтах и количеством таблиц, список
активных процессов (топ-10) с пользователем, временем и текстом запроса.

Обновление — кнопка «↻» в заголовке блока. Если какая-то метрика недоступна, будет прочерк.

### 15.3. Активные процессы и `KILL`

У каждого процесса в списке у администратора есть кнопка запрета (оранжевая).
Нажатие → подтверждение → панель выполняет `KILL` (MySQL/MariaDB) или `pg_cancel_backend`
(PostgreSQL) для процесса с указанным `pid`.

Внимание:

- кнопка есть только у роли `admin` на изменяемом подключении;
- для MongoDB, Redis и SQLite `KILL` не поддерживается (панель сообщит об этом);
- останавливается чужой запрос — убедитесь, что это действительно нужно;
- PostgreSQL отменяет запрос, но не закрывает сессию.

### 15.4. Шпаргалка диагностики

| Симптом | Что проверить |
|---|---|
| «Нет подключения» в шапке | не выбрано подключение в блоке «Подключения» |
| «Ошибка загрузки баз данных» | кнопка «Проверить базу»; порт (MariaDB в демо-окружении — 3307); доступность СУБД |
| Категория СУБД пустая | нет подключений этого типа либо все базы удалены; кнопка «↻» |
| Список таблиц пуст | выбрана база без таблиц; для SQLite — существует ли файл |
| «Bad credentials» | креды подключения |
| «Access denied» / «permission denied» | у пользователя подключения нет прав на объект |
| «Connection is read-only» | снимите галочку «Только чтение» у подключения (нужны права администратора) |
| «Role readonly cannot write» | ваша роль панели — `readonly` |
| «Admin only» | нужна роль администратора |
| «Table not found» / «relation does not exist» | неверно выбрана база или имя таблицы; для PostgreSQL — только `public` |
| «query timeout 30000ms» | запрос дольше 30 с; упростите его или разбейте |
| «No driver for …» | тип подключения не поддерживается (все шесть поддерживаются) |
| «429» | слишком много запросов, подождите минуту |
| Панель перезапрашивает | дождитесь текста ошибки в уведомлении — он точнее, чем надпись на экране |

## 16. Журналы: события и история запросов

### 16.1. Журнал операций и SQL (нижняя панель вкладки «Структура»)

Три вкладки:

- **«Последние операции»** — последние 100 выполненных запросов: время, пользователь, текст
  запроса, результат (успех/ошибка);
- **«Журнал SQL»** — выполненные в этой сессии запросы с временем, длительностью и числом строк;
  у каждой записи при наведении есть кнопки «Копировать», «Вставить в редактор», «Выполнить снова»;
- **«События»** — аудит панели: время, уровень (успех/ошибка), источник (`query`, `row.insert`,
  `design.drop`, `import`, `backup`, `kill`, `db.drop` и т. д.) и сообщение (цель, пользователь,
  длительность). Фильтры «Все / Успешно / Ошибки», кнопка обновления.

Вкладка **«Операции»** верхнего уровня показывает полный журнал запросов текстом.

У каждой вкладки справа в заголовке есть кнопка **«Очистить»** — об этом в разделе
[16.4](#164-очистка-журналов).

### 16.2. Уведомления в шапке

Колокольчик показывает последние 50 событий аудита: создание/удаление подключения, создание/удаление
базы, проверка подключения и ошибки (для них в заголовке добавляется «— ошибка»). Событие можно
открыть (детали), отметить все прочитанными (список очищается) или удалить выборочные. Состояние
«прочитано/скрыто» хранится в браузере, поэтому после очистки уведомления не вернутся сами.
Если уведомления отключены в настройках, колокольчик предложит их включить.

В окне события внизу слева есть кнопки **←** и **→** и счётчик вида `3 / 50`: они листают
уведомления, не закрывая окно. Работают и стрелки клавиатуры `←` / `→`. На первом уведомлении
кнопка «назад» отключена, на последнем — «вперёд», так что видно, где вы находитесь.
Просмотренное уведомление сразу считается прочитанным.

### 16.2-bis. Что именно изменилось: значения в аудите

Журнал событий (**«События»** в нижней панели) показывает не только «кто тронул таблицу», но и
**что именно поменялось**: для вставки, правки и удаления строки в нём есть строки
**«было: …»** и **«стало: …»**.

- `row.insert` — добавленная строка;
- `row.update` — состояние до и после, а также набор изменённых полей;
- `row.delete` — удалённая строка.

Что стоит знать:

- значения обрезаются: строка длиннее 200 символов и глубина вложенности больше двух уровней
  сокращаются, а вся запись не превышает 8 КБ — журнал не должен раздувать файл метаданных;
- читать аудит может всё, кроме роли `readonly`; там же видны обычные действия (создание БД,
  DDL, бэкапы) — для них значений нет;
- через API это поле `values` в ответе `GET /api/audit`; сырой столбец `valuesJson` наружу
  не отдаётся;
- очистка журнала (`DELETE /api/audit`) стирает и значения — это не отдельный архив.

### 16.3. История запросов

Каждый выполненный запрос автоматически попадает в историю. Вручную добавляется кнопкой
**«Сохранить»** в редакторе — запись помечается как сохранённая и не удаляется при очистке.

- Очистка: у пользователя остаются последние **200** несохранённых записей, старые удаляются;
  сохранённые хранятся, пока вы их не удалите;
- у каждого пользователя своя история, чужие записи не видны;
- фильтры: по подключению, только сохранённые, поиск по тексту запроса;
- переименовать запись и снять/поставить отметку «сохранён» можно через API
  (`PATCH /api/history/:id`), удалить — `DELETE /api/history/:id` (только владелец);
- в самом интерфейсе записи истории показываются в «Последних операциях» и «Журнале SQL».

### 16.4. Очистка журналов

В правой части заголовка панели журналов есть кнопка **«Очистить»** — она чистит журнал той
вкладки, на которой вы находитесь:

| Вкладка | Что стирается | Кто может |
| --- | --- | --- |
| «Последние операции» | своя история запросов | любая роль |
| «События» | журнал операций (аудит) всех пользователей | только администратор |
| «SQL» | список запросов текущей сессии (ничего не сохраняется) | любая роль |

Дополнительно администратору доступны варианты, которых нет в кнопке:

- очистить **все** записи истории запросов всех пользователей (а не только свои) — второе
  подтверждение «Очистить ВСЕ записи…?»;
- очистить только **сохранённые** запросы, не трогая остальные;
- очистить журнал операций по конкретному подключению вместо всего сразу.

Что важно знать:

- очистка **необратима** и всегда требует подтверждения — отмены нет;
- факт очистки остаётся в журнале операций (`audit.clear` / `history.clear`), поэтому след виден
  даже после полной очистки аудита;
- чужую историю запросов увидеть нельзя: `GET /api/history` всегда отдаёт записи текущего
  пользователя, даже администрателю; общая картина действий — в журнале операций;
- из API то же самое: `DELETE /api/audit?all=1` (admin) и
  `DELETE /api/history?scope=mine|saved|all` (+ `&connId=`).

## 16-bis. Модели проекта: сохранить схему и перенести её

**Модель** — это сохранённая схема целиком. Отличается от остальных механизмов панели:

| Механизм | Что хранит | Где смотреть |
| --- | --- | --- |
| Точка восстановления | дамп одной таблицы | только API |
| Откат DDL | последний пакет изменения структуры | кнопка «Откатить DDL» |
| Откат данных | образ изменённых строк | кнопка «Откатить данные» |
| **Модель** | **всю схему: таблицы, колонки, индексы, связи, триггеры** | **«Модели проекта»** |

### 16-bis.1. Где открыть

Правая панель → **«Быстрые действия» → «Модели проекта»**.

### 16-bis.2. Сохранить схему базы

Выберите подключение и базу, введите имя (например `shop-2026-02`) и нажмите
**«Забрать схему»** — модель создастся с текущими таблицами, индексами, внешними ключами и
триггерами. Повторное сохранение того же имени вернёт ошибку: имена моделей уникальны.

### 16-bis.3. Версии

Кнопка **«Сохранить как версию»** создаёт новую версию модели, предыдущая уходит в историю
(хранятся последние 20). У каждой версии в списке есть **«вернуть»** — это не откат, а новая
версия с прежним содержимым, поэтому историю никогда не терять.

Если открыть модель в двух вкладках, версия может устареть: панель отклонит сохранение с
сообщением о конфликте — обновите модель и повторите.

### 16-bis.4. Применить к базе

Выберите в списке целевую базу и одну из двух кнопок:

- **«Дописать отсутствующие»** — создаются только те таблицы, которых ещё нет. Схемы, которые
  уже созданы вручную, остаются нетронутыми (их имена попадут в список «пропущено»);
- **«Пересоздать (с точкой восстановления)»** — все таблицы модели удаляются и создаются заново.
  **Данные этих таблиц будут потеряны**, поэтому перед каждой таблицей панель снимает точку
  восстановления (восстановить данные потом можно через API, см. [12.6](#126-точки-восстановления-checkpoints)).

Порядок применения: сначала создаются все таблицы, затем индексы и внешние ключи, затем
триггеры. Таблицы удаляются в обратном порядке зависимостей — иначе СУБД не даст удалить
родительскую таблицу, пока на неё ссылается внешний ключ.

После применения в окне показывается отчёт: что создано, что пересоздано, что пропущено, ошибки
(если таблица не применилась, остальные применяются) и фактические SQL-команды.

### 16-bis.4-bis. Перенос на другую СУБД

Модель можно применить не только к той СУБД, с которой её сняли. Типы колонок и выражения
`DEFAULT` при этом переводятся в диалект цели, поэтому `VARCHAR` становится `VARCHAR2` в Oracle,
`TEXT` — `CLOB`, `INT` — `NUMBER`, а `BOOLEAN` — `SMALLINT` в MySQL. Длина и точность
переносятся по возможностям цели: `VARCHAR(5000)` станет `VARCHAR2(4000)`, а `NUMBER(19)` в
Oracle — `BIGINT` в PostgreSQL и MySQL.

Что стоит проверить после переноса:

- **точность денежных колонок**: `DECIMAL(10,2)` и `NUMBER(10,2)` сохраняются, но проверьте
  значения — округление на границе может отличаться;
- **значения по умолчанию**: `CURRENT_TIMESTAMP`, `now()` и выражения с `serial` переводятся
  по возможности, а незнакомое выражение применится как есть и может быть отвергнуто сервером —
  тогда в отчёте будет ошибка этой таблицы, а остальные применятся;
- **внешние ключи и триггеры у таблиц, которых уже нет**: они попадут в «пропущено».

Если в отчёте есть ошибка `ORA-00942`/`42P01` («таблицы не существует»), это почти всегда
внешний ключ или триггер, ожидающие таблицу, которую этот прогон не создавал: сначала примените
модель с пустой базой или пересоздайте таблицы.

### 16-bis.5. Сравнить модель с базой (сначала посмотрите, а не применяйте)

Кнопка **«Сравнить с базой»** ничего не меняет — она отвечает на вопрос «насколько база
разошлась с моделью». Это стоит делать до применения: сразу видно, что появилось в базе
руками, чего не хватает и какие таблицы разошлись по типу или `NOT NULL`.

Отчёт состоит из:

- **нет в базе** — таблицы и колонки из модели, которых ещё нет;
- **лишние в базе** — таблицы, колонки, индексы, связи и триггеры, которых нет в модели
  (например, созданные вручную);
- **изменённые** — расхождения по существу: тип колонки, `NOT NULL`, первичный ключ,
  автоинкремент, состав индексов и связей, `ON DELETE`.

Что специально не считается расхождением (иначе отчёт «дребезжал» бы на пустом месте):

- запись типов: `INT` = `integer` = `int4`, `VARCHAR(100)` = `character varying(100)`;
- автоиндекс первичного ключа (`PRIMARY`, `t_pkey`) — он есть в любой таблице с ключом;
- значения по умолчанию, `extra` и тела триггеров — сервер их переформатирует;
- `datetime` и `timestamp`, `text` и `varchar` считаются разными типами.

Итог внизу: сколько таблиц совпадают, сколько отсутствует, сколько лишних и сколько изменено.
Если расхождения вам не мешают, смотрите на кнопку применения: в MySQL и PostgreSQL в базе
могут быть служебные таблицы, которых нет в модели.

Через API: `POST /api/models/:id/diff` с `{connId, db, includeExtra?}`. Параметр
`includeExtra: false` убирает «лишние» объекты, когда база намеренно богаче модели.

### 16-bis.6. Права и ограничения
- читать модели может любой вошедший, в том числе роль `readonly`;
- сохранять и применять может `editor` и `admin`, удалять — только `admin`;
- ограничения: до 200 таблиц в модели, до 200 колонок в таблице, имя до 128 символов (буквы,
  цифры, подчёркивание), размер модели до 4 МБ;
- модель хранит **схему, а не данные** — переносится конструкция, строки остаются в исходной базе;
- через SQL-редактор сделанные изменения в модель не попадают: модель — это снимок на момент
  сохранения.

## 16-ter. Панели: сетка панелей

При открытии базы панель открывается сразу: вкладка **«Панели»** — основной вид рабочей
области, а экран «Мониторинг» собран из таких же панелей. Разница с привычными вкладками: панели можно переставлять и растягивать.

Как это работает:

1. Панель перетаскивается за шапку — соседи разъезжаются, панель не может наехать на
   другую.
2. Размер меняется за любой из восьми краёв. У каждой панели есть минимальный размер:
   таблицы и SQL-редактор не сжимаются в нечитаемую полоску.
3. Шевронка в шапке сворачивает панель в одну строку. Размер при этом запоминается —
   раскрытие возвращает панель того же размера.
4. Кнопка со стрелкой вверх в шапке выносит панель в отдельное окно: его можно таскать,
   растягивать, разворачивать на весь экран и свернуть. Кнопка «Вернуть в сетку» в окне
   возвращает панель на свободное место. Панель «Таблицы» открывается кликом по имени таблицы.
   Отдельного оконного режима, который открывал бы панели мимо раскладки, в интерфейсе
   больше нет — окна принадлежат сетке панелей и живут в ней же.
5. «Вернуть все окна» возвращает в сетку сразу все откреплённые панели.
6. Двойной клик по шапке открывает панель на всю рабочую область. Остальные панели при этом
   превращаются в полосу вкладок над ней — их можно увидеть и переключить кликом. Повторный
   клик, кнопка в шапке фокусной панели или Escape возвращает сетку. Панель занимает всю
   доступную область и никогда не уезжает за её пределы: если панелей много, область
   прокручивается, а не обрезается. Открытая панель всегда впереди: она перекрывает и
   остальные панели, и всплывающие окна, — иначе её не было бы видно, если открыто
   развёрнутое окно, и поверх боковых панелей: окно можно перетащить на левый или
   правый сайдбар, и оно окажется сверху. При этом активированное окно всегда впереди остальных: клик по
   окну поднимает его, даже если оно было позади.
7. Когда панель не в фокусе, её можно двигать и растягивать с клавиатуры: встаньте на
   шапку (Tab) и жмите стрелки, а Shift со стрелками меняет размер — мышью трудно попасть
   ровно в две колонки. В режиме фокуса стрелки не двигают панель: она занимает всё поле,
   и перестановка была бы невидимым эффектом.
Быстрое редактирование полей: у значения поля (имя, тип, длина, Null, значение по
умолчанию) есть карандаш — по клику значение открывается во всплывающем окне, где его
удобно набрать целиком. Enter применяет, Escape отменяет, клик снаружи закрывает без
изменений. В таблице структуры клик по значению открывает обычный редактор колонки —
так же, как кнопка с карандашом в строке.

8. «Сбросить компоновку» возвращает исходное расположение.

Что стоит знать:

- компоновка запоминается в браузере отдельно для вас (по имени пользователя, а не по роли)
  и отдельно для рабочей области и для мониторинга: переставлять панели заново после перезагрузки не нужно, но
  компоновка мониторинга не влияет на рабочую и наоборот;
- компоновка общая для всех баз: переключение базы её не сбрасывает;
- порядок колонок у существующей таблицы перетаскиванием не меняется — он задан в СУБД;
- у сайдбаров слева и справа своё сворачивание влево и вправо, они не панели и на сетку не
  переезжают;
- если панель откреплена, она пропадает с сетки и появляется в таскбаре;
- вкладка «Структура» со своим журналом окон осталась рядом с сеткой как запасной вариант:
  вкладка «Панели» открывается по умолчанию, «Структура» — в один клик.

## 17. Настройки панели

Модальное окно **«Настройки»** (шестерёнка в шапке, иконка в левой панели, меню пользователя →
«Профиль»). Пять вкладок.

| Вкладка | Что можно настроить | Кто может |
|---|---|---|
| **Общие** | название проекта (до 120 символов, видно в боковой панели и в шапке), тема, часовой пояс (`UTC`, `Europe/Moscow`, `America/New_York`), включение всплывающих уведомлений и их длительность в миллисекундах (`0` — не скрывать), «проверять обновления» | администратор |
| **Уведомления** | показывать ли уведомления о состоянии сервера, резервных копиях и активности | администратор |
| **Безопасность и 2FA** | информация: 2FA не настроена (серверного механизма нет), таймаут сессии задан сервером и из браузера не меняется | любой вошедший (информационно) |
| **Резервные копии** | расписания и запуск копии сейчас | администратор и редактор (`readonly` — нет) |
| **Пользователи** | управление пользователями панели | администратор |

Изменения сохраняются кнопкой **«Сохранить»** и действуют для всей панели сразу (общие настройки),
а не только в вашем браузере. Кнопка «Отмена» ничего не применяет. Тема дополнительно
запоминается в вашем браузере, поэтому переключатель в шапке работает мгновенно.

Часовой пояс влияет только на подписи настроек; таймстемпы в журналах показываются в формате
браузера.

## 18. Работа с файлами SQLite

### 18.1. Загрузить файл

В интерфейсе загрузка файлов .sqlite недоступна — это серверная операция
(`POST /api/sqlite/files`, multipart, до 100 МБ, ровно один файл, имя
`[A-Za-z0-9_.-]{1,64}\.(db|sqlite|sqlite3)`). Файлы попадают в каталог данных панели
(`sqlite/` рядом с `meta.db`; в Docker — `/data/sqlite`).

Практический сценарий: попросите администратора панели загрузить файл, затем создайте
подключение типа **SQLite** с путём `sqlite/<имя-файла>` — и база появится в панели.

### 18.2. Скачать файл

`GET /api/sqlite/files/:name/download` — потоковая выдача файла.
В интерфейсе кнопки скачивания нет: для получения данных используйте экспорт таблицы
(«Экспорт» → CSV/JSON/SQL) или сделайте резервную копию.

### 18.3. Удалить файл

`DELETE /api/sqlite/files/:name` — только администратор. Проверки связей с подключениями на
сервере нет, поэтому **сначала отключите подключение** к этому файлу: после удаления файла
оно останется в списке подключений, но база станет пустой, а «Проверить базу» начнёт возвращать
ошибку «файл не найден».

### 18.4. Особенности SQLite

- Создание базы в панели = создание файла + отдельное подключение; удаление базы = удаление файла
  вместе с подключением;
- пользователей, прав и `KILL` у SQLite нет — соответствующие разделы покажут честное сообщение;
- при удалённом файле подключение остаётся в списке, но база пуста, а «Проверить базу» вернёт
  ошибку «файл не найден» — так вы узнаете, что файл потерян или перемещён;
- изменение типа, `NULL`, `DEFAULT` и `PK` существующей колонки не поддерживается: SQLite не умеет
  `ALTER COLUMN`. Используйте SQL-редактор и пересоздание таблицы;
- внешний ключ нельзя добавить к существующей таблице: нет `ALTER TABLE ... ADD CONSTRAINT`.
  Задавайте его прямо в `CREATE TABLE` (вкладка «SQL»). По той же причине откат DDL не
  восстанавливает удалённые внешние ключи;
- зато индексы и триггеры в SQLite создаются и удаляются из панели: индексы — вкладка «Индексы»,
  триггеры — вкладка «Триггеры» (тело может содержать несколько стейтментов, `BEGIN ... END`
  панель подставляет сама);
- DDL-пакет в SQLite выполняется в транзакции целиком, поэтому при ошибке не остаётся
  «наполовину применённых» изменений;
- переименование таблицы панель выполнит только на SQLite 3.25+.

## 19. Типичные сценарии

### 19.1. «Развернуть новую базу с нуля»

1. Войти под администратором.
2. «Подключение» → тип, хост, порт, пользователь с правами `CREATE`, имя подключения.
3. «Проверить базу» → должен быть `OK`.
4. «Создать» → категория СУБД, подключение, имя базы → «Создать».
5. База появится в левой панели — выберите её.
6. «Создать таблицу» → имя, колонки, при необходимости `AUTO_INCREMENT`/`SERIAL` для ключа.
7. В карточке таблицы добавьте индексы (вкладка «Индексы») на колонки, по которым будете искать,
   и внешние ключи (вкладка «Связи») — кроме SQLite, где FK задаётся в `CREATE TABLE`.
8. Импортируйте данные (CSV/JSON) или выполните SQL-скрипт.
9. Настройте резервное копирование: Настройки → Резервные копии → «Создать копию сейчас».

### 19.2. «Выгрузить данные в CSV для анализа»

1. Выберите подключение и базу.
2. Вкладка «Структура» → таблица → вкладка «Данные», при необходимости выберите размер
   страницы (до 200 строк).
3. Экспорт всех таблиц базы: правая панель → «Экспорт» (получите набор CSV), либо точечно:
   вкладка «Экспорт» → таблица → CSV → «Начать экспорт».

Учтите: экспорт выгружает **всю таблицу**, а не только ту страницу, которую вы видите.

### 19.3. «Найти, где в базе встречается значение»

Вкладка **«Поиск»** → введите значение → «Искать». Панель покажет таблицы и конкретные строки.
Если значение не найдено, увеличьте лимит совпадений (это делается на стороне панели) или
ищите по частям — например, по номеру заказа.

### 19.4. «Подготовить стенд»

1. Создайте подключение к тестовому серверу.
2. Создайте базу `staging`.
3. Скопируйте схему: вкладка «Экспорт» у нужной таблицы в формате SQL → файл.
4. Импортируйте файл на стенд: вкладка «Импорт» → выберите файл `.sql` (таблицу указывать
   не нужно — таблицы создаст сам скрипт).
5. Сравните количество строк: `SELECT COUNT(*)` в SQL-редакторе.

### 19.5. «Дать коллеге доступ на чтение»

1. Создайте подключение к нужной СУБД с правами `SELECT` (или с правами администратора и
   ограничьте панель галочкой «Только чтение»).
2. Настройки → Пользователи → «Создать» → логин, пароль, роль `Readonly`.
3. Передайте коллеге логин и пароль панели.
4. Он увидит просмотр данных, поиск, экспорт и мониторинг, но не увидит кнопок изменения,
   удаления, импорта и управления правами.

### 19.6. «Разобраться, кто что делал»

- Вкладка «События» (или вкладка «Операции») — аудит панели: действие, объект, пользователь,
  результат, длительность.
- Вкладка «Последние операции» — выполненные SQL с указанием пользователя.
- API: `GET /api/audit?connId=<id>&limit=100` (роль `readonly` не имеет доступа).

### 19.7. «Восстановиться после ошибки в структуре»

После неудачного изменения структуры (индекс, внешний ключ, триггер, колонка):

1. Откройте таблицу → **«Откатить DDL»** в шапке. Панель восстановит удалённые индексы, внешние
   ключи и триггеры ([6.8](#68-откатить-ddl)).
2. Если последний пакет менял колонки, откат не сработает — но панель покажет DDL до изменения,
   который можно выполнить в SQL-редакторе.
3. Данные при этом не откатываются: если строки успели измениться или удалиться, верните их
   экспортом (раздел 11) или из резервной копии.

### 19.8. «Восстановиться после потери данных»

1. Настройки → Резервные копии → найдите расписание вашей базы.
2. Заберите нужный файл из каталога данных панели (у вас должен быть к нему доступ — в Docker
   том `dbpanel-data`).
3. Восстановление в интерфейсе не предусмотрено: попросите администратора выполнить
   `POST /api/backups/runs/:id/restore` (или импортируйте файл вручную: SQL → Импорт).
4. Для SQL-файла важно: он начинается с `CREATE TABLE IF NOT EXISTS`, поэтому в таблицу, где
   уже есть строки с теми же ключами, импорт добавит дубликаты. Сначала очистите таблицы
   (кнопка «ластик») либо воспользуйтесь восстановлением, которое очищает таблицы само.

## 20. Что делать, если не работает

### Не могу войти

- Проверьте раскладку клавиатуры (Caps Lock) и неверный регистр логина.
- Проверьте, не истекли ли 12 часов сессии: войдите заново.
- После смены вашей роли или удаления вашей учётной записи старая сессия перестаёт работать —
  это ожидаемо, войдите заново.
- Если учётных данных нет — обратитесь к администратору панели.

### Панель открывается, но ничего не происходит

- В шапке должно быть имя подключения и зелёная точка. Если «Нет подключения» — выберите
  подключение в левой панели.
- Категория СУБД показывает «Нет подключений» — подключение этого типа не создано.
- Категория показывает базы, но их список пуст — нажмите «↻» рядом с заголовком «Базы данных».
- Проверьте консоль браузера (F12 → Network): красная строка с кодом ответа и текстом ошибки —
  самый надёжный источник диагностики.

### «Внутренняя ошибка сервера»

Панель специально скрывает тексты ошибок драйверов (в них могут быть строки подключения, пути
и фрагменты SQL) — подробности только в логе backend. Попросите администратора посмотреть лог
сервера панели; там будет точная причина (проблема сети, отказ СУБД, нехватка прав, превышение
лимитов).

### Изменения не применяются

- Проверьте, не включено ли «Только чтение» у подключения (нет жёлтой полосы?).
- Проверьте вашу роль (роль `readonly` не может менять данные).
- Убедитесь, что выбрана правильная база: `INSERT`/`CREATE` уходят в выбранную базу, а не в
  «базу по умолчанию» подключения.
- Посмотрите результат в таблице под редактором: возможно, запрос вернул 0 изменённых строк
  (например, `WHERE` не совпал).

### Ошибки изменения структуры (DDL)

| Что видите | Что это значит | Что делать |
|---|---|---|
| **409** `Applied partially (2 of 5 ops). MySQL/MariaDB commit DDL implicitly and cannot roll back: fix it manually or re-apply.` | Пакет из нескольких операций оборвался на середине в MySQL/MariaDB. DDL там коммитится неявно, поэтому часть операций уже применена | Сверьте таблицу ([6.4](#64-вкладка-индексы)/[6.5](#65-вкладка-связи)), посмотрите применённый SQL в панели DDL и в журнале, доведите до нужного состояния точечными операциями; для индексов, внешних ключей и триггеров поможет «Откатить DDL» ([6.8](#68-откатить-ddl)) |
| **Пересборка SQLite не удалась (`Foreign key check failed: ...`)** | Новая структура нарушает внешний ключ (например, составной `PK` при дочерней ссылке на одну колонку) | Пакет откатывается целиком — данные целы. Исправьте структуру (PK/FK) и повторите. Подробнее — [6.3](#63-изменить-таблицу) |
| **Смена `PK` в SQLite** | Пересборка таблицы с новым первичным ключом | Выполняется панелью автоматически (см. [6.3](#63-изменить-таблицу)); дочерние внешние ключи должны указывать на новый ключ, иначе `foreign_key_check` откатит пакет |
| **`Bad FK action: ... (CASCADE / RESTRICT / SET NULL / SET DEFAULT / NO ACTION)`** | В правило `ON DELETE`/`ON UPDATE` попало значение не из списка | Выберите правило из выпадающего списка в форме связи: `CASCADE`, `SET NULL`, `RESTRICT`, `NO ACTION`, `SET DEFAULT` или пустое значение ([6.5](#65-вкладка-связи)) |
| **`Trigger body must be a single statement (SQLite allows several — they are wrapped in BEGIN ... END)`** | В теле триггера для MySQL/MariaDB больше одного стейтмента | Оставьте один стейтмент (обычно `SET ...` или `INSERT ...`). Несколько стейтментов допустимы только для SQLite |
| **`FK name is required`** | Имя ограничения не заполнено | У MySQL/MariaDB и PostgreSQL имя ограничения обязательно: заполните поле «Имя» в форме связи (например `fk_orders_user_id`) |
| **`FK columns/refColumns length mismatch`** | Число выбранных колонок не совпадает с числом ссылочных колонок | В «Колонки ref» перечислите столько же значений через запятую, сколько колонок выбрано слева |
| **`Bad column type for <диалект>`** | Тип колонки не входит в allowlist диалекта | Выберите тип из списка или задайте его вручную в SQL-редакторе ([6.2](#62-создать-таблицу)) |
| **`Index type GIN is PostgreSQL-only`**, **`Partial indexes (WHERE) are PostgreSQL-only`**, **`SQLite indexes have no type`** | Индекс создан с возможностями, которых нет у этой СУБД | Уберите поле «Тип» для SQLite, используйте `BTREE`/`FULLTEXT` для MySQL/MariaDB, `GIN`/`GIST`/`BRIN` — только для PostgreSQL |
| **400 `Primary key constraint name is required to drop it`** | Не удалось определить имя ограничения первичного ключа в PostgreSQL | Проверьте, что у таблицы вообще есть `PRIMARY KEY`; если ограничение переименовали, посмотрите его имя в `pg_constraint` и удалите ключ через SQL-редактор |
| **409** `Already exists: ...` (в том числе «триггер уже есть», «дубль имени индекса», «дубль ограничения») | Объект с таким именем уже есть | Удалите старый объект (корзина в строке) или выберите другое имя. Коды `ER_TRG_ALREADY_EXISTS`, `ER_FK_DUP_NAME`, `ER_DUP_KEYNAME`, `ER_TABLE_EXISTS_ERROR`, `42710`, `42P07`, `23505` панель переводит в 409 |
| **404** `Not found: ...` | Удаляемый объект уже отсутствует на сервере (коды `ER_TRG_DOES_NOT_EXIST`, `ER_NO_SUCH_TABLE`, `42P01`, `42704`) | Обновите карточку таблицы: возможно, объект удалён другим клиентом |
| **409** «The last package changed columns ... cannot be rolled back automatically» | «Откатить DDL» нажат после пакета, менявшего колонки или переименование | Панель покажет `CREATE TABLE` до изменения — выполните его вручную; автоматически откатываются только индексы, внешние ключи и триггеры ([6.8](#68-откатить-ddl)) |
| **403** на изменение структуры | Подключение в режиме «Только чтение» или роль `readonly` | Снимите галочку «Только чтение» (нужны права администратора) или войдите с ролью `editor`/`admin`. Текст ответа: `Connection is read-only` |

Общее правило: любая операция изменения структуры недоступна для роли `readonly` и для
подключения в режиме «Только чтение», даже если вы видите её в интерфейсе через прямой API —
backend отвечает 403 (`assertRoleWritable`). Если текст ошибки начинается со слов
«Bad column type», «Bad FK action», «Bad index type», «Bad trigger …» — это проверка формы
панели, а не проблема сервера: исправьте введённое значение по подсказке из сообщения.

### Экспорт «зависает»

Это нормально для больших таблиц — данные идут потоком. Если соединение обрывается, уменьшите
объём: экспортируйте по таблицам или используйте CSV. При обрыве попробуйте скачать напрямую
через API в `curl`/браузере — панель отдаёт файл потоком и не держит его в памяти.

### Импорт не удался

- Смотрите текст ошибки: он указывает причину (нет прав, нет таблицы, превышен лимит, неверный формат).
- Импорт не откатывает уже вставленные строки — проверьте таблицу и при необходимости очистите её.
- Для CSV/JSON убедитесь, что имена колонок в файле совпадают с колонками таблицы.
- Для SQL убедитесь, что скрипт написан в диалекте вашей СУБД.

### Бэкап не создался

- Вкладка «Резервные копии» → «Создать копию сейчас»: при ошибке придёт текст от СУБД
  (например, «Access denied» — у пользователя подключения нет `SELECT`).
- Для MongoDB формат должен быть `JSON`.
- Проверьте свободное место в каталоге данных панели.

### Кнопка «Выйти» не появляется

Панель запущена без обязательной авторизации. Это значит, что вход и роли не применяются —
обратитесь к администратору, если это не задумано.

### Панель «медленная»

- Возможна лимит частоты запросов (200 в минуту) — при множестве открытых вкладок.
- Поиск по большой базе читает данные таблиц — он действительно тяжёлый.
- Мониторинг обновляет данные каждые 10 секунд; при множестве вкладок нагрузка суммируется.

## Приложение A. Поднять панель самостоятельно

Требуется Node.js 22+ и Docker (для демонстрационных СУБД).

```bash
npm ci
cp backend/.env.example backend/.env
```

В `backend/.env` обязательно замените:

```ini
ENCRYPTION_KEY=<64 hex: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))">
JWT_SECRET=<длинная случайная строка>
ADMIN_PASSWORD=<пароль длиной не менее 12 символов>
```

Дальше два пути.

**Весь стек в Docker** (UI на `http://localhost:3001`, API на `http://localhost:3002`):

```bash
npm run stack:up
npm run seed:dbs
```

**Локально** (UI на `http://localhost:3000`, API на `http://localhost:3001`):

```bash
npm run dbs:up
npm run seed:dbs
npm run dev:backend     # в одном терминале
npm run dev:frontend    # в другом
```

Демо-данные: база `demo` с таблицей `users` (Ann, 30 лет; Bob, 25 лет) на MySQL, MariaDB,
PostgreSQL и MongoDB; Redis без данных.

Команды администратора: `npm run build`, `npm run typecheck`, `npm run verify`,
`npm run e2e:all` (нужны поднятые СУБД и backend с `REQUIRE_AUTH=1`).
Схема API: `http://localhost:3001/docs` (или `:3002/docs` в Docker) — Swagger UI.
